# Логи проблем ZeTer OS — порядок анализа для CODEX

Эта папка находится рядом с `run_zeter_os.py`. На каждый день использования ZeTer OS создаёт каталог `ГГГГ-ММ-ДД`, а внутри — компактный и сортируемый по времени `run-ЧЧММСС-мс-<id>`. Новый сеанс начинается при запуске и при первом действии нового дня без перезапуска программы. Операция, начатая до полуночи, завершается в исходном сеансе, чтобы сохранить её связь с началом. Пользовательские документы, имена файлов, полные пути, URL, токены и исходные тексты ошибок намеренно не записываются.

## Читать в таком порядке

1. `latest_run.json` — проверить `owner`, `schema`, `day`, `session` и открыть указанный файл. При `mode: daily-overflow` читать дневной `overflow.json`, а не искать несуществующий run-файл.
2. В указанном `run-ЧЧММСС-мс-<id>/manifest.json` — сверить версию, runtime и `sourceSetSha256`; не смешивать выводы от разных наборов исходников.
3. В том же сеансе открыть `summary.json` — итог, целостность диагностики, дедуплицированные проблемы, метрики и `improvementSignals`.
4. `problems.jsonl` — первое безопасное evidence для каждого fingerprint: этап, outcome, тип исключения, errno/winerror и относительные source frames.
5. `events.jsonl` — использовать только для восстановления порядка этапов и distinguishing check.

`latest_problem.json` — быстрый указатель на последнее опубликованное сообщение о проблеме. У дневного fallback проверяй `evidenceAvailable`: при `false` подробного образца этой ошибки нет, `evidenceOmitted` объясняет ограничение. Указатели сравнивают время и идентификатор; закрытие старого параллельного сеанса не заменяет новый. `report.txt` — короткая человеческая сводка. `health.json` показывает полноту журнала.

## Дополнительный диагностический контекст

`schema: 1` сохраняется для совместимости. `diagnosticRevision: 2` обозначает расширенные записи; отсутствие поля означает старый журнал. Старые сеансы не переписываются.

- `operationId`, `parentOperationId`, `rootOperationId` связывают вложенные этапы с конкретным сохранением. Это внутренние идентификаторы, а не ID документов. Исключение содержит тип, числовые errno/winerror, ограниченную цепочку причин и относительные source frames. `failureClass: access_denied` не означает временную блокировку.
- `metrics[stage].lastCompleted`, `lastIssue`, `lastSuccess` показывают порядок завершения и последний результат даже после ограничения timeline. `laterSuccessCount` и `successAfterIssue` означают поздний успешный вызов того же этапа; они не доказывают устранение всех прежних ошибок или исправность того же пользовательского объекта. Исторические fingerprints и повторы сохраняются.
- `problemClassification` разделяет наблюдения ошибок, частичных результатов и медленных операций. Один сбой может наблюдаться на нескольких вложенных этапах: счётчики не равны числу независимых аварий. `inFlightOperations` отличает незавершённые операции; закрытие прямого logger с активной операцией помечается `incomplete`, а целостность — `degraded`.
- Медленное `save_state` сопоставляй с `primary_confirm`, `previous_backup`, `readable_build`, `readable_publish`, `archived_export`, `payload_cleanup` и `lockWaitMs`. `childMs`/`selfMs` относятся к синхронным вложенным этапам в одном потоке; длительности включают накладные расходы диагностики.
- При публикации Windows-копии сохраняются безопасные `publishAction`, `fileKind`, счётчики замен/неизменных/удалённых файлов и, когда доступны, `targetExisted`, `targetReadOnly`, `targetStatusKnown`. `publicationComplete: true` записывается после публикации дерева и сводки. Имена документов и полные пути не записываются.
- `identity` — снимок файлов на диске в начале сеанса, не доказательство байтов уже загруженного Python/JS. `processStartIdentity` сохраняет первоначальный снимок при смене дня; `diskSourceDrift` показывает расхождение. `sourceFileCount` — ожидаемое число файлов, `hashedSourceFileCount` — прочитанное; missing counts и `sourceIdentityComplete` показывают пробелы. Для frozen-режима записывается SHA-256 executable, если файл доступен, без его пути. Mock frozen не доказывает запуск установленного EXE.
- `previousIncompleteCount` и до восьми `previousIncompleteSessions` показывают найденные сеансы без закрытой сводки. Они могут быть ещё активны или прерваны; причина неизвестна, старые файлы не меняются. `previousIncompleteOmitted` показывает число не вошедших в список.

Первые три перехода к позднему успеху сохраняются дополнительно к обычным timeline-примерам; все totals и последние результаты остаются в summary. Если расширенный контекст не помещается в лимит управляющего JSON, `contextDetailsOmitted: true` и health-gap `summary_context_limited` явно обозначают сокращение: итоговые outcome, время, связи операций и счётчики сохраняются, необязательные result-поля убираются. Дневной `overflow.json` остаётся сокращённым fallback без полного расширенного контекста.

## Правила вывода

- `health.integrity = degraded`, ненулевой `dropped` или `diagnosticGaps` означают: отсутствие записи не доказывает отсутствие сбоя.
- Один fingerprint в `problems.jsonl` может иметь много повторений; точный счётчик находится в `summary.json`.
- `slowestOperations` — сигнал для измеримого улучшения, а не автоматическое доказательство бага.
- Сначала установи failure stage по `events.jsonl`, затем root cause по `problems.jsonl` и source frames. Не восстанавливай скрытые сообщения, пути или содержимое по догадке.
- Для сравнения запусков группируй только совпадающие `schema`, версию и `sourceSetSha256`.

## Ограничения размера

Записываются первые три вызова каждого этапа и первые три timeline-примера каждого проблемного outcome; точные totals остаются в `summary.metrics`. Повторы проблем дедуплицируются и увеличивают `occurrences`. Один сеанс ограничен 2 МиБ, вся папка — 32 МиБ; timeline-запись — 4 КиБ, управляющий JSON — 64 КиБ. Внутри бюджета сеанса 128 КиБ защищены от обычных событий для проблем и завершения.

Из общего бюджета заранее выделен 1 МиБ для одного `overflow.json` до 4 КиБ на день. При заполнении подробного журнала уже записанные сеансы сохраняются, а дневной fallback учитывает запуски, закрытия, операции, ошибки, пропущенные подробности, отказы самой диагностики и до четырёх безопасных образцов. У каждого образца собственный source hash. Сводка всегда `degraded`, `detailsComplete: false`; она не доказывает отсутствие других проблем. Счётчики активных запусков могут отставать до очередного сброса; при закрытии сбрасываются итоговые значения. Межпроцессный lock защищает приращения от потери и повторного начисления.

App-owned сеансы и дневные fallback-файлы старше 120 полных календарных суток удаляются, включая незавершённые; ровно 120 суток сохраняются. До этого срока журналы не удаляются ради размера. Неизвестные, вручную добавленные файлы и небезопасные ссылки не удаляются автоматически. Если внешние файлы уже заняли весь бюджет, папка недоступна или диск заполнен, запись может не состояться: фиксируется короткий stderr-сигнал без перенаправления в другое место.

При каждой записи бюджет пересчитывается под межпроцессным lock без кэша размера. Обход проверяет всю цепочку пути перед открытием каждого каталога, затем атрибуты его элементов без перехода по ссылкам. Symlink/reparse и ошибки чтения каталога или атрибутов приводят к отказу измерения, а не к успешному частичному размеру. Повторная проверка одних и тех же родителей для каждого файла не выполняется.

## Граница проверки

Автоматические проверки используют временные каталоги: подтверждают редактирование кодов исключений, границу срока, квоты, атомарные указатели, два процесса и смену дня во время операции. Они не заменяют запуск desktop/pywebview из фактической переносной папки. Проверка Windows-ссылок, запрета записи и аварийного выключения на пользовательском компьютере остаётся отдельным runtime-тестом. Файлы браузерного режима без Python здесь не создаются.
