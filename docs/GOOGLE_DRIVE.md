# Google Drive: архивная интеграция (пользовательский интерфейс отключён)

**Текущий интерфейс ZeTer OS:** в разделе «Копии и восстановление» находятся только две кнопки: «Скачать резервную копию данных» и «Загрузить резервную копию данных». Работа идёт с локальными ZIP, без обращения к Google Drive. Из интерфейса удалены облачное подключение, расписание, списки облачных архивов и ручное создание точек восстановления. Автоматические точки по таймеру отключены; аварийная страховка перед восстановлением сохранена. Ни старые облачные, ни локальные данные не удалены.

## Историческая информация о ранее доступных режимах

Дальнейшие сведения описывают предыдущие варианты, оставленные только для сопровождения кода и старых данных; это **не действующие пользовательские возможности**.



**Действующая схема (с 27.10.2026):** в разделе «Копии и восстановление» пользователь подключает Google Drive, нажимает «Создать ZIP и загрузить в Google Drive» либо включает расписание (1–720 часов, по умолчанию выключено). Полный ZIP содержит JSON-состояние и обязательные локальные файлы, манифест и SHA-256. Архив проверяется локально перед upload; после отправки API сверяет размер, SHA-256/MD5 и перечитывает ZIP. Native и Web используют одинаковые appProperties `app=zeter-os-backup`, `kind=backup-v1` и одну папку «ZeTer OS — резервные копии»; старое дерево `ZeTer OS/data` не трогается. Список ZIP берётся из Google Drive, фильтруется по appProperties владельца и может быть пустым до первой успешной записи. Ни вход в Google-аккаунт, ни наличие старого head в Cloudflare/D1 **не означает успешный ZIP-бэкап**.

При нажатии «Скачать ZIP» файл скачивается после проверки checksum и ZIP-структуры. «Проверить / восстановить» открывает существующий безопасный мастер: можно вернуть выбранный файл/проект/стол отдельно или после дополнительного подтверждения полностью заменить ZeTer OS из архива. До применения выполняется проверка содержимого, а непосредственно перед записью создаётся подтверждённая страховочная точка. В браузере/на телефоне восстановление некоторых Windows-вложений может быть ограничено — ZIP можно скачать и открыть на Python/EXE. Ни подключение, ни обновление списка автоматически не заменяют локальные данные.

Native расписание хранится в `%LOCALAPPDATA%/ZeTer OS/google-drive/installation-<hash>/zip-preferences.dpapi`; браузер использует отдельную IndexedDB `zip-backups-v1`. Настройки не смешиваются со старой синхронизацией. Архивы не удаляются автоматически, а таймер работает только при запущенной ZeTer OS и подтверждённом Google-подключении; без сети данные продолжают жить локально. Один архив — до 120 МиБ, полный ZIP не содержит внешние файлы, на которые указывают ярлыки. У ZIP нет собственного пароля, поэтому защищай Google-аккаунт.

Ключевой код: `security_backup.py` (проверенный архив), `google_drive_backup.py` (`zip_preferences`, `upload`, `list`, `download`), `app/js/core/google-drive-backup-utils.js` (`createController`), `app/js/core/security-recovery-utils.js` (проверка и восстановление), `app/js/app.js` (только ZIP-контроллер). Проверки: `python tools/smoke_google_drive_zip_mode.py`, `python tools/smoke_google_drive_backup.py`, `node tools/smoke_google_drive_runtime.js`, `node tools/smoke_security_restore.js`.

## Архивная спецификация: прежняя файловая синхронизация (не используется при обычном запуске)

Ниже оставлены технические сведения о старом файловом обмене с Cloudflare/D1, чтобы можно было разбирать старые логи и мигрировать данные. Описанные ниже автоматические конфликты и синхронизация `ZeTer OS/data` **не являются действующим пользовательским режимом** и не запускаются из интерфейса ZIP-копий.

Исходники поддерживают автоматическую синхронизацию через Google Drive. Worker и отдельная D1 развёрнуты; код Worker проверен контрольным чтением. Настоящий Windows OAuth, проверка аккаунта координатором, запись/чтение отдельного искусственного файла, повтор без дубликата и продление Google-доступа проверены. Обмен Windows ↔ телефон, опубликованные сборки и доступ другого Google-аккаунта требуют отдельной приёмки.

## Пользовательский контракт

Предупреждение о разных версиях относится к конфликту, проверенному в текущем подключении. После отключения или до первой успешной сверки сохранённая запись конфликта не показывается как состояние облака. Страховочные копии сохраняются. Если координатор подтвердил отсутствие облачного снимка, старый конфликт не мешает первой отправке; запись конфликта очищается только после принятой и проверенной публикации. Пустая видимая папка Google Drive сама по себе не является доказательством отсутствия принятого снимка у координатора.

Каждый пользователь подключает один свой Google-аккаунт внутри ZeTer OS на каждом устройстве. Перед первым подключением показаны короткие правила; отдельной галочки подтверждения нет. Успешное подключение автоматически включает обмен после подтверждённого сохранения настройки; отдельные «Включить» и «Применить» не нужны. Подробная инструкция для EXE, Python и телефона свёрнута. Перед сменой устройства нужно дождаться «Всё синхронизировано», а на следующем устройстве — нажать «Загрузить новые данные» в синем уведомлении. До явного подтверждения облачные данные не применяются, включая первое подключение пустого устройства. «Позже» сохраняет предложение в центре уведомлений и панели Google Drive; та же версия не вызывает повторный popup. Новая облачная версия может показать новое уведомление. Отправка локальных изменений остаётся автоматической. Без сети работа остаётся локальной. Если обе версии изменились, автоматическая замена останавливается; обе ветки сохраняются до явного выбора пользователя.

На Drive находятся обычные файлы в `ZeTer OS/data`, а не ZIP. Загружаются изменившиеся файлы и новое описание состояния. Обязательные внутренние файлы и оформление входят в снимок. Внешние цели ярлыков не читаются, сами записи ярлыков остаются в состоянии. Служебная история хранит прежние неизменяемые версии. Автоматическое удаление облачных файлов не предусмотрено.

Если общая папка удалена с Google Drive, при следующем обмене ZeTer OS создаёт новую и полностью загружает в неё текущие локальные данные. Удалённая папка остаётся в корзине. Новая структура закрепляется один раз для аккаунта, поэтому одновременный запуск устройств и повтор после обрыва используют ту же папку. Новая облачная копия содержит данные устройства, которое первым завершит загрузку; последующие отличающиеся версии проходят обычную проверку конфликта. Сетевые ошибки, отказ авторизации и чужие служебные метки не считаются удалением и не запускают создание папки. Повторное удаление ещё не завершённой новой копии останавливает обмен для проверки.

Проверенный `trashed:true` разрешает пересоздание даже до первой принятой копии. HTTP 404 считается удалением у корня принятой копии; до её появления ID может быть лишь зарезервирован и ещё не создан. В последнем случае повтор использует тот же ID, чтобы обрыв первой передачи не создавал дубликаты. Новая резервация и история замен хранятся в D1, прежний принятый head меняется только после полной загрузки через CAS. Контракт `/sync/recreate` и миграция принадлежат [README брокера](../cloud/google-drive-broker/README.md).

## Владельцы

- `google_drive_backup.py`: Desktop PKCE, системный браузер и временный loopback callback, обновление Google-разрешения. Токены CurrentUser DPAPI вне `data` и экспортов: `%LOCALAPPDATA%/ZeTer OS/google-drive/`.
- `google_drive_sync.py`: только собственные обычные Drive-файлы/папки, контрольные суммы, уникальные operation ID, metadata-only перемещение; запросы к координатору.
- `app/js/core/google-drive-backup-utils.js`: OAuth web/native adapters, broker session и панель подключения.
- `app/js/core/google-drive-sync-utils.js`: единый Windows/browser алгоритм, baseline, incremental snapshot, CAS, конфликт и согласование видимой папки.
- `app/js/core/cloud-payload-utils.js`: проверенные browser Blob, пути и сохранённые ветки в отдельной IndexedDB.
- `app/js/app.js`: сбор сохранённого состояния, безопасное применение и подключение контроллеров.
- `cloud/google-drive-broker/`: HTTPS OAuth/refresh и D1 account-bound head; инструкция развёртывания принадлежит его `README.md`.

## Облако и защита данных

Публичный `app/google-drive-config.json` содержит только `desktopClientId`, `webClientId`, `brokerUrl`. Google client secret и ключ шифрования запрещены в `app`, экспортах, Git и сообщениях ошибок. В браузере access token живёт в памяти, opaque broker session — в отдельной IndexedDB. Эта постоянная сессия является секретом входа; хранение в IndexedDB не защищает от вредоносного кода того же origin.

Для браузера брокер хранит зашифрованный Google refresh token, привязку аккаунта и сведения о принятой версии. В Windows код входа с PKCE и последующее обновление проходят через фиксированный `/native/token`; Desktop client secret остаётся в Cloudflare Secrets. Native refresh token сохраняется только локально через Windows DPAPI, сервер передаёт его Google без записи в D1 и журналы. Содержимое пользовательских файлов через брокер не проходит. Обычное отключение закрывает только это подключение, без глобального Google revoke для остальных устройств. Для Desktop-сеанса брокер проверяет Google audience/authorized client/scope/expiry, затем Drive identity; произвольный token другого OAuth-приложения не принимается.

Native HTTP-порт меняется при запуске, поэтому настройки/baseline не хранятся только в IndexedDB локального origin. `google_drive_sync_preferences` использует DPAPI-каталог `installation-<SHA256 resolved DATA_DIR>` внутри private credentials root. `google_drive_sync_preserve` сохраняет проверенную конфликтную ветку локальным неизменяемым ZIP в его `conflicts/`; этот архив в Drive не загружается. Browser использует собственную стабильную IndexedDB сайта. Private metadata и ветки автоматически не удаляются.

Предложение входящей версии — временная UI-проекция контроллера, вне workspace.notifications и синхронизируемого состояния. При отключении или смене аккаунта оно исчезает; прежние кнопки теряют силу. Подтверждение заново проверяет актуальную версию, аккаунт и локальные изменения.

## Публикация состояния

Сбор открытых заметок, Markdown, названий таблиц и стикеров меняет `updatedAt` и запускает сохранение только при реальном изменении полей. Чтение неизменённого редактора не назначает новую синхронизацию и не создаёт повторные конфликтные ветки.

Каждая фоновая сверка проверяет текущий облачный указатель и локальный снимок. После полностью завершённого согласования в текущем процессе повторное скачивание неизменённых вложений пропускается до пяти минут. Перезапуск, незавершённый план передачи, изменение указателя и команда «Проверить синхронизацию сейчас» сохраняют полную проверку; незавершённая публикация не считается согласованной. После конкурентной записи явный выбор локальной версии создаёт предложение для актуального поколения, сохраняя прежние облачные файлы в истории.

Google может уточнить MIME обычного вложения, отправленного как `application/octet-stream`, например до `image/png`. Это допускается только для binary payload; типы папок, состояния и манифеста остаются строгими, Google-native документы не принимаются как обычные bytes. Проверки namespace, ID, имени, родителя, operationId, pathKey, SHA-256, размера и прочитанных bytes сохраняются.

Новые bytes получают новые Drive IDs. Прежние принятые bytes не перезаписываются. Неизменённые файлы повторно используются по ID, SHA-256 и размеру. Снимок содержит точный список `{path,fileId,sha256,sizeBytes}` и отдельный immutable state. Указатель в D1 принимает новую версию условной записью по ожидаемому поколению; проигравший конкурент не заменяет принятую версию. Повтор операции использует прежний operation ID.

До создания объектов контроллер сохраняет `uploadIntent`, затем выделенные Drive IDs. Потеря ответа или перезапуск повторяет тот же ID. Координатор атомарно закрепляет одну структуру `root/data/history/staging` на аккаунт и один ID каталога по корню и пути; два устройства не выбирают разные папки из-за задержки списка Drive. Существующая единственная подходящая папка переиспользуется, неоднозначность дочерних папок останавливает обмен без удаления. Подробности полей и миграции — в [NATIVE_BRIDGE.md](NATIVE_BRIDGE.md) и [README брокера](../cloud/google-drive-broker/README.md).

После принятия указателя обычная папка `data` приводится к этому снимку, state — последним. Изменение дерева папок Drive не является атомарной транзакцией: источником истины служит принятый immutable manifest. Перед согласованием дерева нужно перечитать актуальный head; старый receipt не разрешает переместить файлы поверх более нового поколения.

Получение версии проверяет все bytes и schema до применения. Primary ACK, сохранённая страховочная точка и проверка отсутствия новых локальных изменений предшествуют публикации live-state. После native path remap baseline считается по фактическому локальному состоянию. Телефон сохраняет исходные Windows-вложения в отдельном Blob-хранилище для возврата на компьютер. Возможности DOC/DOCX-редактирования в браузере этим не расширяются.

## Проверки и ограничения

Команды и preflight принадлежат [TESTING.md](TESTING.md). Реальные данные `data/` запрещены для synthetic tests. Native тест вводит synthetic credentials root и `configure_temp_data` до конструктора API.

Текущий безопасный предел связан с существующим импортом: 120 МиБ полного набора, ограниченное число файлов. Не увеличивать его только в транспорте: нужны согласованные проверки коллектора, staged payload, browser quota и применения. Закрытое приложение не обменивается свежими локальными изменениями. OAuth Testing, Workspace-политики, отзыв доступа и free-hosting quotas могут прерывать соединение.

Google Audience настроен как `External / In production`; сохранён только non-sensitive `drive.file`. Verification Center не требует проверки sensitive/restricted scopes. Проверка оформления Google отдельно от доступа: отсутствие опубликованного branding не доказывает сбой OAuth. Разрешение, полученное ранее в режиме Testing, может потребовать повторного подключения после семи дней; публичный режим не делает старые разрешения бессрочными.

Native OAuth/tokeninfo и обновление доступа проверены на настоящем аккаунте с отдельным credentials root и искусственными файлами. Этот тест не записывает canonical head аккаунта. D1 CAS `RETURNING`, popup/COOP, совместная видимость Desktop/Web клиентов, установленная PWA и EXE требуют самостоятельного runtime evidence.

Для 4.0.92 на настоящих Google Drive и D1 проверены fixed-ID запись/повтор/чтение 34 искусственных байтов, обновление доступа и повторный bootstrap с теми же четырьмя ID. Сайт опубликован с проверкой 136 файлов и переключением манифеста последним. Живой веб-вход не завершён: управление окном выбора аккаунта Google остановилось по тайм-ауту; до чтения/записи тестового файла веб-клиент не дошёл. Временная тестовая страница обезврежена, постоянные данные приложения в ней не использовались. Обмен между настоящими Windows и телефоном, установленная PWA и собранный EXE остаются отдельной проверкой.


## Диагностика ошибок синхронизации (Python/EXE)

Сбор событий начинается автоматически в `run_zeter_os.py`, когда запущен исходный проект с новым кодом. Не надо включать debug-консоль или копировать аккаунт и токены. Новый сеанс находится в `Логи проблем/ГГГГ-ММ-ДД/run-.../`. Сначала читай `latest_run.json`, затем `events.jsonl`, `problems.jsonl`, после закрытия — `summary.json` и `report.txt`.

Для диагностики Google Drive фильтруй события по `stage`:

- `google_drive_connection`: обращение к native OAuth/Google Drive; `driveAction=status|connect|...`, безопасные `driveError`, время.
- `google_drive_sync_rpc`: конкретный вызов backend, например `sync_head`, `sync_commit`, `bootstrap`, `put_file`, `read_file`; статус ошибки и при успешном `sync_head` — `cloudHeadPresent`, `cloudGeneration`, `rootMissing`.
- `google_drive_client`: путь принятия решений в JS: `remote_checked`, `local_collected`, `conflict_saved`, `publish_start`, `publish_committed`, `reconcile_complete`, `choice_selected`, `incoming_offered`, `failure` и смены `drivePhase`.

При повторе одной и той же стадии JS ограничивает частоту технических событий пятью минутами. Подтверждённые ошибки JS попадают также в `problems.jsonl` с дедупликацией без счётчика попытки. Проблемы Python фиксируются с безопасными типами исключений, временем выполнения, причинными этапами и классификацией отказа; сырые тексты исключений не сохраняются.

**Разбор «папка Google Drive пуста, но есть конфликт»:** проверь `remote_checked.cloudHeadPresent`. Значение `true` говорит только о сохранённом указателе принятого снимка на сервере; оно **не доказывает**, что пользователь видит содержимое `ZeTer OS/data` или что целостность снимка подтверждена. Проверь `rootMissing`, этапы `read_file`, `reconcile_complete`, `publish_committed` и `cloudGeneration`. Запись `conflict_saved` — локальная защищённая конфликтная ветка, а не успешная отправка на Google Drive. Ни пустая папка, ни `status.phase=conflict` не дают права автоматически перезаписывать версии или очищать D1.

**Утерянный манифест при сохранённом head:** если координатор подтверждает принятую версию, но Google Drive API возвращает HTTP 404 на её manifestFileId при существующем root, старое облачное состояние нельзя загрузить. Native мост сообщает строгое сообщение `Принятый манифест облачной копии отсутствует в Google Drive.`, а синхронизатор выставляет `cloudManifestMissing`. Выбор облачной версии в интерфейсе блокируется. Обычный запуск и автоматический опрос **не меняют серверный head и не загружают местные данные**. Только после отдельного подтверждения «Использовать данные этого устройства» программа сохраняет локальную страховочную копию, формирует новый полный immutable snapshot без чтения удалённого манифеста, выполняет CAS с ожидаемым поколением и проверяет видимое дерево файлов. Ошибки других классов (сеть, запрет доступа, checksum, повреждённый JSON) не разрешают этот обход. Даже после нового снимка восстановить ранее физически удалённые байты невозможно.

**Коды ошибок:** `token_broker_unreachable` — недоступен обмен OAuth через Worker; `broker_unreachable` — недоступен координатор синхронизации; `google_unreachable` — сбой обращения к Google; `auth_required` — требуется новое подключение; `safety_readback` — ошибка подтверждения контрольным чтением; `stale_cloud` — версия изменилась параллельно; `unknown_failure` — данных недостаточно, смотри ближайший backend-этап и `problems.jsonl`. Невозможно отличить DNS, TLS, прокси, сетевой timeout и блокировку фаерволом только по общему коду; для этого нужна отдельная безопасная проверка сети. Историю ошибок не удалять и не выдавать отсутствие события за отсутствие сбоя, если `health.integrity=degraded`.

Никогда не сохраняются `accessToken`, `refreshToken`, session handles, Google account/email, Google file IDs, имя или содержимое пользовательского файла, локальные пути, URL с параметрами, сырые JS/Python ошибки и HTTP-body. Схема клиента принимает только фиксированные enum и неотрицательные счётчики; неизвестные поля полностью отклоняются. Инструментальные события не влияют на состояние синхронизации, Google Drive и пользовательские файлы.
