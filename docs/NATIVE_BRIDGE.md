# JavaScript ↔ Python bridge

Этот документ фиксирует публичный контракт между веб-интерфейсом и `run_zeter_os.py`.

## Запуск native-режима

1. `run_zeter_os.py` запускает локальный HTTP-сервер только на `127.0.0.1` со свободным портом.
2. pywebview открывает `index.html?native=1` и передаёт экземпляр `NativeStorageApi` как `js_api`.
3. `app/js/core/native-storage.js` распознаёт native-режим по query-параметру или доступному `window.pywebview.api`.
4. `app/js/app.js` ждёт событие `pywebviewready` не более 3000 мс и вызывает Python только через `nativeStorageCall(...)`.
5. В native-режиме service worker не регистрируется; данные сохраняются в папку `data`.
6. До создания pywebview-окна `startup_window_maximized()` безопасно читает `state.systemSettings.startup.windowMode` из текущего `data/zeter-os-state.json`. Значение `windowed` запускает обычное окно 1320 × 840, остальные/старые/повреждённые значения используют совместимый развёрнутый режим.

## Формат ответа

Установщик описан в [UPDATES.md](UPDATES.md). Служебная страница `app/update-probe.html` имеет отдельный bridge `confirm_update_probe(nonce, version)`: подтверждение проверяется отдельным ProbeApi без создания NativeStorageApi, пользовательского state и startup normalization/GC. Эта страница не загружает `app.js` и не является обычным запуском рабочего пространства.

Все публичные методы возвращают объект:

- успех: `{ ok: true, ...данные }`;
- ошибка: `{ ok: false, error: "понятный текст" }`.

Если существующий `zeter-os-state.json` не читается, содержит повреждённый JSON или некорректную обёртку `state`, `load_state()` возвращает ошибку. JavaScript оставляет запись заблокированной и не подменяет такое состояние новым default state.

`nativeStorageCall` преобразует `ok: false` в JavaScript `Error`. Не меняй envelope без одновременного обновления обеих сторон и smoke-теста ошибок.

Checker автоматически сравнивает публичные методы класса, вызовы `nativeStorageCall(...)`, эту таблицу и наличие envelope `{ ok, error }`.

Ранний `boot-guard.js` вызывает `report_client_error(details)` напрямую, потому что ошибка может произойти до загрузки `native-storage.js`; после успешного запуска он продолжает ловить необработанные runtime-ошибки. JavaScript передаёт тип, источник, строку и колонку, но Python записывает только разрешённый тип, относительный известный source и числовые координаты. Сообщение, stack, URL, состояние и пользовательские документы в `Логи проблем` не попадают.

## Автозапуск Windows

`WindowsStartupManager` работает только с пользовательской веткой `HKCU`, поэтому включение не требует прав администратора и действует после входа текущего пользователя Windows. Для исходной Python-версии команда использует `pythonw.exe`, если он находится рядом с текущим интерпретатором, и абсолютный путь к `run_zeter_os.py`; для собранной версии — путь к текущему executable. Аргументы формируются без shell через `subprocess.list2cmdline`.

Источник истины — сама запись Windows, а не `state` отдельного рабочего стола. `get_windows_startup_status()` считает включённой только запись, которая точно указывает на текущую копию программы. Запись из старого расположения возвращается как `stale: true`: интерфейс снимает галочку и предлагает включить её снова для безопасного обновления пути. JavaScript не получает и не логирует абсолютную команду автозапуска.

## Сохранение

JavaScript формирует запись с `id`, версией, режимом, временем, размером и `state`. Python создаёт отдельную JSON-копию входа, проверяет объект `state`, очищает удалённые ссылки только в этой рабочей копии, атомарно записывает JSON и повторно читает его. Ответ `ok: true` содержит `primaryVerified: true` только после совпадения прочитанной записи с подготовленной.

Перед записью Python заменяет только служебный абсолютный путь из native-статуса папки на переносимый `data/zeter-os-state.json`. Пользовательские абсолютные цели Windows-ярлыков не меняются. Windows-читаемая копия, payload-cleanup и ротация backups запускаются только после подтверждённого основного файла. Если primary-запись не удалась, прежний state, restore points, backups и payload не меняются, ответ содержит `ok: false`, `stage: "primary-confirm"`, а причина попадает в лог. Если не удалась только производная Windows-копия, основной state остаётся успешно сохранённым, а ответ содержит `readableOk: false`.

Производная копия и метрики:

Публикация Windows-копии пропускает файлы с одинаковым содержимым. Для generated DOCX сравниваются все части ZIP, включая изображения и relationships; даты и способ сжатия архива не означают изменение документа. Изменённый недоступный файл по-прежнему даёт `readableOk: false`, прежняя копия этого файла сохраняется; весь каталог не является одной атомарной транзакцией. Контекст этапов описан в [контракте диагностики](<../Логи проблем/README_FOR_CODEX.md>).

`get_storage_info()` возвращает наблюдаемые размеры и количество файлов из одного `stat` на файл. Исчезновение файла во время обхода пропускается; другие ошибки доступа остаются видимыми. Это приблизительная сводка меняющейся папки, а не атомарный снимок всех категорий.

Защита основной записи:

- каждая запись использует свой временный `.zeter-atomic-*.tmp` в каталоге назначения, `flush`/`fsync`, `os.replace` и обязательную очистку остатка при ошибке;
- ограничение читаемого JSON размером 200 МБ;
- дневная startup-копия и периодические previous-снимки с уникальными именами;
- максимум двенадцать автоматических backup-файлов;
- максимум двенадцать точек восстановления; активный профиль может хранить меньше;
- старый подробный журнал операций в `data/logs/zeter-os.log`;
- компактная диагностика для CODEX в `Логи проблем` рядом с программой; размещение по дням, лимиты и fallback принадлежат `Логи проблем/README_FOR_CODEX.md`.

Обычное сохранение и удаление объекта не переписывают существующие restore points и JSON-backups. Эти снимки удаляются только ротацией по лимиту, выбранной пользователем очисткой или отдельным подтверждённым действием. Перед очисткой payload Python объединяет ссылки из текущего state, всех оставшихся точек и всех оставшихся JSON-файлов `data/backups/`. Если хотя бы один из этих источников повреждён или содержит небезопасный путь, очистка пропускается целиком.

Чтение, preflight, добавление, замена по ID, удаление и очистка `restore-points.json` синхронизированы одним reentrant-lock. Изменяющие операции дополнительно соблюдают общий порядок блокировок `state → restore points → uploads`, поэтому read-modify-write и последующий payload-GC видят один согласованный набор точек. Параллельные запросы не делят общий `.tmp` и не теряют уже записанную точку.

`clear_state()` сначала создаёт уникальную побайтово проверенную JSON-копию прежней основной записи. Сам основной файл удаляется только после подтверждения этой копии. Managed-файлы, значки и фоны не удаляются, пока на них ссылается созданная копия, точка восстановления или другой оставшийся backup.

Перед применением native-точки JavaScript вызывает `preflight_restore_point`. Отсутствующий файл либо путь за пределы управляемых каталогов блокирует замену состояния: интерфейс показывает точный список и предлагает восстановить полный payload из проверенного ZIP-бэкапа.

Текстовые скачивания из native-окна проходят через `save_text_download`: пользователь выбирает папку и имя в системном диалоге, отмена не создаёт файл и не считается ошибкой, CSV записывается как UTF-8 с BOM для совместимости с Excel, размер входа ограничен 20 МБ. Если в диалоге подтверждена замена существующего файла, запись выполняется атомарно.

Двоичные скачивания проходят через `save_binary_download`: Base64 проверяется до записи, размер ограничен 50 МБ, XLSX и ZIP получают профильный фильтр системного диалога. В лог попадают путь, MIME-тип и размер, но не содержимое файла.

`save_desktop_backup` принимает только `{desktop, fs}`, а не всё состояние ОС. В ZIP сохраняются `desktop.json` (обёртка `app: "ZeTer OS"`, `format: "zeter-desktop-backup"`, `version: 1`, время создания и снимок), `README.txt` и файлы `data/<managedPath>` / `data/<assetPath>`, найденные рекурсивно внутри этого снимка. Встроенные Data URL остаются в JSON. Абсолютные цели Windows-ярлыков сохраняются только как ссылки: метод не читает внешние файлы и не обращается в сеть. Отсутствующий или небезопасный payload блокирует создание ZIP. JSON ограничен 200 МБ, число payload-файлов — 100000, общий payload — штатным лимитом managed-файлов; данные файлов обрабатываются потоками по 1 МБ. Место сохранения должно быть вне служебной `data/`.

ZIP создаётся во временном файле рядом с выбранным назначением. Перед атомарной заменой каждый элемент повторно читается из ZIP и сверяется по размеру и SHA-256 с записанными байтами. Отмена не создаёт файл; ошибка до публикации сохраняет прежний ZIP. Ответ содержит `ok`, `cancelled`, `fileName`, при успешной публикации — `bytes`, без Base64. Это архив одного рабочего стола для сохранности данных, не полный бэкап ОС и не автоматическое восстановление всей системы.

Физические JSON-архивы неизменяемы: при повторном сохранении той же записи файл используется повторно, а другой снимок с тем же `archiveId` возвращает ошибку проекции и сохраняет прежний файл. Импорт активного state не перезаписывает такой архив.

После подтверждённой основной записи native сохраняет каждую запись `state.archivedDesktops` отдельным атомарным JSON в `data/Архив рабочих столов/<archiveId>/desktop.json`. ID ограничены безопасными буквами ASCII, цифрами, `_` и `-`, без Windows-зарезервированных имён и дублей. Проекция не удаляет прежние папки; ссылки на payload остаются в canonical primary-state и участвуют в общей защите от GC. Кроме этого, GC читает физические `desktop.json` только из непосредственных безопасных подпапок архивов (не более 10000 элементов и суммарно 200 МБ JSON). Поэтому архив и его payload остаются после замены/import/reset активного состояния даже без `archivedDesktops` в новом state. Повреждённый, недоступный, отсутствующий или небезопасный архив либо превышение лимита блокируют GC целиком. Ошибка проекции не отменяет подтверждённый primary-state: ответ содержит `archiveOk: false`, `archiveError` и `readableOk: false` с пояснением в `readableError`. Успех содержит `archiveDir` и `archiveCount`.

Свои значки папок/ярлыков и фоны папок проходят через `save_item_asset`. Метод принимает только PNG, JPG, WebP, GIF и BMP размером до 12 МБ, сам строит путь по безопасному ID, типу и SHA-256 содержимого и атомарно записывает неизменяемую версию в `data/Оформление объектов/Папки/<ID>/` либо `data/Оформление объектов/Ярлыки/<ID>/`. До подтверждённого `save_state` рядом хранится ограниченный ownership-маркер; поэтому конкурентная очистка не удалит ещё не опубликованную версию, а старый asset точки восстановления не будет перезаписан новой картинкой. В состоянии хранится относительный `assetPath`; Data URL остаётся для отображения и переносимого полного бэкапа. После подтверждённого сохранения неиспользуемые файлы оформления удаляются только из этого служебного каталога и только если на них нет ссылок в текущем state, точках и JSON-backups.

Перетащенные файлы копируются через `begin_file_import` → `append_file_chunk` → `finish_file_import`. JavaScript не передаёт абсолютный путь исходника и не держит большой файл целиком в памяти. Python проверяет порядок смещений, заявленный и фактический размер, свободное место и границы `data/Файлы ZeTer OS/`; до успешной проверки виден только файл `.incoming/*.part`. Экземпляр API удаляет только временные файлы собственных отменённых или истёкших сеансов: общий startup-sweep запрещён, потому что файл может принадлежать другому активному окну или процессу. После атомарной записи `save_state` физическая копия удаляется лишь при отсутствии `managedPath` во всём наборе удержания: текущем state, оставшихся точках восстановления и оставшихся JSON-backups. Поэтому удаление ярлыка, вложения, страницы таблицы или родительского элемента убирает объект из текущего состояния, но файл остаётся доступен для локального отката, пока существует хотя бы один recovery-снимок с этой ссылкой.

`open_external_target` используется только для явно созданных пользователем ярлыков. Метод принимает лишь `http://`/`https://`, абсолютный путь вида `C:\\...` или UNC; относительные пути и другие URL-схемы отклоняются. Командная строка и shell не используются: Windows получает путь через `os.startfile`, а сайт — через системный браузер по умолчанию. В отличие от drag/drop-импорта, абсолютная цель такого ярлыка намеренно хранится в state.

## Изменение bridge

При добавлении или изменении метода:

1. Проверь все вызовы `nativeStorageCall("имя")`.
2. Сохрани формат `{ ok, error }` и обратную совместимость полей ответа.
3. Не передавай абсолютные пользовательские пути из JavaScript, кроме явно сохранённой цели пользовательского ярлыка для `open_external_target`.
4. Для операций записи используй атомарную замену и резервирование исходника.
5. Обнови таблицу методов и проверки в [TESTING.md](TESTING.md).
6. Проверь native-режим и браузерный режим отдельно.

## Системный монитор

`get_system_metrics()` использует только стандартные средства Python и Windows API, поэтому не требует `psutil` и не отправляет телеметрию в сеть. Общая загрузка CPU вычисляется по разнице двух последовательных `GetSystemTimes`; первый или слишком короткий замер может вернуть `cpuPercent: null`. RAM читается через `GlobalMemoryStatusEx`, память процесса — через `GetProcessMemoryInfo`, время работы Windows — через `GetTickCount64`, а свободное место — через `shutil.disk_usage(DATA_DIR)`.

Метод только читает состояние компьютера и не изменяет пользовательские данные. JavaScript опрашивает его раз в три секунды, хранит короткую историю только в памяти открытого окна и очищает её при закрытии Монитора. В копируемый отчёт не входят пути к пользовательским документам, имена файлов и содержимое данных.
