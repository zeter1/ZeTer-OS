# Модель данных и совместимость

Этот документ описывает устойчивый контракт пользовательских данных ZeTer OS. Точные normalizers и миграции в текущих файлах всегда важнее примеров из документации.

## Источники истины

Импортированные DOC/DOCX остаются `managedFile`: рабочая версия — физический файл в `data/Файлы ZeTer OS`, первоначальная копия удерживается через `sourceDocument.managedPath`. Поле `documentDraft` содержит только несохранённые правки и исходные путь/SHA; после подтверждённого сохранения новой DOCX-ссылки оно удаляется. Преобразование и recovery-маркеры описаны в [native-контракте](NATIVE_BRIDGE.md#документы-doc-и-docx).

- Стартовое состояние: `app/js/core/initial-state-utils.js`.
- Миграция загруженного состояния: `app/js/core/state-migration-utils.js`; `app/js/app.js` передаёт runtime-зависимости тонким адаптером `migrate(...)`.
- Нормализация предметных данных: `system-settings-utils.js`, `data-normalizers.js`, `automation-utils.js`, `object-link-utils.js`, `workspace-utils.js`, `trash-utils.js`, `state-maintenance-utils.js`.
- Глубокая проверка импортируемого бэкапа: `state-import-validator.js`.
- Python-сохранение и Windows-читаемая копия: `run_zeter_os.py`.

## Меню Пуск

Параметры Пуска глобальны: `systemSettings.startMenu`, нормализатор — `system-settings-utils.js#normalizeStartMenuPreferences`. `layout`: `balanced`/`compact`, `iconSize`: `normal`/`large`; `showPinned`, `showRecent`, `showDesktops`, `showQuickActions` по умолчанию включены. `quickActions` — уникальные `note`/`task`/`explorer`; `pinOrder` — уникальные ключи `app:<id>`/`item:<id>`, до 1000. `recentItems` — до 20 уникальных `{id, openedAt}` по убыванию времени; UI показывает до четырёх доступных документов. Сами файлы и содержимое в историю не копируются. При `showRecent:false` новые открытия не записываются; очистка списка не меняет файлы. Старые состояния получают значения по умолчанию, schema не меняется. `app.js#updateStartPreferences` использует primary transaction: snapshot → подтверждение записи → публикация только поля `startMenu`; UI немедленно показывает локальный draft и сохраняет его через `start-ui-utils.js#createStartPreferencesWriter`: одна запись выполняется, следующие изменения объединяются по полям в следующую пачку. Формы не блокируются, подтверждение старой пачки не стирает более новый выбор. При отказе draft остаётся явно несохранённым с действиями «Повторить»/«Отменить изменения»; отмена возвращает подтверждённые настройки и недоступна во время записи. Основное состояние приложения обновляется только после подтверждения записи. Очередь сохраняет независимые изменения и смену рабочего стола во время записи.

## Вид папок

Внешний вид значков рабочего стола хранится отдельно в `desktops[].data.settings.desktopAppearance`: `iconSize` (`small`/`medium`/`large`), `density` (`compact`/`comfortable`), `extensions` (boolean), `labelSize` (`small`/`medium`/`large` = 10/12/14 px), `labelLines` (0/1/2/3, где 0 показывает целиком), `openMode` (`double`/`single`). Defaults сохраняют прежний вид: `medium`/`compact`/`true`, подпись 12 px без лимита строк, двойной щелчок. `visual-utils.js#normalizeDesktopAppearance` сохраняет неизвестные поля. `settings.accent` выбирается из `ACCENT_PRESETS` (blue/violet/emerald/rose/amber), default blue; тема остаётся тёмной. Это представление не меняет имена и данные объектов. `desktop-ui-utils.js` устанавливает datasets до измерения DOM и защищает фактические размеры зазором 4/16 px; drag clone наследует datasets. Папки используют собственный `explorerView`.

`first-run-ui-utils.js#applyFirstRunDraft` меняет только staged snapshot выбранного стола: имя/фон/вид, root-ярлыки приложений, закрепления taskbar и системные настройки. Снятие выбора удаляет только соответствующие app-ярлыки корня; файлы, вложенные ярлыки и другие столы сохраняются. Поддерживаемые закрепления вне видимого каталога сохраняются. `app.js#saveFirstRunSetup` публикует изменения и `firstRunCompleted` после `saved:true`. Первый ZIP-бэкап — отдельное необязательное действие после сохранения, через существующий экспорт с проверкой манифеста. Настройка автозапуска Windows не входит в state/ZIP: её явный переключатель вызывает существующий native API сразу, с проверкой результата и блокировкой повторного действия.

`state.fs[folderId].explorerView` хранит предпочтения конкретной папки; `desktops[].data.settings.explorerView` — вид корня соответствующего стола и исходный вид папок без собственных предпочтений. Поля: `mode` (`huge`, `large`, `medium`, `small`, `list`, `table`, `icons` — плитка, `content`), boolean `navigation`, `details`, `preview`, `compact`, `checkboxes`, `extensions`, `freePlacement`. `columnWidths` содержит отдельные ширины `name`, `type`, `size`, `date` в CSS px, с минимальными значениями 120/80/64/92 и общим максимумом 1600; отсутствие ключа возвращает стандартную ширину. Отсутствующие или неверные значения нормализует `explorer-ui-utils.js#normalizeExplorerView`: плитка, панели и расширения включены, компактность/флажки/свободное размещение выключены. Старые координаты и schema не меняются при выборе обычной сетки.

`app.js#renderExplorer` сохраняет только изменённое поле через primary transaction: merge с актуальным владельцем (включая отдельные ключи `columnWidths`) → snapshot → подтверждённая запись → публикация. Desktop ID захватывается до ожидания, чтобы переключение стола не меняло адрес назначения. При отказе прежний вид остаётся действующим. Mounted-окна одной папки синхронизируются событием `explorer-view-change` на своих DOM-корнях. Свободная раскладка использует фактические размеры карточек и зазор 4 px; список/таблица/содержимое, поиск и представление корня остаются упорядоченными.

### Сортировка папок

В том же `explorerView` сохраняются `sortBy` (`name`, `type`, `extension`, `updated`, `created`, `size`), `sortDirection` (`asc`/`desc`), boolean `foldersFirst` и `pinnedFirst`. Defaults: имя по возрастанию, папки и закреплённые сверху; для нового критерия даты/размера UI выбирает убывание. Некорректные значения нормализует `normalizeExplorerView`. Плоский patch проходит прежний подтверждаемый transaction и синхронизацию окон, не заменяя ширины колонок или параметры вида.

Владелец порядка — `explorer-utils.js#sortExplorerItems`. По умолчанию закреплённая группа имеет приоритет над папками; группы не разворачиваются при смене направления. `Intl.Collator("ru", {numeric: true, sensitivity: "base"})` задаёт естественное сравнение имён/типов/расширений; равные ключи разрешаются по имени и ID. Неизвестная дата/размер остаётся в конце обоих направлений. Размер managedFile берётся из `managedFile.size`, для остальных файлов используется прежний `explorerItemSize`; папки не получают фиктивный размер JSON. Вычисления критерия выполняются один раз на элемент. Вызов со старым строковым критерием также поддерживается.

`explorerSortMenuHTML` и кнопки `data-sort-column` используют эти же параметры. Выбор сортировки отключает `freePlacement`, сохраняя x/y, поиск и выделение. Меню сортировки и вида имеют разные DOM-владельцы и независимое позиционирование.

## Настройки и индекс поиска

`state.searchSettings` содержит `filters`, `filtersVersion: 2`, необязательные `scope` (`current`/`all`), `projectId` (составной ключ источника проекта), `dateFrom`/`dateTo` (ISO-даты), `history: [{query,at}]` и `recent: [{key,at}]`. Нормализатор поиска сохраняет совместимые поля и ограничивает историю и недавние материалы 12 записями. Прежний выбор всех семи типов расширяется до новых только один раз при отсутствии marker `filtersVersion`; текущий выбор пользователя сохраняется точно. История содержит только запросы и ссылки на материалы, не их содержимое; очистка списков независима. Запись происходит через обычное основное хранилище, отказ сообщается пользователю. Недавние материалы разрешаются по сохранённым ключам до ограничения выдачи, с соблюдением выбранных фильтров.

`search-utils.js#buildSearchDocuments` собирает только активные столы: fs с проверкой предков/циклов, задачи и проекты обоих task stores, календарь, library, promptLibrary, timeTracking, приложения и команды. Архивные/удалённые источники исключены. Ключ материала включает вид, стол, tasklist и домен проекта; одинаковые ID не смешиваются. Индекс нормализованного текста существует только в памяти; запросы не вызывают внешнюю сеть. `app.js#searchRevision` меняется при сохранении и замене state; все primary transaction adapters используют `persistSearchAwareTransaction`, в том числе rename/customization/recovery. Новый mutation adapter обязан сохранять эту связь либо явно инвалидировать поиск.

Действия поиска повторно разрешают актуальные ID через `app.js#searchTargetRecord`. Отложенное открытие файла, задачи или события после смены стола повторяет эту проверку перед открытием и проверяет текущий стол; смена стола или исчезновение материала отменяют действие без записи успешного открытия в историю. Текст предпросмотра экранируется, адрес открывается штатным shortcut owner. `task-app-ui-utils.js#createTaskCompletionController` использует общий task-store lock, staged snapshot и ACK до публикации статуса; отказ оставляет прежнюю задачу. Команды поиска не удаляют материалы.

Поиск в Пуске с `ignoreFilters` не применяет ограничения типов, проекта и дат отдельного поиска. В обычном поиске недоступный в выбранной области `projectId` очищается в текущем settings-объекте с сообщением и обновлением ревизии поля/подтверждённого значения. Сам запрос не запускает запись; нормализованное значение попадает в следующее обычное сохранение.

В fs прежних версий `deletedAt: 0` означает активный материал и учитывается индексом вместе с предками; это исключение не меняет tombstone-контракт задач и занятий.

`search-ui-utils.js#persistSettings` сериализует историю и controls через одну очередь. Текущий выбор control применяется сразу, queued write не воспроизводит устаревший patch. Ревизии полей защищают более новый выбор; отказ откатывает только принадлежащие записи поля к подтверждённым значениям, без промежуточных pending drafts. `app.js#persistSearchPreferences` проверяет identity state/settings и создаёт snapshot внутри primary transaction после ожидания barrier; возвращаемый `searchSettings` принадлежит фактическому ACK, поэтому откат не зависит от момента начала запроса. Подтверждённые значения существуют только в памяти и принадлежат текущему settings-объекту; замена state не применяет старые отложенные изменения к новому состоянию.

## Запись состояния

В Python-режиме `data/zeter-os-state.json` содержит объект-обёртку:

| Поле | Назначение |
|---|---|
| `id` | Идентификатор основной записи, сейчас `current` |
| `app` | Имя приложения |
| `osVersion` | Номер приложения, записавшего состояние, из `version.js` |
| `versionNumber` | Отдельный номер формата данных, `OS_VERSION_NUMBER` из `config.js` (сейчас `26`) |
| `storageMode` | Режим хранения |
| `updatedAt`, `savedAt` | Время сохранения |
| `stateBytes` | Размер вложенного состояния |
| `state` | Полное пользовательское состояние |

`load_state` также принимает старый «голый» объект состояния и оборачивает его при чтении. Эту обратную совместимость нельзя удалять без отдельной миграции.

`save_state` работает с отдельной JSON-копией входной записи. Python сначала нормализует и очищает только эту копию, атомарно записывает `zeter-os-state.json`, затем повторно читает файл и сравнивает его с подготовленной записью. Только после подтверждения разрешены производная Windows-копия, очистка осиротевших payload и ротация автокопий. Если запись либо повторное чтение не подтверждены, предыдущий основной файл восстанавливается, а производные операции не запускаются.

## Учёт времени рабочего стола

`desktop.data.timeTracking` хранит `entries[]`, `active` (одна незавершённая сессия или null) и `dailyGoalMinutes` (целое 0–1440, 0 отключает цель). Старое состояние получает пустой журнал и цель 0. Сессия содержит `id`, `title`, `taskId`, `projectId`, снимок `projectName`, `createdAt`, упорядоченные непересекающиеся `segments[]` с `start/end` в миллисекундах, `runningSince`, `finishedAt` и `runtimeId`. Необязательные поля: `notes` (до 5000 символов), `manual` (boolean), `deletedAt` (timestamp либо отсутствует/null). Старые записи без этих полей допустимы. `deletedAt=0` тоже означает удаление; активная сессия не может иметь tombstone. Исторические ссылки на удалённые задачи/проекты допустимы; их снимки не удаляются и не заменяются при обычном переименовании.

Мутации проходят primary-save transaction barrier: кандидат находится в отдельном снимке полного state и публикуется после `saved:true`. Отказ сохраняет прежние данные и оставляет UI-черновик. `expected` в редакторе сравнивается с текущей записью внутри той же очереди: устаревший ввод отклоняется до записи. Правка названия, связей и заметки не меняет интервалы и паузы; start/duration передаются только при явном исправлении времени. Если начало и длительность фактически не изменились, интервалы также сохраняются. Ручная запись или исправление времени ограничены 1 мс–366 днями без окончания в будущем; пересечение с фактическими интервалами другой записи/активного таймера требует `allowOverlap=true`. Участок внутри паузы пересечением не считается.

Runtime ID общий для окон текущего запуска. После перезапуска активный отсчёт другого запуска блокирует обычную паузу/продолжение/завершение до подтверждения окончания от runningSince до текущего времени. `recover(end, true)` закрывает старый отрезок в end и начинает новый сейчас, исключая промежуток между ними. Пауза сохраняется и может быть продолжена после перезапуска. Закрытие окна не останавливает отсчёт; сон компьютера входит в календарное время. Повтор создаёт новый ID/пустые интервалы, сохраняя название и заметку; недоступная исходная задача заменяется свободным занятием, существующий проект может сохраниться.

Сводка дня/недели охватывает весь рабочий стол и включает текущие интервалы, кроме неподтверждённого хвоста после перезапуска. Неделя начинается с понедельника; границы дней вычисляются локальным календарём, без фиксированного 24-часового сдвига. Завершённые итоги кешируются при render; секундный tick читает только active, обновляет числа/график без перестроения форм. Adapter берёт уже инициализированный desktop.data напрямую, без повторной полной нормализации на каждом tick. При смене локальной даты сводка обновляется с сохранением ввода.

`selectTimeEntries` — общий владелец выборки журнала, группировки и CSV: период [from,to), поиск title/projectName/notes, проект и режим корзины; длительность обрезается по каждому фактическому интервалу, полная длительность хранится отдельно в row. В карточке явно показаны полная длительность работы и отдельно выбранный период; дата/промежуток относятся ко всему занятию, включая паузы. `timeEntryTiming` вычисляет паузы как finishedAt−createdAt−сумма segments и показывает диапазон дат при переходе через полночь. Произвольные даты включают оба календарных дня. Журнал рисует первые 30 результатов с явной догрузкой; экспорт включает все выбранные завершённые записи, исключая активную сессию и корзину. Столбики недели фильтруют журнал по дню. `timeReportRows` формирует восемь колонок и добавляет защитный апостроф только в экспортируемые текстовые ячейки с опасным префиксом формулы; исходные данные не меняются. Общий `tablePageToCSV` обеспечивает кавычки/разделитель/переносы. `app.js` создаёт UTF-8 Blob с одним BOM и вызывает binary `downloadBlob` в обоих режимах, избегая второго BOM native text-path. Отмена/отказ скачивания не меняет журнал. Совместимость открытия и повторного сохранения в реальном Excel/LibreOffice отдельно не подтверждена; универсальная защита всех табличных программ не заявляется.

UI удаления использует локальный pendingDeletion: карточка сразу показывает ожидание подтверждения, основной state до ACK не меняется. Подтверждение предупреждает об окончательном удалении; отмена не запускает операцию. Очередь controller/primary transaction сохраняет несколько удалений последовательно. При отказе исходная карточка возвращается с ошибкой и возможностью повтора; формы и черновики сохраняются.

Удаление занятия физически убирает только выбранную активную запись из candidate через существующую транзакцию; live-state публикуется только после saved:true. API restoreEntry/purgeEntries и корзины в интерфейсе нет. Прежние записи с deletedAt, включая 0, остаются совместимыми, скрытыми от журнала/поиска/CSV и сохраняются в JSON/ZIP без автоочистки. Импорт проверяет до 10000 записей, до 1000 интервалов на сессию, ID, даты и порядок интервалов, включая архивы. Группа timeTracking управляет удалением данных стола; по умолчанию они остаются в архиве. Владельцы — time-tracking-utils.js, workspace-utils.js, state-import-validator.js; UI — time-tracking-ui-utils.js.

Создание проекта/задачи из «Учёта времени» использует `createTaskCreationController` в `task-app-ui-utils.js`, канонические `makeTaskProject`/`makeTask` и общий lock с доской/редактором задач. В primary transaction сохраняется staged snapshot tasks/taskProjects/activeTaskProjectId выбранного стола, legacy aliases синхронизируются в снимке. Live-поля заменяются после saved:true. Задача создаётся без срока/напоминаний; таймер автоматически не запускается.

Планирование из «Учёта времени» использует существующий `workspace.events[]`, без второго списка планов и без изменения timeTracking/номера формата. `timePlanDraft` переносит title/notes, taskId/projectId/projectName, даты date/endDate и start/end с точностью до минуты; подписи в description остаются снимком, исходная задача доступна по ID. Кнопка «Запланировать занятие» открывает calendaredit с initialEvent/timeTrackingPlan. `createCalendarPlanController` проверяет реальные даты, обязательные времена, непустой title, будущее начало, положительную длительность, привязку к задачам своего стола, лимит и ID; canonical normalizeCalendarEvent → staged full-state primary transaction → saved:true → append только принятого события к текущему events. Прочие изменения календаря во время записи не заменяются кандидатом; их queued save следует за barrier. Legacy aliases синхронизируются в снимке. Отказ сохраняет live-state и ввод формы. План не создаёт entries/active, не увеличивает итоги и не запускает таймер. Переход через полночь сохраняет явную endDate и полное время окончания. UI ручной записи хранит перенесённый черновик в памяти текущего окна до записи или закрытия.

## Подтверждённые изменения календаря

Редактор проверяет исключённые даты до нормализации: неверный формат, несуществующая дата или больше 1000 разных исключений отклоняют запись с сохранением ввода. Для «Только это вхождение» параметры повторения скрыты и не ограничивают перенос отдельного события датой окончания исходной серии. При переносе будущей части её исключения отсчитываются от новой даты начала. Если до выбранного вхождения нет прежних фактических повторов (с учётом дней недели и исключений), изменение/удаление последующих убирает пустую старую запись после ACK; при замене она не занимает дополнительное место в лимите. Существующие записи без отдельного действия не очищаются.

События расширены совместимыми полями `endDate` (по умолчанию `date`), `allDay`, `repeatInterval`, `repeatWeekdays` (0=воскресенье), `repeatUntil` (включительно), `excludedDates`, `taskId`, `projectId`, `projectName`, `attachments`. Для timed конец — исключительная граница, для all-day `endDate` включительно; ICS переводит её в exclusive DTEND. Прежние ID, пустые legacy times и неизвестные поля сохраняются. Новая запись с окончанием раньше начала требует явного следующего дня; скрытый перенос не выполняется.

`calendarOccurrences` вычисляет ограниченные диапазоном фактические вхождения, включая начавшиеся ранее многодневные события; лимит сохраняет ближайшие вхождения по дате/времени/ID независимо от порядка записей. Расширение каждой серии и промежуточное объединение ограничены; после заполнения результата дальнейшие серии проверяются только до последней сохранённой даты. Поиск/категория/проект повестки применяются до расширения и ограничения выдачи. `occursOn` проверяет только дату начала вхождения для напоминаний/автоматизаций. `occurrenceDate` и `occurrenceKey` принадлежат исходному повторению, `id/eventId` — сохранённой серии. Изменение одного вхождения исключает исходную дату и создаёт отдельную запись; изменение последующих ограничивает старую серию и создаёт новую с введёнными исключёнными датами будущего диапазона. Исключения прежней части серии сохраняются. Все изменённые записи публикуются вместе после ACK. Занятость объединяется без двойного счёта; фильтры не освобождают скрытое время.

При выборе `repeat:none` редактор перед валидацией и записью сбрасывает скрытые `repeatInterval/repeatWeekdays/repeatUntil/excludedDates`: неверный прежний интервал не блокирует обычное событие, граница серии не запрещает перенос, исключения не скрывают его дату. До ACK исходная серия и черновик сохраняются; активные повторения продолжают проверять введённые границы и исключения. Автоматизация `event_relative` ищет начало вхождения в интервале `[now − offset − 24h, now − offset]`, переводя границы в местные даты до перебора: знак смещения и DST не сужают предусмотренное окно обработки.

`workspace.calendarState` хранит вид, рабочие часы и показ сроков задач; выбор и фильтры окна остаются runtime. `workspace.calendarCategories` хранит до 100 собственных категорий `{id,name,color,description?,icon?}`: необязательное описание до 1000 символов, значок из `CALENDAR_CATEGORY_ICONS`; ID `calcat_…`, имя до 80 символов, HEX-цвет. Стандартные категории остаются доступны; отсутствующее определение не заменяет category ID события. Категории и настройки записываются привязанным к исходному workspace adapter через primary transaction, с проверкой ACK и старого снимка категории. Редактирование использует `createPreferencesWriter`: debounce текста 450 ms, serial ACK, сохранность более новой ревизии формы и явный retry/discard после отказа. До записи/отмены черновика выбор категории и удаление блокируются; обновление другого окна вызывает `refreshCalendar`, сохраняя DOM и черновик. Создание категории остаётся отдельным действием. Удаление собственной категории требует подтверждения и явной категории назначения, если она используется: удаление определения и переназначение всех связанных событий публикуются одним ACK. События, описания, повторы, ссылки вложений, файлы и соседние категории сохраняются. Стандартные категории не удаляются; неизвестная/удалённая категория назначения, старый снимок и отказ записи оставляют прежнее состояние.

`event.attachments` использует существующий формат `{kind:"fs",id}`, до 200 ссылок без байтов файлов. До первого сохранения ссылки принадлежат черновику. Отсутствующая ссылка сохраняется для показа недоступного материала. Открепление/удаление события не удаляет файл. Native upload использует штатное chunked managed storage: самостоятельная fs запись публикуется после ACK, затем может быть прикреплена к событию. При отказе её записи завершённая копия остаётся в managed storage, а повтор из той же формы переиспользует её; отмена события оставляет материал. В browser общая binary upload не подменяется текстовой заглушкой. Полный backup переносит fs и managed payloads, JSON календаря — ссылки.

Привязка блока к задаче относится только к `workspace.tasks/taskProjects`; новая/изменённая привязка проверяется у исходного владельца. Сохраняемая историческая ссылка после удаления задачи не запускает таймер другой задачи. Восстановление проекта включает связанные блоки, определения категорий и вложения с переназначением ID; отсутствующие historical refs не привязываются к одноимённому объекту назначения.

Обычное создание/редактирование/удаление событий использует `calendar-utils.js#createCalendarEventController`: привязанный workspace → общая mutation queue → primary transaction → staged events → `saved:true` → публикация только затронутого события. При отказе live-events и черновик не меняются. Существующая запись сравнивается со снимком на момент открытия редактора внутри transaction; удалённое или изменённое событие отклоняет старый ввод. Сравнение исключает только служебные `updatedAt` и `reminderNotifiedOccurrence`: доставка напоминания не конфликтует с формой, остальные данные и metadata сравниваются. Сохраняются ID, исходный createdAt и дополнительные metadata; новые события ограничены лимитом календаря, проверяются существующая ISO-дата и время. Ограничение прошедшей даты относится только к созданию.

`app.js#calendarPersistenceOptions` сохраняет событие и очередь автоматизации `event_created` одним полным снимком с legacy aliases. Автоматизация и календарное планирование используют ту же mutation queue. При переключении стола ACK относится к исходному workspace; текущая навигация другого стола не меняется. Независимые события и marker напоминания, изменённые во время записи, сохраняются при публикации и последующем обычном save за transaction barrier. Редактор сообщает успех/закрывается после ACK, блокирует повторное сохранение на время записи; ошибка обновления UI после ACK не разрешает повторно создать уже принятое событие.

## Подсчёты рабочего стола

`desktop.data.calculations` содержит `currency` (BYN/RUB/USD/EUR), уникальный упорядоченный `selected[]` с ID выбранных калькуляторов и `inputs` со строковыми полями всех 10 типов. Необязательный `sizes` хранит размеры по ID: целочисленные `width` (280–2400), `height` (240–2000) и `span` (1 или 2 колонки). Старый объект без `sizes` остаётся допустимым и получает пустой словарь; импорт отклоняет неверные размеры. Скрытие сохраняет размер; сброс удаляет только выбранную настройку. CSS ограничивает ширину доступным местом, а содержимое низкой карточки прокручивается. Pointer-preview размера публикуется в state только после saved:true; на отказе ввода/размера DOM возвращается к принятой настройке, dirty-ввод остаётся в окне. Владельцы — `business-calculations-utils.js` и `business-calculations-ui-utils.js`. Старое состояние получает четыре примерные карточки; пустой `selected` остаётся пустым при нормализации. Скрытие карточки сохраняет её ввод. Валюта меняет подпись, без конвертации. Строки сохраняют незавершённый и неверный ввод (до 48 символов), вычислитель отмечает его ошибкой. Полный JSON/ZIP, ZIP рабочего стола и архив сохраняют порядок, валюту и все поля; импорт проверяет новый объект до нормализации, включая архивы. При удалении стола отдельная группа «Подсчёты» управляет удалением этих данных.

Мутации используют существующий `primaryStateSaveQueue.transaction`: кандидат сохраняется в копии полного состояния и публикуется в текущем workspace только после `saved:true`. Отказ записи оставляет принятое состояние прежним; несохранённый ввод остаётся в окне для повторного сохранения. Перетаскивание реализовано pointer-событиями с захватом на ручке и работает только для карточек внутри данного окна. `moveTo` занимает индекс целевой карточки до удаления источника; вся площадь цели имеет одно значение. Кнопки порядка используют отдельный `reorder` с явным before/after. Ввод и размеры принадлежат ID и не меняются при переносе.

## Основные поля state

`desktop.data.contacts` — справочник одного рабочего стола: `projects[]` (`id`, `name`), `categories[]` (`id`, `projectId`, `name`) и `entries[]`. Контакт содержит имя, компанию, должность, город, теги, описание, избранное, даты и `projectId`/`categoryId`. Повторяемые пользовательские `fields[]` содержат уникальный `id`, тип `phone`/`email`/`social`/`url`/`text`/`multiline`, подпись `label` и текст `value`. Старые фиксированные способы связи сохраняются для совместимости. Пустой `projectId` означает «Без проекта» и требует пустого `categoryId`; любая другая категория принадлежит тому же проекту. Категории показываются только внутри выбранного проекта. Названия проектов уникальны, названия категорий уникальны внутри проекта. Пустые старые состояния получают пустой справочник без образцов; схема данных не меняется.

Владельцы — `contacts-utils.js`, `contacts-ui-utils.js`; интеграция хранения — `app.js#renderContactsApp` и `workspace-utils.js`. Категории выбираются выпадающим списком; создание — справа в заголовке проекта рядом с меню проекта. Мутации сохраняют отдельный кандидат через primary transaction и публикуют его только после `saved:true`. Отказ не меняет принятые данные, редактор удерживает ввод для повтора. Редактор передаёт исходную карточку третьим аргументом `saveEntry`; после входа в transaction контроллер сверяет её с актуальной карточкой. При расхождении сохранение отклоняется без записи: введённый текст остаётся в форме, актуальную карточку нужно открыть заново. Удаление категории снимает только categoryId; удаление проекта сохраняет его контакты с пустыми projectId/categoryId. Полный JSON/ZIP, ZIP рабочего стола и восстановление целого стола сохраняют все поля. Импорт проверяет иерархию и типы до нормализации, включая архивы. Группа `contacts` при удалении рабочего стола по умолчанию удерживается в архиве; явный выбор удаляет только эту группу. Поиск внутри приложения не отправляет контакты в сеть.

Новый стол получает стандартные ярлыки из `config.js#DEFAULT_DESKTOP_APP_IDS`; первичный стол формируется в `initial-state-utils.js`, дополнительные — в `workspace-utils.js#createVirtualDesktopController`. Новые данные не содержат образцов «Проекты»/Welcome.txt, событий календаря и уведомлений об обновлении. Миграция сохраняет уже существующие документы, события и уведомления. Каталог скрывает приложение-коллекцию `notes`, отдельные объекты `type: note` продолжают открываться в редакторе. Координаты значков могут корректироваться по фактическим размерам DOM для устранения наложений; ID, имена и содержимое при этом сохраняются.

`desktop.data.promptLibrary` содержит `projects[]` (`id`, `name`), `categories[]` (`id`, `projectId`, `name`) и `entries[]` (`id`, `projectId`, `categoryId`, `name`, `text`, `favorite`, `createdAt`, `updatedAt`). Библиотека принадлежит одному рабочему столу и не имеет корневого legacy alias. Старое состояние получает пустую библиотеку. Категория ссылается на существующий проект; запись имеет существующий projectId либо пустую строку для общего раздела без проекта. У записи без проекта categoryId строго пустой; категория проектной записи принадлежит тому же проекту. Названия проектов уникальны, названия категорий уникальны внутри проекта без учёта регистра. Текст промпта сохраняется без trim и выполняется только как обычный текст. Импорт проверяет иерархию до миграции, включая архивные столы. Полный JSON/ZIP и ZIP рабочего стола сохраняют библиотеку целиком. При удалении категории запись переходит в «Без категории» своего проекта. Удаление проекта с режимом transfer сохраняет все его записи с исходными ID, текстом, датами и избранным, меняя projectId/categoryId на пустые строки; delete удаляет только записи этого проекта. В обоих случаях удаляются проект и его категории. Все мутации библиотеки в production проходят существующий primary-save transaction barrier. Кандидат хранится только в отдельном снимке и становится текущей библиотекой после saved:true; при отказе текущие данные не меняются. Параллельные primary-save снимают snapshot после завершения транзакции, а ранее запланированный внешний backup видит только принятое состояние. Группа `prompts` при удалении рабочего стола участвует в сохранении архива и выборочном удалении. Владельцы — `prompt-library-utils.js`, `workspace-utils.js`, `state-import-validator.js`.

### Обзор проекта и прикреплённые объекты

Store задач в `task-ui-utils.js#taskStoreFromParams` удерживает исходный объект workspace либо tasklist. Снимок, общий save-lock и откат в `task-app-ui-utils.js` используют этот объект даже после смены активного стола: поздний отказ записи не переносит задачи и проекты в новый стол. Это runtime-ссылка, она не входит в сохранённые данные. Действие «Поставить срок» проверяет реальность календарной даты через общий `project-overview-utils.js#validProjectDue` до изменения задачи.

Параметры каждого проекта (`workspace.taskProjects[]` и `state.fs[tasklistId].taskProjects[]`) включают `description` (до 2000 символов), `color` (прежние `default/blue/green/orange/pink/purple` либо `#rrggbb`), `defaultView` (`overview/board/list`), `sortBy` (`created/due/priority/title`), `hideCompleted` (boolean) и `defaultPriority` (`low/medium/high`). Дополнительно доступны необязательные `goal` (до 1000 символов), `status` (`planned/active/paused/completed`), `startDate` и `deadline` (пустая строка или существующая ISO-дата; срок не раньше начала). Статус и даты справочные, не изменяют задачи/события/таймер. Старые проекты не получают новые ключи до редактирования. `normalizeTaskProjectSettings` задаёт совместимые defaults; фабрика `makeTaskProject` создаёт сразу нормализованные поля. Старые проекты не требуют изменения schema; импорт проверяет длины, enum и тип boolean. Поля проходят обычный JSON export/backup вместе с проектами. `showTaskProjectSettingsDialog` в режиме `{autoSave:true}` (из календаря) использует существующий serial writer: более новый ввод сохраняется после предыдущего ACK, ошибки удерживают черновик, закрытие дожидается записи. Обычная форма из «Задач» сохраняет прежние кнопки сохранения и отмены.

`normalizeTaskProjectColor` сохраняет прежние имена и нормализует шестизначный HEX в нижний регистр; произвольный CSS не принимается. `taskProjectColorCSS` возвращает проверенный CSS-цвет для шапки, списка проектов и предпросмотра. Палитра содержит 22 готовых варианта; radio, нативный input color и HEX синхронизируются в локальном draft и записываются только при сохранении.

`task-app-ui-utils.js#createTaskProjectSettingsController` сохраняет candidate массива проектов внутри primary transaction с общим task-store lock и проверкой исходного владельца. Live-массив заменяется после `saved:true`; задачи, категории, связи и неизвестные поля сохраняются. Открытый диалог держит снимок редактируемых полей: изменение этих полей в другом окне отклоняет устаревшее сохранение; изменения связей/категорий не теряются. При отказе draft остаётся в диалоге. Начальный вид применяется при выборе проекта; сохранённый вид восстановленного окна остаётся в `params.projectView`. Сортировка действует внутри статусов доски/списка, закрепления остаются первыми. Скрытие выполненных не меняет сводку обзора; переход к задаче из поиска/уведомлений временно показывает её. Приоритет используется только при создании: в редакторе при выборе проекта и в общем creation-controller «Учёта времени».

Каждый проект в workspace или файловом tasklist хранит `categories: [{id, name}]` (до 200, имя до 160 символов), а задача — `categoryId` либо пустую строку. `normalizeTaskStore` оставляет задачу только в категории её проекта; старые задачи и недоступные ссылки становятся «Без категории». Категории сохраняются внутри существующего массива проектов и проходят обычный backup/import; schema не меняется. `createTaskCreationController.createCategory` проверяет проект, лимит и совпадение имён без учёта регистра внутри общей task-store транзакции, публикуя candidate только после `saved:true`. Фильтр категории принадлежит окну и сбрасывается при смене проекта; он отбирает задачи во всех трёх представлениях, не ограничивая общие материалы и время проекта.

Существующие проекты в `workspace.taskProjects[]` и `state.fs[tasklistId].taskProjects[]` могут содержать optional `attachments: [{kind: "fs" | "event", id}]`, до 200 ссылок. Это ссылки на исходные объекты текущего рабочего стола, без копирования содержимого. `project-overview-utils.js#normalizeProjectAttachments` ограничивает список, проверяет ID и удаляет дубли; `data-normalizers.js#normalizeTaskProject` сохраняет поле при нормализации обоих видов store. `state-import-validator.js#validateImportedTaskStore` проверяет поле до импорта, включая tasklist, legacy-root и desktop. Формат данных и старые проекты без поля совместимы.

`task-app-ui-utils.js#createTaskProjectAttachmentController` использует общий task-store lock. Внутри primary transaction повторно проверяются адресат, проект и доступность добавляемого объекта; candidate проектов попадает в полный snapshot, legacy aliases синхронизируются, live `taskProjects` публикуется только после `saved:true`. Отказ оставляет исходные данные. Связь с удалённым/перемещённым объектом остаётся видимой как недоступная и может быть откреплена; удаление связи или проекта не удаляет материалы и события.

`project-overview-utils.js#buildProjectOverview` считает задачи выбранного проекта и категории: прогресс, открытые/просроченные/сегодня/без срока/ближайшие 7 дней, ближайший срок и этапы. `validProjectDue` — общий валидатор существования календарной даты для модели и `task-ui-utils.js#taskMatchesBoardFilter`: некорректная дата считается отсутствующей, исходные данные не меняются. Быстрые карточки передают `deadline` в `showBoard`, сохраняют категорию и сбрасывают поиск/приоритет/тег. «На 7 дней» включает местное сегодня + шесть календарных дней; все фильтры сроков отбирают только открытые задачи. Следующие дела упорядочены по сроку, затем закреплению и приоритету.

Итоги времени и семь дневных buckets текущей недели используют один набор project entries + active и `timeInRange`; удалённые записи исключены, неделя начинается в местный понедельник. Границы дней строятся календарными операциями, без предположения о 24 часах; каждый интервал обрезается своим днём и `now`. До recovery не прибавляется незавершённый отрезок старого запуска. Категория влияет только на задачи. График и итоги обновляются без пересоздания формы поиска материалов. Время и запуск таймера доступны только для workspace-проектов: модель таймера не связывает занятия с отдельным файловым tasklist.

Представление `overview/board/list` хранится в параметре окна `projectView`. `refreshTaskBoard` обновляет данные без пересоздания окна и сохраняет вкладку, положение доски и фокус проекта/checklist/status/действия карточки. `task-ui-utils.js#taskBoardGroups` формирует группы по общему фильтру: список исключает пустые статусы, доска сохраняет их как drop targets. Перед группировкой недоступный в текущем проекте `ui.taskFilter.tag` сбрасывается в `all`; select и выборка читают одно значение. `refreshProjectOverviews` синхронизирует подписи и доступность материалов, события и изменения времени между окнами текущего стола. Экспорт задач и общий state/desktop backup сохраняют поле attachments вместе с проектами.

Навигация проектов принадлежит `task-app-ui-utils.js#createTaskProjectNavigationController`: общая `WeakMap` хранит только runtime-ревизию/ожидающий выбор для конкретного workspace или tasklist. Выбор отображается синхронно; одна запись в работе и один последний ожидающий ID, без нормализации всех задач, запуска task automation и `renderAllFileSurfaces`. Перед транзакцией навигация ждёт task-save lock через Promise; внутри барьера повторно проверяет lock и владельца, но не ждёт task-save (иначе deadlock). Свежий снимок `createTaskProjectPersistence` меняет только `activeTaskProjectId`, проверяет исходный desktop/item identity и синхронизирует legacy aliases. Отказ записи оставляет видимый выбор, сообщает об ошибке; повторное нажатие явно повторяет запись. Runtime-ревизия в task rollback snapshot не позволяет старому откату отменить новый выбор. Она не сохраняется в JSON и не меняет schema.

Создание проекта из модального окна использует существующий staged `createTaskCreationController` и тот же lock; новый проект публикуется в live store только после `saved: true`. Название остаётся в открытом диалоге при отказе. После commit adapter синхронизирует aliases, small settings, backup/protection hooks и открытый «Учёт времени». Смена владельца отклоняет запись; форма не запускает native/browser `prompt`.

### Автоматизации и связи объектов

Окно `automationedit` отделено от списка `automations`: обновление списка после автоматического запуска не пересоздаёт редактор. Создание/шаблон передают начальный черновик в параметры окна, редактирование — `automationId`; несохранённый ввод не является правилом и не имеет гарантии восстановления после перезапуска. Сохранение одного черновика под общим mutation-lock объединяется с актуальным списком, сохраняет runtime-поля правила, отклоняет удалённое правило/категорию и смену рабочего стола. Только после подтверждения записи редактор закрывается, а список открывается/фокусируется в категории сохранённого правила; отказ записи оставляет форму открытой.

«Файл для проверки» — временный выбор в окне автоматизаций, не поле сохраняемого правила. Список ограничен текущим рабочим пространством и папкой-источником; перед ручным запуском ID заново разрешается в актуальном state внутри mutation-lock. Удалённый или перемещённый из выбранной папки объект не заменяется первым доступным файлом. Предпросмотр не меняет данные, отсутствие примера само по себе не означает повреждение правила.

Явные кнопки проверки файлового примера потребляют временный выбор после вычисления результата. Результат сохраняет имя проверенного объекта, но не даёт ручной запуск со сброшенным выбором. Повторная проверка требует нового выбора. Автоматический preview при смене файла не потребляет выбор, чтобы пользователь мог нажать явную проверку или намеренный ручной запуск.

`workspace.automationCategories[]` хранит до 200 пользовательских категорий `{id, name}` (название до 160 символов); `automations[].categoryId` — одна категория либо пустая строка. Старые правила остаются без категории. Поле проходит defaults, legacy aliases, нормализацию, импорт и перенос данных при удалении рабочего стола. Категории других рабочих пространств не подмешиваются. Создание/переименование не допускает пустых и совпадающих без учёта регистра имён. Категории, правила и их удаление сохраняются через общий automation mutation-lock с откатом при ошибке хранилища.

История содержит `categoryId` на момент запуска. Фильтр категории для существующих правил использует их текущую принадлежность (включая старую историю без этого поля), для удалённых — сохранённую принадлежность; отсутствующая категория отображается как «Без категории». Удаление только категории снимает назначение у правил. Удаление с правилами также убирает их ожидающую очередь и связанные checkpoints, не затрагивая другие правила, произведённые объекты и прошлую историю. Очистка истории внутри категории не очищает другие категории. Сводка считает только ограниченную сохранённую историю, не пожизненные итоги.

Конкретный источник (включая корень рабочего стола) выбирает только непосредственных детей; пустой `folderId` — файлы всего текущего пространства. Заметки входят в файловый список, папки и значки приложений — нет. UI различает рабочий стол и папку в подписях, открытие выбранного объекта и открытие его родителя. Перед обоими переходами выбранный ID повторно проверяется в текущем пространстве и источнике; недоступный объект не заменяется переходом на рабочий стол. Подсказки переменных показывают контекст триггера, а не тип выбранного файлового примера: заметка при `file_added` использует `{file.name}`, не `{note.name}`.

`workspace.automations[]` хранит правила текущего рабочего стола. Legacy-поля `condition: "always"`, одиночный `action`, исходный `id` и `lastRunKey` сохраняются; нормализованная запись дополнительно содержит `conditionMode` (`all`/`any`), ограниченные массивы `conditions[]` и `actions[]`, политику ошибки каждого действия и диагностические `pausedReason`/`lastError`. Поддерживаются расписания `weekly`/`daily`/`monthly`, триггеры относительно события, добавление файла в ZeTer OS, состояния задач, создание/изменение заметки, создание события и запуск ZeTer OS. Действия: уведомление, заметка, перенос файла и связь объектов. Текстовые поля допускают только подстановку разрешённых переменных; произвольный код не выполняется. Для переноса хранится политика совпадения имени `skip`, `rename` или `replace`; импортированная замена без `replaceAcknowledged: true` остаётся заблокированной до явного подтверждения.

`workspace.automationRuntime` хранит сохраняемое состояние выполнения: общую паузу, baseline известных файлов, ограниченные `queue[]`, `history[]`, `checkpoints[]` и журнал частоты запусков. Baseline при первом запуске не превращает существующие объекты в новые события. Запись очереди идентифицируется парой automation/run key; checkpoint фиксирует уже успешные действия, поэтому повтор после ошибки не дублирует их. История хранит итоговый статус и результаты каждого действия. Завершение/просрочка задачи, создание/изменение заметки, создание события и запуск ZeTer OS передаются в эту же очередь до подтверждённого сохранения; task-list задачи разрешаются по вложенному store. Очередь, история и checkpoints ограничиваются normalizer’ом и отдельно проверяются при импорте; origin/chain и rate guards прерывают цикл или слишком частые запуски и оставляют видимую диагностическую запись. Автоматический или ручной запуск, пауза и изменения правил используют один mutation-lock; при отказе хранилища действие откатывается и успех не показывается.

`workspace.objectLinks[]` хранит двусторонние связи без копирования самих объектов. Запись содержит `id`, стороны `a`/`b` вида `{ kind, id }`, необязательные `label` и `createdAt`. `kind` принимает `fs` для заметок, документов, таблиц и файлов либо `event` для событий календаря. Пара сторон канонизируется, обратные дубли отбрасываются, а связь с удалённой стороной очищается при нормализации рабочего пространства. Удаление связи никогда не удаляет связанные объекты.

Уведомление автоматизации использует `source: "automation:ID"`. Для перехода к результату оно может хранить `linkedObjectKind`, `linkedObjectId` и `linkedEventDate`; эти поля дополняют существующие task/calendar-поля и проходят проверку импорта вместе с записью уведомления.

### Глобальные системные настройки

`state.systemSettings` не относится к отдельному рабочему столу и действует во всей ZeTer OS:

| Путь | Назначение |
|---|---|
| `startup.restoreWindows` | Восстанавливать ли сохранённые окна после запуска |
| `startup.desktop` | `last` либо ID рабочего стола, который нужно выбрать при запуске |
| `startup.windowMode` | `maximized` для развёрнутого pywebview-окна либо `windowed` для обычного окна 1320 × 840 |
| `windows.openingSize` | Размер новых внутренних окон: `full` (100% рабочей области), `large` (85%), `medium` (70%), `compact` (55%). Старые/некорректные значения → `full`; минимум окна 330 × 240 |
| `windows.placement`, `windows.lastPositions` | Новые окна: center/cascade/last, default center. Last хранит ограниченную геометрию по app ID; размер берётся из openingSize, session rect имеет приоритет. Закрытие maximized сохраняет нормальный lastRect |
| `clock.format`, `showSeconds`, `showDate` | 24h/12h, секунды и дата нижней панели. Defaults: 24h/false/true; часы паузы используют тот же формат без секунд |
| `calendar.weekStart` | monday/sunday, default monday. Меняет сетку и заголовок календаря, не ISO-даты событий и не статистическую неделю Учёта времени |
| `notifications.enabled` | Главный выключатель создания новых уведомлений |
| `notifications.tasks`, `calendar`, `system` | Разрешения по категориям |
| `notifications.quietHoursEnabled`, `quietFrom`, `quietTo` | Период без всплывающих сообщений; записи в центре уведомлений сохраняются |
| `notifications.popupDuration` | Длительность новых popup: 3500/5000/8000/12000 ms, default 3500. Категории и тихие часы не меняются |
| `accessibility.textScale` | Допустимый размер текста: 90–150 процентов с шагом 10 |
| `accessibility.largeControls`, `highContrast`, `reducedMotion` | Крупные элементы, повышенный контраст и уменьшение анимации |
| `hotkeys.*` | Канонические сочетания для поиска, Пуска, Настроек, Календаря, уведомлений и переключения рабочих столов; пустая строка отключает действие |

Источник defaults и совместимой нормализации — `system-settings-utils.js`. Неизвестные поля сохраняются для прямой совместимости будущих версий. Системные настройки входят в полное состояние, ZIP/JSON-бэкапы и маленький диагностический снимок `localStorage`.

Сессия Настроек хранится в `ui.settingsSessions` по desktop ID и переживает перерисовку/смену стола. Общий `preferences-writer-utils.js` удерживает revision-aware draft, объединяет быстрые изменения, сериализует batches и останавливается на отказе до явного retry/нового выбора. `renderSettingsApp` строит актуальный snapshot внутри primary transaction, накладывает только allowlisted patch и после `saved:true` повторно накладывает его на актуальный live state, сохраняя чужие поля. Статус различает primary/fallback ACK; `lastError` не заменяет результат записи. Подписки writer и asset lifecycle снимаются `disposeSettingsView` при close/refresh/clearRuntimeWindows; сам writer завершает pending запись. Async uploads адресуются захваченному desktop ID; file-generation защищает замену/удаление/отмену. Отдельная `wallpaperSelectionRevision` не позволяет поздней подготовке изменить более свежий фон или сброс: готовое изображение сохраняется без автоматического переключения. `pendingAssets` содержит только актуальный token каждого вида изображения, а `assetListeners` оповещает все действующие view о начале/завершении/ошибке, включая повторно открытое окно.

Сброс раздела — явный preference patch, а не замена settings/desktop. Он сохраняет профиль, customWallpaper, файлы, unknown fields, историю и кеш геометрии. Автозапуск Windows не входит в общий сброс. Предпросмотр остаётся локальным до ACK; глобальное оформление/размер окна/порядок календаря применяются после подтверждения.

Превью иконки профиля в Настройках строится каноническим `desktopAvatarHTML` из модели с draft-патчем; адаптер принимает текущую запись рабочего стола третьим аргументом. Загрузка, удаление и discard обновляют превью без переоткрытия, отказ записи сохраняет draft для повтора. Захват hotkey принадлежит только сфокусированной кнопке: Esc/Tab/Shift+Tab, потеря фокуса, отключение и сброс завершают его; переход в другое поле не переназначает сочетание.

Размер внутренних окон рассчитывает `window-metrics-utils.js`; применение и восстановление выполняет `window-ui-utils.js`. Выбор в Настройках сохраняется через primary transaction до изменения live-state и геометрии окна Настроек; отказ возвращает прежнее значение select и сообщает ошибку. Остальные открытые окна не меняются. Новые окна получают выбранный размер, восстановленные — сохранённую геометрию, ограниченную текущей рабочей областью; небольшие окна больше не увеличиваются до стандартных. На узком экране существующий responsive CSS растягивает окно по ширине с боковыми отступами 6 px; выбранный размер определяет высоту. Внешнее Windows-окно управляется отдельно через `startup.windowMode`.

Галочка «Запускать ZeTer OS вместе с Windows» намеренно не входит в `state.systemSettings`: это внешняя настройка текущего пользователя Windows. Её источником истины служит запись `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, которую desktop-версия читает и изменяет через native bridge. Поэтому галочка одинакова во всех рабочих столах, не переносится через ZIP/JSON-бэкап и недоступна в browser/PWA-режиме.

У календарного события поле `reminderNotifiedOccurrence` хранит ключ уже обработанного повторения (`дата|время|минуты`). Оно предотвращает повторное уведомление об одном и том же событии, но позволяет напомнить о следующем повторении. Уведомление календаря хранит `calendarEventId` и `calendarDate`, чтобы открыть нужный рабочий стол и день.

### Уведомления об обновлениях

Системное предложение обновления содержит `action: "open-update"` и `source: "update:MAJOR.MINOR.PATCH"`. `data-normalizers.js` при нормализации уведомлений удаляет предложения версий не выше текущей `OS_VERSION`, сравнивая три числовые части. Это действует при загрузке, импорте и обработке каждого рабочего стола без обращения к сети; результат попадает в обычное последующее сохранение. Более новые предложения, другие уведомления и записи с неизвестным форматом остаются. Номер формата данных не меняется.

## Файловая модель

`state.fs` — объект вида `id → item`. Общие поля элемента: `id`, `type`, `name`, `parent`, `x`, `y`, `createdAt`, `updatedAt`. Дополнительные поля зависят от типа: `content`, `extension`, `appId`, `color`, данные таблицы, tasklist или изображения. Ярлык на полностью скопированный Windows-файл имеет `type: "managedFile"` и объект `managedFile` с `id`, `name`, относительным `managedPath`, `size`, `mime`, `extension`, `importedAt`.

Созданный пользователем ярлык имеет `type: "shortcut"`, объект `shortcut: { target, kind, itemId? }` и совместимую запись `managedFile` с `kind: "shortcut"`, `shortcutTarget` и `shortcutKind`. `kind` принимает только `windows`, `url` или `zeter`. Внутренняя цель хранится как `zeter://item/ID`; сайт — только как нормализованный `http://`/`https://`; Windows-цель — как явно введённый абсолютный путь диска или UNC. Такой ярлык не копирует внешнюю цель в `data` и при удалении не удаляет внешний файл/папку. Абсолютный Windows-путь сохраняется внутри полного state и его бэкапов, поэтому пользователь должен учитывать, что он может содержать имя профиля или сетевого ресурса.

Папки и пользовательские ярлыки могут иметь объект `appearance`. У папки он содержит нормализованный `color`, необязательные `icon` и `background`; у ярлыка — только `icon`. Каждое изображение хранит безопасный Data URL для отображения/полного бэкапа и, в Python-режиме, переносимый относительный `assetPath` внутри `data/Оформление объектов/`. Цвет папки используется только при отсутствии своего значка. Фон применяется к рабочей области открытой папки. Импорт проверяет MIME, объём Data URL и границы `assetPath`; миграция сохраняет неизвестные поля, но нормализует поддерживаемые настройки.

Окно настройки хранит выбранные изображения в отдельном черновике. Последний выбор или удаление отменяет публикацию предыдущей незавершённой обработки. Пока текущая картинка готовится, сохранение недоступно. Adapter `renderItemSettingsApp` записывает кандидат через `primaryStateSaveQueue.transaction` в снимок полного state и меняет текущий объект только после `saved:true`; отказ сохраняет прежнее оформление и черновик окна. Публикация сверяет поля с их значениями перед записью: параллельное переименование/изменение из другого окна сохраняется и попадает в отложенную обычную запись после transaction barrier. Во время записи элементы формы заблокированы, завершение всех native asset-запросов ожидается даже при отказе одного из них.

Заметки и текстовые документы могут содержать массив `managedFiles[]`. Положение файла внутри rich-text сохраняется безопасным пустым маркером `<span data-managed-file-inline="ID" data-managed-file-inline-x="X"></span>` в `richContent`; `data-managed-file-inline-x` задаёт проверенное горизонтальное смещение, а имя, иконка и кнопки при отображении восстанавливаются из `managedFiles[]`. Если файл опущен ниже последней строки, редактор создаёт сохраняемые пустые абзацы до точки drop, поэтому ярлык остаётся в выбранной нижней области и после повторного открытия. Старые вложения без маркера автоматически добавляются в конец текста и не теряются. Стикер использует `richContent` и `managedFiles` той же заметки, отдельной копии вложений в данных стикера нет.

В Windows-читаемой копии и читаемом ZIP-экспорте заметки каждого рабочего стола сохраняются плоско, прямо в его каталоге `Заметки`, без повторения родительских папок ZeTer OS. Если после выравнивания структуры встречаются одинаковые имена, экспорт добавляет безопасные суффиксы ` (2)`, ` (3)` и не перезаписывает документы. Полный путь и исходная иерархия заметки остаются в `zeter-os-state.json`.

Страница таблицы хранит свой массив `managedFiles[]`; у записи дополнительно есть ячейка `row`/`col`, координаты `offsetX`/`offsetY` внутри неё и необязательная сохранённая ширина `displayWidth`. Drag/drop меняет координаты ярлыка, поэтому его можно разместить в любой части ячейки. Размер ячейки не переписывает `displayWidth` и координаты: выступающая часть только скрывается границами ячейки, а при обратном увеличении снова раскрывается. Внутренний drag/drop переносит существующую ссылку с тем же ID и удаляет исходное размещение; `Ctrl+C`/`Ctrl+V` создаёт новый ID ссылки с той же целью (`managedPath` или `shortcutTarget`). Физическая managed-копия остаётся общей до удаления последней ссылки. Поле `managedPath` всегда относительно `data/`, начинается с `Файлы ZeTer OS/` и никогда не содержит абсолютный путь исходника Windows.

Связи через `parent`, открытые окна, вкладки, закрепления и стикеры должны очищаться вместе с удаляемыми ID. Логику descendants, перемещения и очистки ссылок нельзя менять независимо друг от друга.

## Хранилища

- Python/pywebview: полное состояние в `data/zeter-os-state.json`.
- `data/updates/<уникальная-транзакция>/`: служебные staging, verified backup, journal и receipts установщика. Это не пользовательское state и не входит в замену program files; recovery сохраняется без автоматического удаления. Контракт — [UPDATES.md](UPDATES.md).
- Браузер: основная запись в IndexedDB `zeter-os-primary-state`.
- `localStorage`: только маленький диагностический снимок; старое полное состояние может быть прочитано для миграции или временно записано как аварийный fallback.

- `data/restore-points.json`: до двенадцати неизменяемых снимков состояния; профиль `standard` использует 8, `enhanced` — 12, `manual` — 5.
- `data/backups/`: до двенадцати неизменяемых автоматических JSON-копий Python-режима.
- `data/Рабочие столы/`: производная Windows-читаемая копия, которая пересоздаётся из состояния.
- `data/Файлы ZeTer OS/`: полные самостоятельные копии перетащенных файлов. Состояние содержит только относительные ярлыки; копия удаляется после успешной записи только при отсутствии ссылки в текущем state, всех сохранённых точках и всех сохранённых JSON-backups.
- `data/Оформление объектов/`: свои значки папок/ярлыков и фоны папок. Путь строится приложением по ID объекта; служебное изображение очищается по тому же объединённому набору ссылок.

Не считай `data/Рабочие столы/` источником восстановления и не редактируй `data/` для тестирования миграции без отдельной копии.

Новая аварийная browser-копия хранится в envelope `storageMode: localStorage-emergency`, `updatedAt`, `state`. При чтении выбирается аварийная копия, только если она не старее IndexedDB; старое полное состояние без timestamp используется лишь при отсутствии основной записи. Успешная primary-запись не удаляет более новую аварийную копию. Ошибка чтения или повреждённая запись не считаются первым запуском: запись блокируется до успешного повторного чтения.

Promise основного сохранения возвращает `{ saved: true, fallback: false }` только после подтверждённой записи primary state. В browser-режиме успешная аварийная запись полного state в `localStorage` возвращает `{ saved: true, fallback: true }`. Если не сработало ни доступное основное, ни аварийное хранилище, Promise отклоняется, `lastSavedAt` не обновляется, а критические сценарии не должны показывать успех. Редакторы показывают отдельные статусы ожидания, обычного/аварийного успеха и ошибки; восстановление и текущее удаление ожидают Promise, при отказе возвращают state в памяти и не перезагружают систему.

Обычное удаление объекта меняет только новое рабочее состояние: существующие restore points и JSON-backups не переписываются и не очищаются, а нужные им managed-файлы, значки и фоны сохраняются физически. Снимки исчезают только по лимиту хранения, после отдельного подтверждённого действия пользователя или выбранной безопасной очистки; после удаления последней recovery-ссылки payload может быть собран как мусор. Периодическая previous-копия получает уникальное имя и не перезаписывает предыдущий снимок. Повреждённый источник ссылок блокирует payload-GC, чтобы неопределённость не приводила к потере данных.

Полный native-сброс сначала создаёт проверенный JSON-backup прежней основной записи, поэтому его payload остаётся доступным после перезапуска. Перед применением локальной точки desktop-версия проверяет, что каждый `managedPath` и `assetPath` безопасен и соответствующий файл существует внутри `data`; при любой недостаче state не заменяется, показывается точный список и предлагается импорт проверенного ZIP.

Native-загрузка различает успешное чтение, физическое отсутствие state-файла при первом запуске и ошибку существующего файла/bridge. Только отсутствие файла разрешает создать default state. До успешного чтения либо подтверждённого первого запуска `writesAllowed` остаётся выключенным: очередь primary save, малый snapshot, внешние копии и boot-сохранения не запускаются. Повреждённый или недоступный `zeter-os-state.json` показывает блокирующий экран восстановления и никогда автоматически не заменяется default state или backup.

Весь каталог `data/` переносим между компьютерами как единое целое. Канонический state и точки восстановления не должны сохранять абсолютный путь текущей папки программы: служебный native-статус записывается как относительный `data/zeter-os-state.json`. Исключение — явно созданные пользователем Windows-ярлыки: их абсолютная внешняя цель сохраняется намеренно и на другом компьютере может потребовать исправления.

Windows-читаемая копия сначала полностью строится во временном каталоге и только затем публикуется в `data/Рабочие столы/` атомарной заменой отдельных файлов. Ошибка этой производной копии не отменяет уже подтверждённую атомарную запись `zeter-os-state.json`; она возвращается отдельно как `readableOk: false` и записывается в лог.

Переносимый ZIP содержит `zeter-backup-manifest.json` с составом, размерами и контрольными суммами. Формат `.zeterbak` хранит этот проверенный ZIP в контейнере AES-256-GCM; ключ выводится из парольной фразы через PBKDF2-SHA-256 и нигде не сохраняется. Старые JSON/ZIP без manifest остаются импортируемыми, но интерфейс явно помечает их как legacy-копии без подтверждённых контрольных сумм.

## Контракты критических операций

### Google Drive

Контракт синхронизации и владельцы — [GOOGLE_DRIVE.md](GOOGLE_DRIVE.md). Облачный snapshot содержит только каноническое пользовательское состояние и обязательные internal payload; внешние цели ярлыков не обходятся. OAuth credentials, broker handles, device baseline и pending/conflict metadata не добавляются в экспортируемое состояние. На Drive сохраняются обычные файлы и immutable inventories, без облачного ZIP. Private browser Blob store удерживает исходные bytes для safety/version roundtrip; локальный post-apply hash отделён от cloud contentHash из-за native remap путей. Реальное облачное подключение должно быть подтверждено отдельно от synthetic проверок.

Private native metadata также содержит `uploadIntent` (либо `null`): строго поля `{accountKey, operationId, snapshotId, createdAt, expectedGeneration, localHash, bootstrap, fileIds}`. Account обязан совпадать с metadata; operation/snapshot и ключи `fileIds` — 32 lowercase hex, localHash/accountKey — 64 lowercase hex, createdAt — положительное целое время в миллисекундах, expectedGeneration — неотрицательное safe integer. `bootstrap` — `null` либо четыре разных Drive ID `{rootFolderId,dataFolderId,historyFolderId,stagingFolderId}`; `fileIds` содержит максимум 10000 пар ключ→различный Drive ID. Лишние/повреждённые поля отклоняются до сохранения, прежняя private запись сохраняется. Intent подтверждается до первой облачной мутации, ID каждого immutable файла — до POST: перезапуск повторно проверяет тот же объект, даже если listing ещё не показывает его. Поля не входят в пользовательский snapshot/экспорт; account-bound резервирование папок описано в [broker README](../cloud/google-drive-broker/README.md#резервирование-id-и-миграция).

Этот раздел описывает поведение выбранных API; [CORE_API_INDEX.md](CORE_API_INDEX.md) остаётся индексом имён. Сигнатуры и consumers подтверждай в исходниках. Примеры используют уже созданные runtime-объекты, а не вводят новые глобалы или второй механизм хранения.

| API и владелец | Вход и результат | Мутация, порядок и отказ | Ближайшая проверка |
|---|---|---|---|
| `saveState(options = {})` — `app.js` | Опции существующего storage-controller; `Promise` подтверждённого результата `{ saved: true, fallback, ... }` | Ждёт transaction-barrier, синхронизирует legacy aliases, передаёт сохранение controller-у. Skipped/неподтверждённая запись превращается в исключение. Сам по себе не откатывает предметные изменения: откат/черновик принадлежат caller | `smoke_persistence_ack.js`, `smoke_storage_runtime.js` |

Native требует primary-подтверждения; browser допускает аварийный полный localStorage с `fallback: true`. После отказа следующая операция может выполняться; это не повтор прежней записи | `smoke_storage_runtime.js` |
| `primaryStateSaveQueue.transaction(operation)` — `storage-utils.js` | `operation(write)`; `write(snapshot)` возвращает результат той же очереди; внешняя `Promise` возвращает результат callback | Ждёт предыдущие сохранения и удерживает barrier до завершения callback, освобождает его также при исключении. Обычные сохранения откладываются. **Внутри callback нельзя ждать обычный `saveState()` или этот barrier**: запись staged-снимка выполняй только через переданный `write` | `smoke_storage_runtime.js`, `smoke_state_migration.js` |

Режим удаления проекта — `transfer`/`delete`; результат операции удаления может быть `undefined` | Захватывает workspace до очереди. Через adapters `persistTransaction` и `saveSnapshot` сохраняет staged-библиотеку внутри полного state; публикует её только после `saved: true`. Смена/удаление workspace и неподтверждённая запись отклоняют операцию. Текст не обрезается `trim`; отказ сохраняет прежнюю live-библиотеку | `smoke_prompt_library.js` |

Пример подтверждения сохранения в существующем caller:

```javascript
const result = await saveState({ silentStorageError: true });
if (result?.saved !== true) throw new Error("Сохранение не подтверждено");
// Показывать успех можно после await; fallback: true требует аварийного статуса.
```

Пример записи уже подготовленного полного снимка внутри transaction:

```javascript
await primaryStateSaveQueue.transaction(async write => {
  const result = await write(candidate);
  if (result?.saved !== true) throw new Error("Снимок не сохранён");
  return result;
});
```

`candidate` должен быть независимым полным state, подготовленным профильным caller. Этот пример только сохраняет снимок: безопасная публикация предметных полей и проверка параллельных изменений остаются у controller. Готовые adapters смотри в `renderPromptLibraryApp` и `createVirtualDesktopController`; не присваивай весь устаревший снимок в live-state после `await`.

Native-ответ `ok: true` и JS-результат `saved: true` принадлежат разным уровням. Поля подтверждения primary и производных копий описаны в [NATIVE_BRIDGE.md](NATIVE_BRIDGE.md#критические-storage-вызовы).

## Правила миграций

1. Загружай старый объект без предварительного удаления неизвестных полей.
2. Добавляй отсутствующие значения через normalizers и безопасные defaults.
3. Сохраняй ID, пользовательский текст, файлы, задачи, события, настройки и рабочие столы.
4. Не удаляй существующую миграцию после выхода новой версии.
5. После миграции проверяй импорт старого состояния, повторное сохранение и повторную загрузку.
6. Изменение формата требует явного плана совместимости и обновления этого документа.

### Проверка migration

При изменении правила migration отдельно проверь default state, разреженный legacy state, неизвестные поля, пользовательские ID/текст, основной desktop, fallback `currentDesktop`, повторную migration и load → save → load. Запусти migration-smoke и общий suite по командам из [TESTING.md](TESTING.md).

Не исправляй и не переупорядочивай несвязанные normalizers в одном изменении. Для нового поля одновременно найди default, migration/normalizer, import validator и serializer.

## Удаление и legacy-совместимость

В ZeTer OS нет корзины, move/restore API, отмены удаления или автоочистки старых записей. После подтверждения объект удаляется из рабочего состояния через `deletion-utils.js`; отказ сохранения возвращает объект, а окна закрываются только после ACK. Автоматизация с явно разрешённой заменой использует синхронный permanent-remover в своей transaction boundary. Старые поля `deletedAt`/`originalParent` и зарезервированный `LEGACY_DELETED_ROOT` нужны только для чтения прежних state, импортов и исключения старых записей из интерфейса. Миграция, native-запуск и save не удаляют эти записи. Native GC учитывает их payload-ссылки вместе с recovery snapshots. Не тестируй восстановление через удалённую функцию; проверяй прямое удаление, отказ/отмену и совместимость legacy-данных.

Окончательное удаление должно одновременно убрать элементы, descendants, ссылки из окон/вкладок/закреплений/истории и связанные копии с учётом recovery-ссылок. Любое изменение этой цепочки требует автоматического smoke-теста текущего удаления и отдельной проверки legacy-state.

## Библиотеки ссылок рабочих столов

`desktop.data.library = { entries: [], categories: [] }` принадлежит конкретному рабочему столу. Записи, категории и избранное независимы; полные JSON/ZIP-бэкапы сохраняют все библиотеки. Defaults и миграция — `workspace-utils.js`, модель и операции — `link-library-utils.js`; root/desktop импорт проверяется через `state-import-validator.js`.

Категория: `{ id, name, pinned? }`; optional `pinned` — boolean, отсутствие означает обычную категорию. `orderedLinkCategories` показывает закреплённые сверху, сохраняя порядок массива внутри каждой группы. `moveCategory` меняет порядок только внутри такой группы; снятие закрепления возвращает категорию к её сохранённому месту среди обычных. Закрепление проходит ту же очередь/подтверждение сохранения и откат, принадлежит конкретному workspace и входит в JSON/ZIP. Старые категории совместимы без изменения schema. Запись: `{ id, name, target, kind, itemId?, categoryId, description, favorite, createdAt, updatedAt }`; пустая категория означает «Без категории». Windows-цели сравниваются без учёта регистра и вида слешей; сайты и внутренние адреса нормализуются существующим shortcut owner. Удаление категории сохраняет записи, удаление записи не меняет цель. Неизвестные поля сохраняются. Лимиты: 5000 записей, 200 категорий, 300 символов имени ссылки, 120 имени категории, 4000 описания.

Старый state без библиотек получает отдельные пустые библиотеки. Кратковременный legacy-формат `state.library` переносится один раз только в исходный `currentDesktop`, если у него нет своей библиотеки; obsolete root удаляется. При конфликте текущая библиотека не заменяется, а старые данные сохраняются в `state.legacyLinkLibrary` как резерв для ручного восстановления (не показываются как общая библиотека). Смена стола и повторная миграция не клонируют старые записи. Schema не меняется.

Запись может иметь `pinnedIn: string[]` — до трёх уникальных разделов: `all`, `favorites` (только для избранной записи), `uncategorized` (только без категории) либо текущий categoryId. `isLinkPinned` и `filterLinkEntries` стабильно поднимают закреплённые записи только в выбранном разделе, не меняя порядок массива и результаты поиска. `togglePinned(id, filter)` сохраняет независимый pin через обычную workspace-очередь. Перенос записи/удаление категории убирает её старый category-pin; снятие избранного убирает только favorites-pin. Legacy `pinned: true` переводится в all; старые записи без полей имеют пустое закрепление. JSON/ZIP и импорт сохраняют и проверяют это поле.

Действие захватывает workspace до очереди Promise, сериализуется через очередь с автоматизациями и ждёт `{ saved: true }`; отказ восстанавливает только его прежнюю библиотеку. Переключение рабочего стола не перенаправляет ожидающую операцию. Неподдерживаемая схема, повтор ID/адреса и повреждённый импорт отклоняются до записи. Абсолютный Windows-путь может содержать личные данные; он намеренно входит в полный бэкап.
## Удаление рабочего стола и сохранённый архив

Окно удаления дополнительного стола содержит группы files/tasks/calendar/links/automation/notifications. Все флажки выключены. Выбранные группы удаляются из текущего состояния; невыбранные сохраняются в `state.archivedDesktops[]`, без переноса на основной стол. Архив `{id, archivedAt, desktop, fs}` хранит исходные ID, metadata, группы и дерево объектов без активной нормализации. Он не участвует в запуске автоматизации, списке столов или активной файловой системе. Выбранные поля отсутствуют в `desktop.data`, при выборе files архивный fs пуст. Если выбраны все непустые группы, архив не создаётся.

В Windows основной JSON сохраняет архив и его payload references. После подтверждения primary Python создаёт читаемый `data/Архив рабочих столов/<archiveId>/desktop.json`. Эти папки не удаляются автоматически, их безопасные references удерживают payload от GC даже после смены активного состояния. Ошибка производной записи видима через archiveOk/readableOk; основной подтверждённый JSON продолжает хранить данные. Браузер хранит архив в IndexedDB или аварийном localStorage.

Кнопка «Скачать все данные стола» получает detached snapshot только указанного стола после синхронизации редакторов, независимо от выбранных флажков. ZIP содержит desktop.json (`format: zeter-desktop-backup`, version 1) и README; в Windows native API добавляет все безопасные managed/asset вложения. Внешние Windows-пути и сайты по ссылкам не читаются. Отмена/ошибка скачивания не удаляет стол. Этот архив одного стола не является полным OS backup и не импортируется кнопкой полного восстановления ОС.

Удаление использует общую mutation queue и staged storage transaction; live-state публикуется только после saved:true. Отказ оставляет стол и выбор; изменение затронутых данных вызывает одну компенсационную запись, её отказ сообщает неопределённость. Runtime активного стола закрывается до release barrier, переход на третий стол и независимые изменения сохраняются. Backup/restore retention прежних копий сохраняется. Глубокий import validator проверяет архивные документы, группы, HTML и безопасные пути; hydration внешних изображений учитывает архив.

## Проверка архивов и выборочное восстановление

`security-recovery-utils.js` читает выбранный ZIP/.zeterbak в отдельные структуры, проверяет полный состав манифеста/CRC/hash, обязательные payload-ссылки и применяет глубокую валидацию к detached state. Проверка сама не сохраняет state/настройки и не обращается к текущей data для восполнения отсутствующих файлов. Пароль остаётся в памяти. SHA-256 относится к конкретному выбранному файлу; открытие вложений сторонними программами и их безопасность не подтверждаются.

`security-restore-utils.js` строит candidate и список add/update/remove для одного item/folder, task project или desktop. Copy создаёт новые ID и переназначает известные связи; replace работает только на исходном столе и сохраняет новые посторонние объекты при выборочной замене. Неоднозначные и внешние зависимости дают явный отказ. Замена целого стола показывает удаления. Восстановленные автоматизации выключены до ручного включения; ссылки правил/типизированных условий переназначены. Восстановленные таймеры остановлены на последнем записанном интервале. Aliases верхнего уровня относятся к основному столу `desktop`.

Применение требует закрытых редакторов, неизменного preview и подтверждения. Интерфейс/фоновые мутации блокируются на время операции; после страховочной точки candidate проходит primary queue transaction с `requirePrimary:true`. При отказе fallback не записывает новый candidate. Live state публикуется после `saved:true`; native payload удерживается lease до подтверждения. Исходный архив остаётся неизменным. После выбора другого объекта/режима сравнение требуется заново.

Browser-история — `security-vault-utils.js`, отдельная выбранная папка через File System Access, handle в IndexedDB `zeter-security-vault-folder`, собственный подкаталог/marker/index. Web Locks сериализует изменения между вкладками. Поле pending в собственном индексе подтверждается до создания нового ZIP: после отказа публикации следующая попытка сначала принимает этот единственный проверенный candidate либо останавливается, не создавая ещё файлы. История проверяет ZIP после записи, защищает pin/последний valid и не удаляет неизвестные файлы; превышенный после отказа обслуживания лимит блокирует дальнейший рост до изменения настроек. Native конфигурация и browser handle не переносятся внутри ZIP.
