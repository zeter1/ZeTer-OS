# Веб-сборки для uCoz

## Собрать ZIP на Windows

В корне проекта запустите двойным щелчком `build_ucoz.cmd`. Нужен Python 3.10 или новее; дополнительные библиотеки не нужны. При нестандартной установке можно задать `ZETER_PYTHON` — полный путь к Python.

Результат: `dist/ucoz/ZeTer-OS-uCoz-FTP-VERSION.zip`. Версия читается из `app/js/core/version.js`. Архив содержит только веб-приложение и файлы запуска веб-сборки. Python, EXE, пользовательская `data`, журналы и Git в него не входят. Сборщик ничего не загружает в интернет.

Для командной строки из корня проекта:

```powershell
.\build_ucoz.cmd --no-pause
```

Для другого каталога результата:

```powershell
python -B tools/build_ucoz.py --output-dir dist/ucoz-other
```

Одинаковые исходники и сборщик дают одинаковые байты ZIP. Если ZIP этой версии уже есть и отличается, сборщик остановится и сохранит предыдущий результат. Повторная сборка без изменений допустима. Для исправленной версии повышайте версию по [README](../README.md#версии-и-история-изменений) либо используйте отдельный выходной каталог.

## Что находится внутри

```text
index.html
ucoz-loader.js
release.json
manifest.json
service-worker.js
releases/
  vMAJOR-MINOR-PATCH-CONTENT_HASH/
    index.html
    manifest.json
    js/...
    css/...
    assets/...
    update-probe.html
```

В ZIP нет внешней папки `ZeTer OS` или `app`. Папка `releases` нужна для независимых версий ресурсов. Внутри каждой сборки сохраняется исходное расположение файлов приложения, порядок скриптов, отдельные JS/CSS и их относительные пути. Все файлы обычной `app` входят, кроме исходного Service Worker, который заменяется общим веб-обработчиком обновлений. Неожиданные служебные файлы и ссылки/junction вызывают отказ сборки и требуют проверки.

Build ID имеет вид `vMAJOR-MINOR-PATCH-HASH`, например `v1-2-3-0123456789abcdef`; номер здесь только пример. Точки номера версии в имени папки заменены дефисами. Версия приложения и поле `version` в `release.json` остаются исходными, с точками. Старое имя папки с точками отклонялось реальным uCoz: `553 Prohibited file name`; создание каталогов с новым форматом через FTP/MCP принято. Это подтверждает имена, но не завершение публикации или обновление браузера. Сборщик проверяет имена и вложенность до выдачи ZIP.

В подготовленной копии приложения меняются ровно две точки интеграции: ссылка manifest ведёт на общий manifest, регистрация Service Worker ведёт на общий обработчик в корне веб-пакета. Исходные `app/index.html` и `shell-ui-utils.js` сборщик не переписывает. Общий manifest сохраняет постоянный адрес запуска и значки текущей сборки. Идентификатор папки учитывает содержимое всей `app` и самого сборщика, поэтому даже разные сборки одного номера получают разные URL.

Владелец упаковки: `tools/build_ucoz.py`; Windows-вход: `build_ucoz.cmd`. Portable Python ZIP и Windows EXE собираются отдельно.

## Загрузка через файловый менеджер или FTP

Ограничения показанного файлового менеджера uCoz: до 30 файлов за один выбор, общий размер выбранных файлов до 200 МБ, до 1000 элементов в каталоге, глубина до 10 папок, длина имени до 45 символов. Для папок используйте латинские буквы, цифры, `_` и `-`; у файлов дополнительно допустимы точки расширения. Глубина считается вместе с `portfolio/ZeTerOS`. Существующие одноимённые файлы перезаписываются — проверьте каталог назначения перед каждой передачей.

В файловом менеджере создавайте папки по структуре ZIP и загружайте файлы каждого каталога партиями до 30, соблюдая предел размера. Не объединяйте JS/CSS ради лимита выбора, не сокращайте имена без проверки всех ссылок и не рассчитывайте на серверную распаковку ZIP. FTP/API — отдельные способы передачи; предел выбора 30 файлов в интерфейсе не доказывает их предел или успешность. При отказе имени не переключайте указатель и не переименовывайте ресурс только на сервере: исправьте воспроизводимый источник упаковки и заново проверьте пакет.

1. Распакуйте ZIP в пустую локальную папку. На сайте сделайте резервную копию заменяемых корневых веб-файлов и текущего `release.json`. Перед первой миграцией также экспортируйте данные ZeTer OS через штатный интерфейс.
2. Откройте `/portfolio/ZeTerOS/` в файловом менеджере uCoz или FTP-клиенте. Загружайте распакованные файлы, а не сам ZIP.
3. Сначала полностью загрузите новую папку `releases/vMAJOR-MINOR-PATCH-HASH/` с фактическим build ID из ZIP. Не заменяйте содержимое папок прежних сборок. Проверьте завершение всех передач и доступность её `index.html`, JS и CSS.
4. Загрузите общие `ucoz-loader.js`, `index.html`, `manifest.json`, затем `service-worker.js`.
5. **Последним загрузите `release.json`**: это переключатель на новую сборку. Если файловый менеджер или FTP допускает временное имя и переименование, сначала загрузите `release.json.new`, затем замените `release.json` переименованием. При незавершённой загрузке оставьте старый указатель.
6. Откройте постоянный адрес `https://dkl.do.am/portfolio/ZeTerOS/index.html`. После автоматического перехода адрес содержит `releases/<build ID>/index.html` — это ожидаемо. Сохраняйте в закладках постоянный адрес. Общий manifest задаёт его и для запуска PWA.

**Критерий готовности:** первое обычное открытие именно прежнего адреса после завершённой публикации должно показать актуальную сборку. Специальная ссылка, очистка кэша и дополнительное пользовательское открытие/обновление после первого не выполняют этот критерий. При воспроизведённом нарушении результат — `FAIL`; при отсутствии проверки — `NOT_VERIFIED`. Уже открытые рабочие вкладки нельзя принудительно перезагружать.

Старые файлы `js`, `css`, `assets` прежней плоской публикации удалять не требуется. Старые папки `releases` также сохраняйте: ими могут пользоваться открытые вкладки. Сборщик и Service Worker автоматически их не удаляют. Место на сервере и в браузерном кэше будет расти; очистка старых сборок требует отдельного решения, когда они больше не нужны для работы и отката.

Для отката верните сохранённый `release.json` при сохранённой целой папке соответствующей сборки. Код откатится, но данные могут уже иметь новый формат: совместимость такого отката не гарантируется; восстановление данных — отдельный сценарий.

## Как обновляется браузер

Когда браузер получил актуальный общий загрузчик, он читает `release.json` через `fetch` с `cache: "no-store"` и уникальным параметром запроса, затем переходит в новую папку. JS, CSS, изображения и вложенные CSS-импорты получают новые URL за счёт родительской папки; один `?v=` для этого не используется. Получение загрузчика на самом первом открытии со старым кэшем — отдельный обязательный критерий.

Общий Service Worker регистрируется с `updateViaCache: "none"`. На обычное обновление главной страницы уже открытой сборки он заново читает указатель и переходит к актуальной версии. Новые файлы кэшируются под отдельным именем, включающим scope и build ID. Для offline используются только кэши, у которых есть признак завершённой установки; запросы ресурсов сравниваются с полным URL. При отсутствии сети остаётся доступна ранее полностью закэшированная сборка. Чужие кэши, localStorage и IndexedDB не очищаются.

Открытая вкладка не перезагружается принудительно: пользователь может закончить работу и сохранить изменения. Следующее обычное открытие постоянного адреса должно получать новую версию до начала работы. Активация нового worker через `skipWaiting()`/`clients.claim()` не заменяет уже исполняемый JS; массовый `clients.navigate()` не доказывает безопасность для несохранённых черновиков. Новый worker не может предполагать, что старая страница поддерживает новый протокол готовности/сохранения.

**Известное ограничение миграции:** локальная fixture со старой плоской 4.0.19, её worker и HTTP `max-age=1728000` показала 4.0.19 при первом открытии после передачи новой сборки; 4.0.20 появилась только после следующего обычного reload. Сохранённый маркер данных остался. Это `FAIL` строгой первой навигации, даже если прежний эксперимент помечен `PASS_WITH_INITIAL_MIGRATION_LIMIT`. Одинаковый общий загрузчик между A/B сам по себе не является причиной; замена имени загрузчика в новом HTML не исправляет старый HTML, который браузер ещё использует из кэша. Матрица, по которой нужно проверять последующие исправления, — [TESTING.md](TESTING.md#приёмка-обновления-ucoz).

Нельзя обещать универсальное выполнение первой миграции одними новыми файлами, пока старый worker/HTTP-кэш не дал браузеру получить новый код. Нужно установить конкретную цепочку запросов и доступные меры хостинга. После загрузки проверьте HTTP-ответы uCoz, отсутствие login/HTML-заглушек вместо JS/JSON и доступность Service Worker с JavaScript Content-Type. `release.json`, входной HTML и worker желательно отдавать с `Cache-Control: no-cache`; для неизменяемых `releases` подходит длительное кэширование. Новые заголовки не отменяют немедленно прежний свежий HTTP-кэш. Meta-теги HTML не заменяют HTTP-заголовки. Не рассчитывайте на `.htaccess`, PHP или управление заголовками, пока хостинг этого не подтвердил. `updateViaCache: "none"` относится к worker-скриптам, а не автоматически ко всем HTML/JS.

HTTP-кэш, Service Worker CacheStorage и серверный/CDN-кэш — разные уровни. Основания: [MDN: Request.cache](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache), [MDN: updateViaCache](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/updateViaCache), [MDN: HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).

## Порученная загрузка Codex через MCP

Применяй этот порядок, когда пользователь просит загрузить новую сборку или протестировать её публикацию. Такая просьба разрешает необходимые обратимые действия в указанном каталоге; повторное подтверждение на каждую передачу не требуется. Просьба только собрать ZIP или улучшить промпт сама по себе публикацию не разрешает. Не меняй FTP-пароли, ключи, доступы, настройки сайта и другие проекты. При запросе оставить проверенную сборку на сайте не откатывай успешный результат только потому, что тест закончен.

**Цель и точные границы:** подключённый сайт `dkl.do.am`; файловый менеджер `https://dkl.do.am/panel/?a=fm&f=portfolio%2FZeTerOS`; FTP-каталог `/portfolio/ZeTerOS/`; единственный публичный вход `https://dkl.do.am/portfolio/ZeTerOS/index.html`. Не заменяй его специальной ссылкой. Панель управления и публичный сайт — разные адреса. Для передачи предпочитай уже подключённый `mcp__zeter_ucoz__ftp_tool`; действия `list/read/mkdir/upload/write/rename` описаны его текущей схемой. Не вызывай `ftp_password_*` и не проси пользователя пересылать пароли. При недоступном управлении Firefox работай через явно разрешённый MCP; существующую браузерную сессию не подменяй.

1. Проверь `git status`, текущие исходники и эту инструкцию. Установи фактическую версию по `app/js/core/version.js`, выполни профильные проверки и собери ZIP штатным `tools/build_ucoz.py`. Непроверенный ZIP не является готовой публикацией. Изолируй браузерные тесты по [TESTING.md](TESTING.md).
2. Через `list` прочитай именно `/portfolio/ZeTerOS/`. Не предполагай, что прошлое состояние сайта сохранилось. Прочитай текущие `index.html`, `manifest.json`, `service-worker.js`, а также `release.json` и загрузчик, если они существуют. Установи текущую плоскую/release-схему и версию; проверяй свежие HTTP-ответы отдельно от браузерного кэша.
3. До замены сохрани все затрагиваемые существующие файлы в отдельную локальную папку под игнорируемым `work/`, с manifest: точный remote path, локальный backup path, размер и SHA-256. Сохраняй исходные UTF-8-байты и CRLF; преобразование переводов строк при записи текста не является byte-identical backup. Сверь размеры с FTP. Не публикуй резервные копии и пользовательские данные на сайте. Запиши список новых путей и точные действия отката; старые `js/css/assets` не изменяй при переходе на releases.
4. Распакуй проверенный ZIP локально. До массовой передачи сохрани точную карту `local → remote`, размеры и SHA-256. Проверь отсутствие missing sources, traversal, дублей, коллизий и неожиданных перезаписей; root ZIP должен стать содержимым `/portfolio/ZeTerOS/`, без дополнительной папки. Build ID и все имена должны пройти ограничения uCoz. Не переименовывай несовместимый каталог только на сервере — исправь сборщик и пересобери, чтобы ссылки и hash соответствовали результату.
5. Создай новые каталоги сверху вниз. Передай всю новую неизменяемую release-папку. Для каждого вызова проверяй фактический ответ MCP, включая текст ошибки даже при отсутствии `isError`. Сохраняй прогресс по конкретным файлам; общий exit code оболочки не доказывает успешность всех передач. При таймауте сначала прочитай целевой каталог/файл и установи, дошёл ли файл полностью. Допустим ограниченный повтор только отсутствующего/неполного файла после такой проверки; повторяющийся отказ сети — конкретный блокер, а не повод бесконечно перезаливать всё.
6. До переключения сверь каждый intended path и размер с FTP и байты/SHA-256 через свежие HTTPS-ответы. Код HTTP 200 сам по себе не доказывает правильный файл: исключи HTML login/error-заглушки вместо JS/CSS/JSON и проверь Content-Type. При разрешённом независимом чтении можно пакетировать проверки; запись указателя и зависимые шаги выполняй последовательно. Неполная release-папка никогда не становится активной.
7. Передай совместимые корневые loader/index/manifest, затем worker. `release.json` — последним после успешной проверки всей сборки. Если сервер поддерживает замену rename, сначала загрузи временный JSON в этот же каталог, проверь его и переименуй; саму возможность замены существующего файла через rename установи фактически. При отказе не удаляй старый указатель. Для первой миграции предусмотри отсутствие предыдущего release.json: откат возвращает исходный корневой HTML/manifest/worker, а не выдуманный указатель.
8. Выполни [матрицу приёмки](TESTING.md#приёмка-обновления-ucoz) на настоящем HTTPS в отдельном профиле с искусственной заметкой/задачей. Прогрей A до передачи B; сохрани профиль внутри перехода. Для каждого первого открытия запиши первоначальный и конечный URL, версию/build ID, запросы и сохранность данных. Уже открытая вкладка с черновиком остаётся нетронутой. `FAIL` первой legacy-навигации не стирай следующей успешной загрузкой. FTP/MCP-передача не доказывает загрузку через UI файлового менеджера; установленная PWA и браузеры, которые не запускались, остаются `NOT_VERIFIED`.
9. При подтверждённо неработоспособной активной публикации верни сохранённый указатель или исходные корневые файлы из backup и проверь результат; не откатывай формат пользовательских данных и не удаляй браузерные базы. При рабочем результате, который пользователь поручил оставить, сохрани его активным и явно сообщи оставшиеся ограничения. Прежние release-папки сохраняй для открытых вкладок и отката. Тестовые файлы перечисли в отчёте; облачное удаление выполняй только в разрешённых границах и с соблюдением требований инструмента.
10. Финал: активная версия/build ID, постоянный публичный адрес, ZIP и SHA-256, место backup/карты загрузки, точные `VERIFIED`, `FAIL`, `NOT_VERIFIED`, что оставлено на сервере и что нужно прислать при ошибке. Публикация на uCoz не разрешает коммит или GitHub push.
