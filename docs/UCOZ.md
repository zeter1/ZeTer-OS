# Веб-сборки для uCoz

## Прямая загрузка содержимого app

Основной простой вариант: загрузите **содержимое `app/`**, сохраняя `js/`, `css/`, `assets/` и остальные подпапки, прямо в `/portfolio/ZeTerOS/`. Внешняя папка `app` на сервере не нужна. Публичный вход остаётся `https://dkoles.com/zeteros/index.html`.

1. После изменения исходников запустите `prepare_web.cmd` в корне проекта. Он проверяет ссылки и имена uCoz, затем обновляет только `app/web-release.json`. ZIP, папка releases и интернет не нужны. При изменениях через Codex готовность этого файла проверяет общий strict-check. Проверка без записи: `python -B tools/prepare_web.py`.
2. Сохраните резервную копию прежних файлов сайта перед заменой или удалением. Удаление серверных файлов не очищает кэш браузеров. Не удаляйте браузерные данные пользователей.
3. Загрузите **все файлы app, кроме `web-release.json`**, с сохранением путей и завершите передачи. `manifest.json` — обычный PWA-файл, его передают вместе с остальными.
4. **`web-release.json` загрузите последним.** Это отдельный указатель готовой версии с размером и SHA-256 каждого публичного файла. Нельзя брать его из другой копии исходников. Если меняли хотя бы один файл после подготовки, запустите её заново.
5. Откройте постоянный `index.html` или нажмите обычное обновление/F5. После установки нового механизма Ctrl+F5 и очистка данных не нужны. Проверьте версию в «О ZeTer OS».

`app/js/web-bootstrap.js` удерживает запуск предметных скриптов, пока worker не сохранил полный проверенный комплект. `app/service-worker.js` получает указатель и ресурсы без HTTP-кэша, сверяет байты и помечает комплект полным последним. HTML, CSS, JS и изображения вкладки читаются из одного комплекта; сетевой ответ не дополняет работающий комплект. Привязка вкладки хранится в CacheStorage и переживает остановку worker. При оборванной передаче или серверной заглушке прежний полный комплект остаётся рабочим. При первом посещении без полной копии показывается ожидание с явным повтором; приложение и чтение/сохранение его данных ещё не запускаются.

Каждое обычное открытие/F5 проверяет опубликованную версию до запуска. В открытом приложении проверка выполняется при возвращении во вкладку, восстановлении сети и раз в пять минут видимой работы. Уведомление просит сохранить работу и обновить страницу обычной кнопкой; вкладка не перезагружается сама. Без сети доступен последний полный комплект. IndexedDB/localStorage и чужие кэши не очищаются. Полные и частичные комплекты автоматически не удаляются: они нужны открытым вкладкам и восстановлению; это расходует место браузера. При нехватке места новая версия не активируется, данные не сбрасываются.

**Первый переход с прежней публикации:** новый код должен сначала попасть в браузер через старый worker/HTTP-кэш. При наличии старых вкладок без привязки к комплекту новый worker не ускоряет активацию и не перехватывает эти вкладки. Сохраните работу, закройте все старые вкладки ZeTer OS и откройте постоянный адрес снова. Первое открытие из любого старого кэша без мер на стороне хостинга не гарантируется. Удаление старых файлов этого не отменяет; legacy-вкладки могут ещё запрашивать удалённые ресурсы. Firefox, установленная PWA и реальная миграция сайта проверяются отдельно.

Владельцы: `tools/prepare_web.py` + `prepare_web.cmd` — подготовка; `app/web-release.json` — generated, вручную не редактировать; `app/js/web-bootstrap.js` — запуск и уведомление; `app/service-worker.js` — проверка и комплекты. Python/native с локальным `?native=1` и открытие файла с диска запускаются отдельно без веб-кэша. SHA-256 проверяет целостность передачи, а не подлинность скомпрометированного сайта.

## Альтернативная ZIP-публикация

Следующие разделы описывают прежнюю поддерживаемую схему с серверными папками `releases`. Она остаётся отдельным вариантом; её runtime-only патчи нельзя смешивать с прямой публикацией `app`. Для прямой публикации следуйте разделу выше.

## Выбрать объём следующей загрузки

- Изменилось само приложение (`app/`) — соберите полный ZIP и новую immutable-папку. Файл с уже совпадающими байтами повторно не передавайте: сначала подтвердите свежим HTTPS/SHA-256. Указатель переключается последним.
- Исправляется только обработчик обновлений/офлайн-кэша — используйте **runtime-only** из ZIP фактически опубликованной версии. Сохраняются её build ID, версия и payload; на сайт передаётся только `service-worker.js`.
- Python/pywebview/EXE и их упаковка — отдельный контур. Версия веб-runtime задаётся `WEB_RUNTIME_VERSION` в сборщике. Служебный патч не повышает версию приложения и не меняет `app/`, launcher, bridge или PyInstaller.

## Служебный патч без повторной загрузки приложения

Сначала прочитайте актуальный серверный `release.json` и сверьте `version`, `build`, `entry` с выбранным полным ZIP. Локальный архив не доказывает текущее состояние сайта.

```powershell
.\build_ucoz.cmd --runtime-only-from dist/ucoz/ZeTer-OS-uCoz-FTP-4.0.31.zip --output-dir dist/ucoz-runtime --no-pause
```

`4.0.31` — исходный архив первой публикации runtime r2; для следующего патча выбирайте фактически активный архив. Эквивалент: `python -B tools/build_ucoz.py` с теми же аргументами.

Результат: ZIP только с worker, отдельный `service-worker.js` и локальный `upload-plan.json`: version/build/runtime, SHA-256 исходного ZIP, точные размер/хеш файла. **План и ZIP на сайт не загружать.** План не означает выполненную передачу. Конфликтующий результат сохраняется, команда завершается ошибкой; выберите другой выходной каталог. Частичный результат команды с ошибкой не является готовым комплектом.

Порядок для Codex в файловом менеджере:

1. Повторно проверить указатель и `/portfolio/ZeTerOS/`. Сохранить прежний worker и указатель байт в байт локально с размером/SHA-256; зафиксировать карту единственной замены.
2. Выполнить профильный smoke и браузерную проверку. Записать installing/waiting/active и ответ `ZETER_UCOZ_RUNTIME_STATUS` (`runtime`, `build`, `complete`): одинаковый `scriptURL` не различает поколения worker.
3. Передать только worker из плана. Не передавать заново `releases`, `release.json`, manifest, CSS, изображения и JS приложения.
4. Сверить свежий HTTPS worker по размеру/SHA-256/Content-Type. Указатель должен побайтно совпасть с backup. В заранее прогретом отдельном профиле проверить активацию и обычное открытие без Ctrl+F5, очистки данных и ручного `registration.update()`, сохранив соседний черновик.
5. До `complete: true` проверить прежний полный офлайн-кэш; после — текущую версию offline. При отказе вернуть сохранённый worker. Данные и старые папки не удалять.

Загрузка файлов не меняет задним числом исполняемый старый код. Первое открытие под несовместимым прежним reader может показать старую версию до установки r2; это не успешная первая миграция. После активации r2 следующее обычное открытие должно получить текущую сборку. Рабочие вкладки принудительно не перезагружаются.

## Собрать ZIP на Windows

В корне проекта запустите двойным щелчком `build_ucoz.cmd`. Нужен Python 3.10 или новее; дополнительные библиотеки не нужны. При нестандартной установке можно задать `ZETER_PYTHON` — полный путь к Python.

Результат: `dist/ucoz/ZeTer-OS-uCoz-FTP-VERSION.zip`. Версия читается из `app/js/core/version.js`. Архив содержит только веб-приложение и файлы запуска веб-сборки. Python, EXE, пользовательская `data`, журналы и Git в него не входят. Сборщик ничего не загружает в интернет.

Для командной строки из корня проекта:

```powershell
.\build_ucoz.cmd --no-pause
```

Для другого каталога результата:

```powershell
python -B tools/build_ucoz.py --output-dir dist/ucoz-other
```

Одинаковые исходники и сборщик дают одинаковые байты ZIP. Если ZIP этой версии уже есть и отличается, сборщик остановится и сохранит предыдущий результат. Повторная сборка без изменений допустима. Для исправленной версии повышайте версию по [README](../README.md#версии-и-история-изменений) либо используйте отдельный выходной каталог.

## Что находится внутри

```text
index.html
ucoz-loader.js
release.json
manifest.json
service-worker.js
releases/
  vCONTENT_HASH/
    index.html
    ucoz-entry.js
    manifest.json
    js/...
    css/...
    assets/...
    update-probe.html
```

В ZIP нет внешней папки `ZeTer OS` или `app`. Папка `releases` нужна для независимых версий ресурсов. Внутри каждой сборки сохраняется исходное расположение файлов приложения, порядок скриптов, отдельные JS/CSS и их относительные пути. Все файлы обычной `app` входят, кроме исходного Service Worker, который заменяется общим веб-обработчиком обновлений. Неожиданные служебные файлы и ссылки/junction вызывают отказ сборки и требуют проверки.

Build ID имеет вид `v` и 14 шестнадцатеричных символов SHA-256, например `v0123456789abcd`: всего 15 символов. Номер версии хранится отдельно в `release.json`. Фактическая панель uCoz ограничивает создание и переименование папок 15 символами; прежние длинные папки создавались через FTP и сохраняются для открытых вкладок и отката. Новый загрузчик и worker принимают оба формата идентификаторов; старый worker новый короткий формат не понимает, поэтому первое открытие с прежним кэшем может показать прежнюю версию до установки нового worker. Сборщик проверяет длину каждой папки и файла до выдачи ZIP.

В подготовленной копии приложения ссылка manifest ведёт на общий manifest, регистрация Service Worker — на общий обработчик в корне веб-пакета. Перед ресурсами добавляются единственный `<base href="./" data-zeter-ucoz>` и синхронный внешний `ucoz-entry.js`. Он закрепляет абсолютный base папки сборки и до запуска приложения заменяет адрес через `history.replaceState` на постоянный `index.html`, сохраняя query/hash и history.state. Относительные CSS, JS, изображения и PWA продолжают использовать закреплённый base. Только CSP упакованного HTML разрешает `base-uri 'self'`; inline/eval-скрипты не разрешаются. Исходные `app/index.html` с `base-uri 'none'` и `shell-ui-utils.js` сборщик не переписывает; неожиданный CSP/base останавливает упаковку. Общий manifest сохраняет постоянный адрес запуска и значки текущей сборки. Идентификатор папки вычисляется по точным байтам подготовленного immutable-payload, включая entry-bootstrap и преобразования HTML/регистрации worker. Изменение только корневого worker/загрузчика больше не переименовывает все ресурсы; изменение самого payload меняет его адрес.

Владелец упаковки: `tools/build_ucoz.py`; Windows-вход: `build_ucoz.cmd`. Portable Python ZIP и Windows EXE собираются отдельно.

## Загрузка через файловый менеджер или FTP

Ограничения показанного файлового менеджера uCoz: до 30 файлов за один выбор, общий размер выбранных файлов до 200 МБ, до 1000 элементов в каталоге, глубина до 10 папок, длина имени файла до 45 символов, папки — до 15. Для папок используйте латинские буквы, цифры, `_` и `-`; у файлов дополнительно допустимы точки расширения. Глубина считается вместе с `portfolio/ZeTerOS`. Существующие одноимённые файлы перезаписываются — проверьте каталог назначения перед каждой передачей.

В файловом менеджере создавайте папки по структуре ZIP и загружайте файлы каждого каталога партиями до 30, соблюдая предел размера. Не объединяйте JS/CSS ради лимита выбора, не сокращайте имена без проверки всех ссылок и не рассчитывайте на серверную распаковку ZIP. FTP/API — отдельные способы передачи; предел выбора 30 файлов в интерфейсе не доказывает их предел или успешность. При отказе имени не переключайте указатель и не переименовывайте ресурс только на сервере: исправьте воспроизводимый источник упаковки и заново проверьте пакет.

1. Распакуйте ZIP в пустую локальную папку. На сайте сделайте резервную копию заменяемых корневых веб-файлов и текущего `release.json`. Перед первой миграцией также экспортируйте данные ZeTer OS через штатный интерфейс.
2. Откройте `/portfolio/ZeTerOS/` в файловом менеджере uCoz или FTP-клиенте. Загружайте распакованные файлы, а не сам ZIP.
3. Сначала полностью загрузите новую папку `releases/vCONTENT_HASH/` с фактическим build ID из ZIP. Не заменяйте содержимое папок прежних сборок. Проверьте завершение всех передач и доступность её `index.html`, JS и CSS.
4. Загрузите общие `ucoz-loader.js`, `index.html`, `manifest.json`, затем `service-worker.js`.
5. **Последним загрузите `release.json`**: это переключатель на новую сборку. Если файловый менеджер или FTP допускает временное имя и переименование, сначала загрузите `release.json.new`, затем замените `release.json` переименованием. При незавершённой загрузке оставьте старый указатель.
6. Откройте постоянный адрес `https://dkoles.com/zeteros/index.html`. **После завершения загрузки адресная строка должна содержать именно этот адрес**, а приложение — актуальную версию. Внутренний переход к `releases/<build ID>/index.html` завершается до запуска приложения возвратом постоянного адреса. Если `releases/...` остался в строке, публикация не принята. Общий manifest задаёт постоянный адрес и для запуска PWA.

**Критерий готовности:** первое обычное открытие именно прежнего адреса после завершённой публикации должно показать актуальную сборку и сохранить постоянный `index.html` в адресной строке. Повторный обычный reload также сохраняет этот адрес. Проверяйте конечный `location.href`, `document.baseURI`, URL/scope регистрации worker и запросы ресурсов. Специальная ссылка, очистка кэша и дополнительное пользовательское открытие/обновление после первого не выполняют этот критерий. При воспроизведённом нарушении результат — `FAIL`; при отсутствии проверки — `NOT_VERIFIED`. Уже открытые рабочие вкладки нельзя принудительно перезагружать.

Старые файлы `js`, `css`, `assets` прежней плоской публикации удалять не требуется. Старые папки `releases` также сохраняйте: ими могут пользоваться открытые вкладки. Сборщик и Service Worker автоматически их не удаляют. Место на сервере и в браузерном кэше будет расти; очистка старых сборок требует отдельного решения, когда они больше не нужны для работы и отката.

Для отката верните сохранённый `release.json` при сохранённой целой папке соответствующей сборки. Код откатится, но данные могут уже иметь новый формат: совместимость такого отката не гарантируется; восстановление данных — отдельный сценарий.

## Как обновляется браузер

Когда браузер получил актуальный общий загрузчик, он читает `release.json` через `fetch` с `cache: "no-store"` и уникальным параметром запроса, затем внутренне переходит в новую папку. Entry bootstrap закрепляет её абсолютный base и возвращает постоянный адрес без новой навигации. JS, CSS, изображения и вложенные CSS-импорты получают новые URL за счёт папки ресурсов, хотя адрес страницы остаётся постоянным; один `?v=` для этого не используется. Старый совместимый загрузчик/worker тоже может перенаправить к новому entry: возврат адреса принадлежит самому entry. Получение актуальной сборки на самом первом открытии со старым кэшем — отдельный обязательный критерий.

Общий Service Worker регистрируется с `updateViaCache: "none"`. На обычное обновление главной страницы он заново читает указатель и переходит к актуальному entry; bootstrap снова сохраняет постоянный адрес. Runtime r2 проверяет entry и bootstrap при установке и активирует маршрутизацию, не ожидая полной офлайн-копии. Полный precache начинается из fetch-события навигации, выполняется в фоне с четырьмя работниками и объединяет одновременные запросы. Готовые immutable-ресурсы предыдущего полного кэша переиспользуются. Признак полноты записывается только после успеха всех ресурсов; при отказе следующий обычный вход допускает новую попытку. Ключ кэша содержит scope, build ID и runtime. До полной B offline использует последнюю полную A своего scope; чужие кэши не затрагиваются. Для навигационного HTML неизменяемой сборки query/hash не участвуют в cache lookup, но сохраняются в адресе; для остальных ресурсов сравнивается полный URL. При отсутствии сети доступна ранее полностью закэшированная сборка с тем же постоянным адресом. Чужие кэши, localStorage и IndexedDB не очищаются.

Открытая вкладка не перезагружается принудительно: пользователь может закончить работу и сохранить изменения. Следующее обычное открытие постоянного адреса должно получать новую версию до начала работы. Активация нового worker через `skipWaiting()`/`clients.claim()` не заменяет уже исполняемый JS; массовый `clients.navigate()` не доказывает безопасность для несохранённых черновиков. Новый worker не может предполагать, что старая страница поддерживает новый протокол готовности/сохранения.

**Известное ограничение миграции:** локальная fixture со старой плоской 4.0.19, её worker и HTTP `max-age=1728000` показала 4.0.19 при первом открытии после передачи новой сборки; 4.0.20 появилась только после следующего обычного reload. Сохранённый маркер данных остался. Это `FAIL` строгой первой навигации, даже если прежний эксперимент помечен `PASS_WITH_INITIAL_MIGRATION_LIMIT`. Одинаковый общий загрузчик между A/B сам по себе не является причиной; замена имени загрузчика в новом HTML не исправляет старый HTML, который браузер ещё использует из кэша. Матрица, по которой нужно проверять последующие исправления, — [TESTING.md](TESTING.md#приёмка-обновления-ucoz).

Нельзя обещать универсальное выполнение первой миграции одними новыми файлами, пока старый worker/HTTP-кэш не дал браузеру получить новый код. Нужно установить конкретную цепочку запросов и доступные меры хостинга. После загрузки проверьте HTTP-ответы uCoz, отсутствие login/HTML-заглушек вместо JS/JSON и доступность Service Worker с JavaScript Content-Type. `release.json`, входной HTML и worker желательно отдавать с `Cache-Control: no-cache`; для неизменяемых `releases` подходит длительное кэширование. Новые заголовки не отменяют немедленно прежний свежий HTTP-кэш. Meta-теги HTML не заменяют HTTP-заголовки. Не рассчитывайте на `.htaccess`, PHP или управление заголовками, пока хостинг этого не подтвердил. `updateViaCache: "none"` относится к worker-скриптам, а не автоматически ко всем HTML/JS.

HTTP-кэш, Service Worker CacheStorage и серверный/CDN-кэш — разные уровни. Основания: [MDN: Request.cache](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache), [MDN: updateViaCache](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/updateViaCache), [MDN: HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).

5. Создай новые каталоги сверху вниз. Передай всю новую неизменяемую release-папку. Для каждого вызова проверяй фактический ответ MCP, включая текст ошибки даже при отсутствии `isError`. Сохраняй прогресс по конкретным файлам; общий exit code оболочки не доказывает успешность всех передач. При таймауте сначала прочитай целевой каталог/файл и установи, дошёл ли файл полностью. Допустим ограниченный повтор только отсутствующего/неполного файла после такой проверки; повторяющийся отказ сети — конкретный блокер, а не повод бесконечно перезаливать всё.
6. До переключения сверь каждый intended path и размер с FTP и байты/SHA-256 через свежие HTTPS-ответы. Код HTTP 200 сам по себе не доказывает правильный файл: исключи HTML login/error-заглушки вместо JS/CSS/JSON и проверь Content-Type. При разрешённом независимом чтении можно пакетировать проверки; запись указателя и зависимые шаги выполняй последовательно. Неполная release-папка никогда не становится активной.
7. Передай совместимые корневые loader/index/manifest, затем worker. `release.json` — последним после успешной проверки всей сборки. Если сервер поддерживает замену rename, сначала загрузи временный JSON в этот же каталог, проверь его и переименуй; саму возможность замены существующего файла через rename установи фактически. При отказе не удаляй старый указатель. Для первой миграции предусмотри отсутствие предыдущего release.json: откат возвращает исходный корневой HTML/manifest/worker, а не выдуманный указатель.
8. Выполни [матрицу приёмки](TESTING.md#приёмка-обновления-ucoz) на настоящем HTTPS в отдельном профиле с искусственной заметкой/задачей. Прогрей A до передачи B; сохрани профиль внутри перехода. Для каждого первого открытия запиши первоначальный и конечный URL, версию/build ID, запросы и сохранность данных. Уже открытая вкладка с черновиком остаётся нетронутой. `FAIL` первой legacy-навигации не стирай следующей успешной загрузкой. FTP/MCP-передача не доказывает загрузку через UI файлового менеджера; установленная PWA и браузеры, которые не запускались, остаются `NOT_VERIFIED`.
9. При подтверждённо неработоспособной активной публикации верни сохранённый указатель или исходные корневые файлы из backup и проверь результат; не откатывай формат пользовательских данных и не удаляй браузерные базы. При рабочем результате, который пользователь поручил оставить, сохрани его активным и явно сообщи оставшиеся ограничения. Прежние release-папки сохраняй для открытых вкладок и отката. Тестовые файлы перечисли в отчёте; облачное удаление выполняй только в разрешённых границах и с соблюдением требований инструмента.
10. Финал: активная версия/build ID, постоянный публичный адрес, ZIP и SHA-256, место backup/карты загрузки, точные `VERIFIED`, `FAIL`, `NOT_VERIFIED`, что оставлено на сервере и что нужно прислать при ошибке. Публикация на uCoz не разрешает коммит или GitHub push.

## Сборка через веб-версию ChatGPT

Прикрепите ZIP актуального проекта и скопируйте целиком корневой [UCOZ_BUILD_PROMPT.md](../UCOZ_BUILD_PROMPT.md). Если в архиве есть штатный сборщик, инструкция требует использовать его, а не заново менять архитектуру приложения.
