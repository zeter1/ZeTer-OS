# Проверка ZeTer OS

Это единственный источник команд, постоянных smoke-тестов и ручных сценариев. Начинай с узкой проверки; после структурного JS/CSS-, resource-, data-, bridge-, docs- или checker-изменения выполняй полный strict-check.

## Безопасность запуска проверок

`tools/smoke_mobile_polish_ui.js#runMobilePolishSmoke({chromium,startPreview,outputDir})` — явная браузерная проверка, импорт инертен. Только allowlisted preview `app/`, новый touch context с искусственными материалами и двумя столами, без native API, внешней сети и service worker. Проверяет список столов из шапки, галочку текущего, длинные literal-названия, Escape/фокус и закрытие снаружи; заголовки меню материалов desktop/Проводника; «Ещё», TXT и копию, текст → смена стола → возврат → reload. Размеры 320/390/430 и 844×390; при 1440×900 доступны все прежние кнопки редактора. Артефакты — `work/mobile-polish-qa/`. Реальный телефон, экранная клавиатура, PWA/EXE и публикация проверяются отдельно.

Мобильный рабочий стол: `runMobileSmoke` дополнительно проверяет маленькую кнопку «＋» в шапке, скрытие при открытом окне и возврат через «Домой», отдельное меню ярлыка без открытия материала, область нажатия 44×44 px при видимом значке 24×24 px на левом верхнем углу, выравнивание подписи под значком на 320/360/390/430/844 px. Искусственный второй стол проверяет длинное название в шапке, создание папки именно на выбранном столе, reload и сохранность соседнего стола. Артефакты этой проходки — `work/mobile-desktop-qa/`; телефон/PWA и реальная клавиатура проверяются отдельно.

Мобильная панель задач: `tools/smoke_taskbar_overflow_ui.js#runTaskbarOverflowSmoke({chromium,startPreview,outputDir})` — явный browser check, импорт инертен. Только public preview `app/`, отдельный touch context и искусственный state, без native API/сети/service worker. Проверяет появление кнопки при переполнении, все закреплённые приложения и отдельные окна одного приложения, запуск и возврат свёрнутого окна, Escape/фокус и закрытие снаружи, перенос единственного колокольчика/счётчика вверх и обратно на desktop, переходы 390→430→390→844→320, исчезновение кнопки после открепления. Артефакты — `work/taskbar-overflow-qa/`. Настоящий телефон/PWA/production — отдельные проверки.

Телефоны: `tools/smoke_mobile_ui.js#runMobileSmoke({chromium,startPreview,outputDir})` — явная браузерная проверка через Playwright runner; импорт инертен. Только public preview `app/`, новые touch/mouse contexts, искусственные данные; внешняя сеть, native API и service worker исключены. Проверяются 320×568, 390×844, 430×932, 844×390: автоматический режим, меню вниз, поиск только по вызову, границы окон семи системных приложений, касание/удержание/свайп, отпускание удержания без выполнения команды, прокрутка календаря без изменения события, папка → файл, Домой → возврат окна, поворот, короткий viewport, reload и сохранность исходных координат/текста. Отдельный mouse context 1440×900 проверяет настольные панели. Артефакты по умолчанию — `work/mobile-qa/`. Дополнительно на настоящем Android/iPhone проверить адрес сайта, браузерные панели/safe-area, экранную клавиатуру, редактирование последнего поля и сохранение; эмуляция touch и короткого viewport не доказывает аппаратную клавиатуру, установленную PWA или публикацию на uCoz.

Контакты: `node tools/smoke_contacts.js` проверяет модель, произвольные повторяемые поля, поиск, CRUD и отказ → повтор на VM fixtures. `node tools/smoke_contacts_integration.js` проверяет defaults/миграцию, проверку импортов и архивов, полный ZIP round-trip, снимок одного стола, remap восстановления и выборочное удаление. Оба теста без startup/native и реальных `data/`, входят в suite. Браузерная приёмка: проекты слева, категории только внутри проекта; создать контакт с несколькими телефонами/email, своим полем и описанием, найти по полям и цифрам телефона, изменить/перенести, избранное/copy, отмена удаления, отказ → повтор, два окна, другой стол, reload; широкое и узкое окно, клавиатура и контраст. Native/EXE и настоящий clipboard проверяются отдельно.

`tools/smoke_contacts_ui.js#runContactsSmoke({chromium,startPreview,outputDir})` — явная браузерная проверка через Playwright runner; импорт инертен. Public preview только `app/`, отдельный Chromium context с искусственными данными, service worker и внешняя сеть заблокированы. Используется настоящая primary queue с управляемыми отказом/задержкой записи и clipboard double. Проверяются повторяемые поля, поиск, перенос/удаление, отказ → повтор, два окна с незавершённой записью и черновиком, reload и независимость столов; контейнеры 1400/760/460/320 px и viewport 390 px. Результаты и fingerprints текущего интерфейса с выпадающими категориями — `work/contacts-qa/dropdown/`; прежняя компоновка — `expanded/`. Первые отказы запуска среды сохранены отдельно в `first/` и `browser-first/`; первый успешный набор — `functional-first/`. Проверка браузера не доказывает native/EXE, настоящий clipboard и опубликованную PWA.

`tools/smoke_contacts_edges_ui.js#runContactsEdgesSmoke({chromium,startPreview,outputDir})` — восемь независимых браузерных сценариев на настоящих Contacts DOM/controller и primary queue с искусственным состоянием. Импорт инертен; отдельный context на сценарий, public allowlist, без app startup/native, реального хранилища, service worker и внешней сети. Проверяются конфликт старого редактора с другим окном, выбранный контакт за первой страницей и его фактическая видимость/пагинация, низкое окно 390×340, скопированные дефисы в телефоне, удалённый проект при открытом редакторе, отказ удаления → повтор, дубликат названия → исправление и HTML/clipboard error. Модель отдельно проверяет конфликт после transaction barrier. Артефакты прохода — `work/contacts-bugs-qa/`: исходные четыре FAIL — `edges-before/`, дополнительный FAIL фактической видимости строки — `selected-visibility-before/`, полный PASS — `edges-final-expanded/`; базовая матрица после исправлений — `general-final/`. Первые browser-launch отказы среды сохранены в `baseline/` и `baseline-browser/`. Настоящий clipboard, pywebview/EXE и опубликованный сайт проверяются отдельно.

Последующий проход поиска расширяет браузерную матрицу до 35 сценариев: Пуск при ограничениях проекта/дат, исчезнувший проект при смене стола/удалении, настоящее восстановление папки с потомком и отложенное открытие при удалении материала/смене стола, включая события с одинаковыми ID. VM-проверки воспроизводят настоящий restore и отмену delayed navigator. Артефакты — `work/search-followup-qa/verified/`. В `first/` сохранён исходный отказ теста: отсутствующая история давала `undefined` вместо ожидаемого `false`; остановка сценария оставляла область «Все столы» для двух зависимых проверок. Исправлено ожидание теста, затем пройдена вся матрица.

Поиск: `node tools/smoke_search_ui.js`, `smoke_search_index.js`, `smoke_search_controller.js`, `smoke_search_actions.js` и `smoke_search_settings.js` в `tools/` — VM fixtures без app startup/native/data, входят в suite. Проверяются SVG/escaping, collector/index/cache/update/delete, scoped ID, фильтры/исправления, history refusal/rollback/retry, shared lock и staged выполнение задачи. `tools/smoke_search_upgrade_browser.js#runSearchUpgradeSmoke({chromium,startPreview,outputDir})` — явная браузерная проверка; прежний `smoke_search_browser.js#runSearchSmoke` делегирует ей. Импорт ничего не запускает. Только public preview app, отдельный Chromium context, synthetic state, заблокированные service worker/внешняя сеть; clipboard — управляемый double. Проверяются все типы/preview/actions, текущий/все столы и ID collisions, исправления, фильтры/даты, история/reload/очистка, exact prompt/time переход, index reuse/rename/delete/transaction ACK, отказ complete→retry, Пуск/taskbar/отдельный поиск, 1440/760/390/320 px и высота 320 px, контраст и текст 150%. JSON содержит fingerprint источников. Артефакты — `work/search-upgrade-qa/`; initial FAIL сохранён в `first/`, первый полный PASS — `expanded/`. Native/EXE, настоящий clipboard и опубликованный сайт этим не подтверждаются. Полоса — 36 px, кнопки — 26 px с видимыми границами; все восемь команд открываются, включая «Руководство пользователя». Проверка браузера не подтверждает установленный EXE.

Прямая веб-публикация: `node tools/smoke_web_cache.js` исполняет настоящий worker в VM с искусственными сетью/кэшами, без app startup и пользовательского state. Проверяет complete marker, неполную/повреждённую передачу, обычную навигацию A→B, привязку вкладок после перезапуска worker, offline, чужой cache и path traversal. `python -B tools/prepare_web.py` только сверяет generated `app/web-release.json`; `--write` изменяет только этот manifest, не данные и не сайт. Проверка входит в strict.

`tools/smoke_web_cache_ui.js#runWebCacheSmoke({chromium,outputDir})` — явный Playwright-тест. Импорт ничего не запускает. Только 127.0.0.1 и файлы из generated manifest в памяти; сервер имитирует длительный HTTP-кэш и прерванную передачу. Chromium запускается с sandbox в отдельных browser contexts; собственный localStorage/IndexedDB sentinel и чужой cache искусственные. Проверяются первый запуск, query/hash, новый посетитель во время upload без app startup, HTML-заглушка вместо JS, обычный F5 A→B, сохранность соседнего черновика/позднего запроса A, offline B и 390px. Снимки и JSON — `work/web-cache-qa/`. Native/EXE, реальные данные, uCoz, Firefox и установленная PWA этим не подтверждаются.

Прежние UI-тесты с заблокированным Service Worker используют явный `window.__ZETER_UI_PREVIEW__ = true` через `context.addInitScript` **только на localhost/127.0.0.1**. Это обход веб-gate для подмены отдельных скриптов синтетическими fixtures; он не доказывает целостность веб-публикации. Не включайте его в проверке самого кэша.

Реальные DOM rect/CSS проверяют подписи 14 px/2 строки без перекрытий; Ctrl-click не открывает элемент, double sequence в single режиме открывает ровно одно окно. Проверяются 12h/секунды/дата и Sunday calendar. Окна 850/560/374/304 px — внутри широкого viewport, отдельно viewport 390/320 px, текст 150%, крупные контролы и контраст. `tools/smoke_settings_edges_ui.js#runSettingsEdgesSmoke({chromium,startPreview,outputDir})` — явная браузерная проверка гонок; импорт ничего не запускает. Каждый сценарий имеет отдельный Chromium context, synthetic state, заблокированные внешнюю сеть и service worker, allowlisted public preview и управляемую подготовку изображения. Проверяются upload → новый фон, upload → reset, cancel → reopen → поздний результат, обратный порядок двух загрузок, reopen → ошибка декодирования и discard при pending image. Отменённые/устаревшие операции не должны применять результат или оставлять processing; при выборе фона/reset новый файл остаётся доступен. Native API/реальные data не вызываются. Все команды ниже выполняются из корня репозитория. Перед import, startup, smoke или build прочитай entrypoint и достижимые startup-действия: имя `--help`, dry-run или test не доказывает отсутствие записи.

| Граница | Что установить до выполнения |
|---|---|
| Python import и создание API | У launcher начальные пути вычисляются от `__file__`, а конструктор `NativeStorageApi` создаёт каталоги, backup и производные копии. Сначала перенаправь все state-пути, затем создавай API |
| Native storage smoke | Переиспользуй `configure_temp_data(root)` и `RecordingPlatformOpener` из `tools/smoke_managed_file_native.py`; вызывай конфигурацию до конструктора. Для автозапуска/обновлений используй предусмотренные в профильном тесте doubles, без реального registry, opener или сети |
| Browser/PWA | Используй отдельный тестовый browser context с искусственным состоянием. IndexedDB/localStorage/service worker принадлежат origin/profile; новый cwd и запущенный HTTP-сервер их не очищают и не изолируют |
| Updater/release smokes | Они создают искусственные дистрибутивы; updater/feed используют собственные каталоги под `work/` и подменённый HTTP. Не заменяй fake client реальной загрузкой и не передавай тесту каталог работающей установки |
| EXE build и установка | Проверь выходные пути по [BUILD_EXE.md](../BUILD_EXE.md) и [UPDATES.md](UPDATES.md). Сборка артефакта, запуск его окна и замена установленной копии — отдельные проверки |

TEMP/TMP управляют только временными файлами; cwd, worktree и TEMP не перенаправляют основной state автоматически. При новом тесте проследи resolved paths до записи/cleanup и проверь, что они лежат внутри искусственной fixture. После проверки сверь ожидаемые байты/состояние, а не только код завершения. Если изоляция не установлена, продолжи чтением/статической проверкой и явно укажи непроверенную границу.

При недоступной системной TEMP можно задать процессу проверки отдельный каталог под игнорируемым `work/`. Из корня, после preflight:

```powershell
$env:ZETER_PYTHON = (Get-Command python -ErrorAction Stop).Source
$env:ZETER_NODE = (Get-Command node -ErrorAction Stop).Source
$env:PYTHONIOENCODING = 'utf-8'
$checkTemp = Join-Path (Get-Location) 'work/check-temp'
New-Item -ItemType Directory -Force -Path $checkTemp | Out-Null
$env:TEMP = $checkTemp
$env:TMP = $checkTemp
```

Переменные действуют в текущем shell; если команд нет в PATH, подставь фактические пути установленных executable. Не сохраняй пути конкретного компьютера в документацию. Updater-smoke на Windows создаёт тестовый junction: запрет `mklink /J` — отдельный отказ среды, который не исчезает от смены TEMP. Сохрани первый результат, проверь точную запрещённую операцию; допустим только тот же ограниченный тест в разрешённой среде, без ослабления проверок и произвольных повторов.

### Google Drive и синхронизация

Регрессии 4.0.96: runtime smoke проверяет скрытие сохранённого конфликта при отключённом аккаунте и отказ устаревших кнопок; sync smoke — сохранённый конфликт → подтверждённый пустой head → первая публикация без удаления прежних immutable объектов. UI smoke дополнительно проверяет конфликт → отключение → отсутствие предупреждения → повторное подключение → актуальный конфликт, затем отказ primary ACK → явный повтор.

Регрессии 4.0.95: `node tools/smoke_export_runtime.js` проверяет неизменённые editor/markdown/table/sticky без повторной записи и захват реального изменения один раз. `node tools/smoke_google_drive_sync.js` проверяет отсутствие повторного скачивания payload при подтверждённом неизменном head, явную и периодическую полную проверку, конкурентный commit → выбор локальной версии → получение победителя другим устройством. `node tools/smoke_google_drive_runtime.js` проверяет завершение фонового конфликта без ручного refresh и отказ страховочной копии с выходом из статуса загрузки. Все три используют искусственные данные и транспорт.

Серверные тесты отдельно проверяют поддерживаемый Workers режим `redirect:manual` у всех трёх Google-запросов: ответы 3xx не пересылают credentials или `Location` и не создают сессию. Коды `google_client_configuration`, `google_response_invalid`, `google_unavailable` не содержат upstream-описаний; только подтверждённый `401 reconnect_required` меняет состояние подключения. `node tools/smoke_google_drive_sync.js` использует два искусственных устройства и fake Drive/CAS. Проверяет компьютер → телефон → компьютер, отсутствие byte uploads без изменений, отдельную загрузку state, сохранность прежнего payload, first/concurrent conflict, отказ применения → повтор, post-remap baseline и восстановление после потери commit-response. Дополнительно проверяются семь потерянных ответов POST с перезапуском, сохранённый до отправки uploadIntent, отказ ACK без облачных записей, явное подтверждение входящей версии, устаревшее уведомление, изменение локальных данных, отмена во время ACK/вычисления хеша и смена head во время сбора данных. Удалённый корень проверяется с принятым head и без него: полная повторная отправка локальных данных, прежнее поколение до CAS, потеря ответа резервации/файла/манифеста, перезапуск и отказ ACK без облачных записей. Все файлы находятся в `tools/`. `run_smokes.js` последовательно запускает только зарегистрированные в его `smokeFiles` JavaScript-файлы; Python-smokes запускаются отдельно checker-ом. Новый файл не подхватывается автоматически. Одноразовый тест не сохраняй; постоянный риск добавляй в профильный smoke либо в отдельный небольшой smoke с регистрацией в runner/checker.

Дополнительно native-smoke проверяет исчезновение backup во время подсчёта размеров, видимость других ошибок доступа, пропуск неизменных DOCX с разными ZIP-датами, изменённые XML/изображения, extra/duplicate ZIP entries, восстановление повреждённого/неподдерживаемого target, сохранность основной записи и прежнего DOCX при отказе замены, точность контекста удаления старого файла. Problem-log smoke проверяет parent/root-корреляцию, поздний успех после sampling, `archiveOk`, slow-контекст, первоначальную identity при смене дня и drift, неполные исходники, mocked frozen hash, сохранность legacy incomplete и публикацию сводки при максимальном контексте. Эти проверки используют только искусственные данные; реальный установленный EXE ими не проверяется.

При запрете записи в системный TEMP задай `TEMP` и `TMP` процессу проверки на отдельный доступный каталог внутри игнорируемого `work/`. Это перенаправляет тестовые TemporaryDirectory; native state по-прежнему перенаправляется через `configure_temp_data` до конструктора API. Если Windows `py` не находит Python, задай `ZETER_PYTHON` по фактическому пути существующего интерпретатора. Первый отказ окружения сохраняется как отдельный результат, а не объявляется продуктовым багом.

Для узкого smoke используй минимальные заглушки реальных зависимостей и проверь успех, пустой/граничный ввод, ожидаемую мутацию, error/fallback и callback-порядок action flow.

Strict-check запускает documentation, native managed-file, desktop backup, updater, update feed, problem-log и release-builder smokes отдельными Python-процессами через тот же интерпретатор, которым запущен checker. `smoke_documentation.py` проверяет отсутствующий/повторный/кириллический Markdown-якорь, исключение заголовков из code-fence, URL-encoding, границу project root и Python-поиск через AST без исполнения модуля. Регистрация и таймауты принадлежат `tools/check_project.py`: ненулевой код завершения или timeout считается общей ошибкой проверки.

## Воспроизводимая UI-проверка

### Подготовка отдельной native-копии

Обычный запуск launcher из корня использует настоящую `data/`. Для UI-теста сначала подготовь чистую копию из текущих исходников через существующий `tools/build_release.py`. Он собирает только разрешённые runtime-файлы, проверяет состав и байты ZIP; пользовательские данные и созданные журналы не входят. Это ZIP Python-исходников, не EXE и не пакет обновления.

Из корня репозитория, с уже установленным Python и зависимостями проекта:

```powershell
$ErrorActionPreference = 'Stop'
$uiRoot = Join-Path (Get-Location).Path ('work/ui-checks/native-' + [guid]::NewGuid().ToString('N'))
if (Test-Path -LiteralPath $uiRoot) { throw 'Каталог проверки уже существует' }
$archiveDir = Join-Path $uiRoot 'archive'
python -B tools/build_release.py --output-dir $archiveDir
if ($LASTEXITCODE -ne 0) { throw 'Чистая копия не собрана' }
$archives = @(Get-ChildItem -LiteralPath $archiveDir -Filter '*.zip' -File)
if ($archives.Count -ne 1) { throw 'Ожидался один проверенный ZIP' }
$runtimeDir = Join-Path $uiRoot 'runtime'
if (Test-Path -LiteralPath $runtimeDir) { throw 'Цель распаковки уже существует' }
Expand-Archive -LiteralPath $archives[0].FullName -DestinationPath $runtimeDir
$appRoot = Join-Path $runtimeDir 'ZeTer OS'
$launcher = Join-Path $appRoot 'run_zeter_os.py'
$fixtureData = Join-Path $appRoot 'data'
if (!(Test-Path -LiteralPath $launcher -PathType Leaf)) { throw 'Launcher отсутствует' }
if (Test-Path -LiteralPath $fixtureData) { throw 'Копия уже содержит данные: остановись и проверь происхождение' }
Write-Output "Launcher: $launcher"
Write-Output "Тестовые данные: $fixtureData"
Write-Output ('Логи: ' + (Join-Path $appRoot 'Логи проблем'))
```

Зафиксируй напечатанные source/target-пути. Рецепт не запускает приложение и не перезаписывает существующую установку: новый GUID даёт отдельные каталоги архива и распаковки, состав source→target задаёт проверенный ZIP. До первого GUI-запуска прочитай startup текущего launcher и сверь `BASE_DIR`/`DATA_DIR`: в source-режиме они вычисляются от файла этой копии. Не переноси настоящую `data/` и не используй пользовательский backup как фикстуру.

Запускай **только этот** `$launcher` командой `python -B $launcher`, вручную создай искусственные объекты, затем сверь путь данных в настройках с `$fixtureData`. Закрой копию и повтори ту же команду для save → reload. Source-копия не устанавливает бинарные обновления, но внешние действия остаются внешними: не включай автозапуск Windows, не выбирай реальную папку данных/экспорта и не открывай внешние цели ради обычного UI-теста. Для этих границ используй doubles профильного smoke или отдельную явно разрешённую проверку.

Сохрани сценарий и снимки под `$uiRoot`; копию не удаляй автоматически при FAIL. Такой тест подтверждает Python/source + pywebview, но не установленный EXE. Browser context готовь отдельно: его IndexedDB и профиль не изолируются этим ZIP.

### Выполнение сценария

1. Запиши сценарий, режим `native`/`browser`, версию и ожидаемый результат.
2. Для native используй launcher подготовленной выше копии; до теста сверь активный путь данных. Базовый размер окна — `1320×840`, узкий — минимальный `1024×640`.
3. Открой изменённый сценарий с обычными данными, пустым состоянием, длинным русским текстом и большим списком.
4. Проверь mouse, keyboard, touch-поведение при наличии, hover/focus/active/disabled, loading/error, scroll, clipping, overlap и z-index.
5. Если данные сохраняются, закрой приложение, запусти снова и повторно открой объект.
6. Для browser/PWA при необходимости запусти из корня `python -m http.server 8000 --bind 127.0.0.1 --directory app` и открой `http://127.0.0.1:8000/` в отдельном тестовом context; не используй реальные native-данные как фикстуру.
7. Сохраняй временные снимки как `work/ui-checks/YYYY-MM-DD/сценарий-normal.png` и `сценарий-narrow.png`. Папка игнорируется Git.

Если GUI не открывался, передай эти шаги как непроверенные, а не как пройденные.

Категории автоматизаций: создать две категории → назначить им разные правила → запустить правила → выбрать каждую категорию и сверить её список/историю/сводку. Переименовать категорию и повторить после перезапуска. Удаление отменить, затем проверить отдельно удаление только категории и удаление с правилами: чужие правила, файлы/заметки и история должны сохраниться; ожидающие запуски удалённых правил — отмениться. При отказе сохранения весь набор возвращается к прежнему состоянию. Проверить изоляцию рабочих пространств и round-trip импорта. Для файлового примера выбрать заметку → «Проверить автоматизацию» → результат остаётся, выбор пуст, действия не выполнены; повторная проверка недоступна до нового выбора. Проверить оба пути: редактор и проверка сохранённого правила.

Для выбора файла в автоматизациях отдельно проверь на обычной и узкой ширине: рабочий стол с пользовательским названием подписан именно как рабочий стол; файлы из подпапок не показаны при выборе его корня, но видны при «Любая папка ZeTer OS». Выбери заметку в подпапке: «Открыть заметку» открывает её, «Открыть папку объекта» — её родителя, не рабочий стол. Удали пример и убедись, что переход не подменяется другим объектом. Сменив триггер с файла на событие и обратно, проверь соответствующие пояснения переменных и пример подстановки, включая `{file.name}` для заметки в файловом триггере.

## Приёмка обновления uCoz

Профильный `python -B tools/smoke_ucoz_builder.py` также исполняет настоящий worker через `smoke_ucoz_runtime.js`: удержанный ресурс не блокирует активацию; параллельные навигации объединяют precache; отказ не создаёт признак полноты; offline до полного B использует полную A своего scope; служебный патч повторно использует готовые immutable-ресурсы. Проверяются runtime-only состав, неизменность ZIP, неверные metadata/пути и конкурирующий выходной комплект.

Для runtime r2: прогреть A → сохранить искусственные данные и черновик в соседней вкладке → удержать необязательный ресурс B → передать только worker → записать `updatefound/statechange` и `ZETER_UCOZ_RUNTIME_STATUS`. Активация должна завершиться до полного precache; следующая обычная навигация открывает B без Ctrl+F5, ручного `registration.update()` и очистки данных. Затем offline до полноты → A, сеть/полный precache → offline B. Это отдельная проверка от самой первой legacy-навигации ниже: её первый FAIL сохраняется.

Конечный `location.href` обязан оставаться `https://dkoles.com/zeteros/index.html` после первого открытия и обычного reload. Актуальная версия по адресу `releases/...` не проходит приёмку. `document.baseURI` и JS/CSS/изображения при этом относятся к одной immutable release-папке; root Service Worker сохраняет правильные URL/scope. Проверь entry bootstrap до остальных ресурсов, same-origin base/CSP, query/hash/history.state и offline-ссылку с query после полного precache. Не очищай storage/кэши и не перезагружай чужие вкладки.

Публичный вход всегда один: `https://dkoles.com/zeteros/index.html`, без query. Локальная fixture повторяет `/portfolio/ZeTerOS/index.html` на своём origin. После полной публикации B **первое** обычное открытие этого адреса должно показать B до начала редактирования. Автоматический переход внутри загрузки допустим; дополнительный пользовательский reload, специальная ссылка, Ctrl+F5, очистка данных или прерывание другой рабочей вкладки означают `FAIL` критерия.

Перед запуском прочитай `tools/build_ucoz.py` и `tools/smoke_ucoz_builder.py`: штатная упаковка читает `app`, пишет отдельный ZIP и не импортирует приложение; smoke использует искусственные fixtures. Для браузера — отдельный context с искусственными данными. Внутри каждого A→B сохраняй один origin/profile, HTTP/SW-кэши и регистрацию worker. Новый context между A и B, DevTools Disable cache и unregister скрывают проверяемый дефект.

1. Собери A/B с разными build ID в отдельных выходных каталогах. Сверь состав ZIP/CRC, отсутствие лишнего верхнего каталога и приватных файлов, пути uCoz, локальные HTML/CSS/manifest-ссылки и динамические ссылки JS. Проверь байты JS/CSS и исходный порядок скриптов с учётом только явно необходимых преобразований PWA. Распакуй архив и сравни байты с подготовленной копией; повторная упаковка из тех же исходников/шаблонов должна быть воспроизводима.
2. Запусти HTTP-fixture, открой A, дождись готовности интерфейса и worker, прогрей обычные HTTP/SW-кэши. Создай тестовые задачу/заметку и настройки, запиши ID и содержимое. Проверь «Пуск», окна/панель задач, уведомления, настройки и сохранение после reload; отсутствие ошибок HTML ещё не доказывает работу UI.
3. Передай целиком неизменяемую B, проверь каждый файл, затем корневые файлы и `release.json` последним. Выполни сценарии ниже. Для каждой первой навигации запиши первоначальный URL, HTTP-заголовки fixture/сервера, document/loader/metadata/worker-запросы и controller/update-события, конечный build ID, URL загруженных JS/CSS, отсутствие двойной инициализации и сохранность данных.

| Изолированный сценарий | Обязательное наблюдение |
|---|---|
| Чистый посетитель | Первое открытие прежнего URL получает B |
| Прежняя плоская публикация с исходным worker | Прогреть настоящую прежнюю схему A; после публикации первое открытие прежнего URL получает B. Не заменять двумя сборками нового формата |
| Предыдущая сборка новой схемы | Прогреть A; первое открытие прежнего URL и отдельно обычный reload страницы A получают B |
| Свежий HTTP-кэш HTML/загрузчика | Повторить переход с `Cache-Control: max-age=1728000` (20 дней); без принудительного сброса кэша. Это стресс-fixture, не утверждение о сегодняшних заголовках uCoz |
| Изменение логики загрузчика | Между A/B действительно изменить проверяемую логику и доказать выполнение B; новый `src` в ещё не полученном HTML недостаточен |
| Две вкладки | Рабочая A с несохранённым черновиком не перезагружается и сохраняет черновик; новое первое открытие прежнего URL получает B |
| Передача B не завершена | Пока указатель прежний, A работает; при ошибочной metadata=B и отказе B/index.html доступная полная A сохраняется, без redirect-loop и ложного заявления об обновлении |
| Offline после завершённого precache | Открывается целая ранее закэшированная сборка, данные доступны, циклов нет; старая offline-версия не выдаётся за новую |

Локальная legacy-fixture уже воспроизвела первый вход 4.0.19 → следующий обычный reload 4.0.20 при сохранённом маркере (`work/ucoz-browser/legacy-test.cjs`, `legacy-result.json`, если локальные артефакты сохранены). Метка старого опыта `PASS_WITH_INITIAL_MIGRATION_LIMIT` по текущему критерию означает `FAIL` первой навигации. Это свидетельство конкретного перехода, а не автоматический результат будущей сборки. Последующий PASS не стирает исходный FAIL; новый фикс требует новой проверки этой же границы.

Не считать `skipWaiting()`/`clients.claim()`, новый cache name или успешную регистрацию worker доказательством новой страницы. Не исправлять первую навигацию массовым `clients.navigate()`: старые страницы могут не иметь сигнала готовности или сохранённости. Новый заголовок `no-cache` не отменяет уже свежий HTTP-кэш у посетителя.

Публичный HTTPS uCoz проверяется отдельно от локального HTTP: реальные ответы/Content-Type и отсутствие HTML/login-заглушек вместо JS/JSON, worker/scope, прежний URL, первый прогретый переход, сохранность данных и соседняя рабочая вкладка. Если фактический хостинг недоступен, результат `NOT_VERIFIED`; воспроизведённая старая A на первом открытии — `FAIL`. Установленная PWA и загрузка файлов через UI также имеют отдельные границы; успешный FTP/API-вызов не доказывает UI-загрузку.

Отчёт по каждой строке: сценарий → `PASS`/`FAIL`/`NOT_VERIFIED` → конкретное доказательство → следующий шаг. Для результата ZIP приложи версию, build ID, SHA-256, число файлов, источник сборщика/шаблонов и воспроизводимую команду. При сбое нужны первоначальный URL, версии/build ID A/B, последовательность первых запросов, HTTP-статусы/заголовки, консоль и публичный `release.json`, без паролей и личного содержимого документов. Не выдавай кандидат с проваленной первой навигацией за полностью готовую публикацию.

## Ручная матрица

Обновление EXE из GitHub Releases: использовать две отдельные сборки A/B с разными версиями и искусственными данными/контрольными файлами. При обнаружении B сверить запись в центре уведомлений и предложение около «О ZeTer OS», «Позже», ручную проверку и повтор без дубликатов; в обоих уведомлениях «Что нового» открывает точный GitHub CHANGELOG, «Обновить вручную» — окно с шестью шагами, ссылками на репозиторий/Releases и переносом длинных имён на узкой ширине. Проверить загрузку/отмену, отказ сохранения без закрытия, двойное нажатие, SHA/ZIP/manifest, изменённый файл программы, конфликт с чужим файлом, настоящий junction, сбой посреди замены и восстановление без staging. Для успеха сверить контрольные суммы установленных файлов, изолированную WebView2-проверку/nonce, commit и точный новый процесс после обычного перезапуска; при отказе проверки старые файлы и контрольные данные сохраняются. Source/PWA не устанавливают EXE. Полный smoke создаёт только собственные fixtures в `work/update-tests`; Windows sandbox может запрещать `mklink /J`, это отдельный environment FAIL и требует того же ограниченного smoke вне sandbox. Подробности — [UPDATES.md](UPDATES.md).

В инструкции «Обновить вручную» проверить три текстовые ссылки внизу страницы и кнопки сверху. Выделить обычный текст и отдельно URL → щёлкнуть по выделенному левой кнопкой → «Копировать» → вставить и сверить пробелы/переносы. Повторить с ПКМ и Ctrl+C; щелчок вне выделения позволяет начать новое выделение. Проверить узкое окно и сообщение при отказе clipboard. Browser-проверка не подтверждает native clipboard и запуск внешнего браузера в Windows.

Канал Pages после публикации: сверить `updates.json` с реальным ZIP и версией EXE, затем в тестовой установке проверить равную версию → актуальная, новую → предложение без скачивания, 404/повреждённый JSON/offline → ошибка проверки. В сетевом наблюдении проверки должен быть только фиксированный Pages URL, после «Обновить» — прямая Release/CDN-ссылка; запросов к `api.github.com` быть не должно. Убедиться, что шестичасовой таймер и ручная кнопка не обходят Retry-After. Синтетические HTTP и статические проверки CI не доказывают работу Pages/Actions/CDN на настоящем GitHub.

Окно «О ZeTer OS»: открыть с верхней панели → сверить текущую версию, описание, «Что нового», «Обновления системы», «Репозиторий» и все контакты → выделить текст мышью → ПКМ → «Копировать» → вставить в тестовое поле; проверить также Ctrl+C. Проверить ссылки через внешнее открытие в browser/native, перенос длинных адресов и прокрутку при узком окне, закрытие/повторное открытие. В Настройках нет карточек «О системе» и «Разработчик». Проверка browser не подтверждает native clipboard и запуск внешнего браузера в Windows.

Для файлового правила выбрать «Файл для проверки»: проверить название/папку и переменные, смену файла и папки, пустой список → «Открыть папку» → добавить файл → «Обновить список». Создать черновики из всех пяти шаблонов, проверить поиск/фильтры и предупреждение о сломанной ссылке. Связать заметку с таблицей и событием, удалить только связь и убедиться, что объекты сохранены |

`smoke_desktop_group_drag.js` также проверяет реальные controllers создания/установки ярлыков: установить «Промпты» на первом столе → удалить ярлык → установить на втором столе с папкой «Промпты». Название ярлыка остаётся «Промпты», папка сохраняется; повторная установка блокируется, отдельные столы независимы, защита имён обычных файлов/папок остаётся прежней.

При перетаскивании на рабочем столе проверить папку, пользовательскую картинку и длинное название: за указателем движется сам значок исходного размера с сохранением точки захвата, без плашки. Для группы проверить все значки и их взаимное расположение. Проверить отпускание на свободном месте и в другую папку, отмену pointercancel без изменения координат, повторный захват без лишних копий и сохранение после reload; размеры окна 1507×911 и 980×720.

## Перед сдачей

При сохранении значка ярлыка переименовать его из другого окна: после завершения записи и перезапуска должны сохраниться новое имя и значок.

Настройка папки: загрузить значок и фон (PNG/JPG/GIF), во время подготовки попробовать сохранить; быстро выбрать другую картинку и убрать её до завершения старой обработки. Сохранить → перезапустить → открыть папку и её настройки; убрать оба изображения → сохранить → повторить открытие. Повреждённый GIF должен показать ошибку, сохранив прежний предпросмотр. На искусственном отказе primary-записи оформление других окон остаётся прежним, черновик доступен для повтора. При двух native asset-запросах отказ одного не разблокирует форму до завершения другого. Проверить обычное и узкое окно, длинное имя файла и скрытые file-input. Browser fixture не доказывает установленный EXE или live pywebview-диалог.

1. `node --check` изменённых JS и профильный smoke.
2. Поиск старых имён, дубликатов и всех затронутых selectors.
3. Generated docs: `--write`, затем `--check`.
4. Полный strict-check.
5. `git diff --check`, `git status --short`, `git diff --stat` и просмотр diff.
6. Фактический UI-сценарий либо точная передача непроверенных шагов.

В отчёте укажи команды, результаты, изменённые файлы, что проверено только по коду и оставшиеся риски.

## Промпты

`node tools/smoke_prompt_library.js` проверяет проекты и категории внутри проектов, точный текст без trim, CRUD, поиск, избранное, принадлежность категорий, независимость рабочих столов и откат при отказе записи. Import/ZIP и архив рабочего стола проверяются дополнительно профильными smoke.

Ручной сценарий: открыть «Промпты» из Пуска/Приложений, создать два проекта и категории с одинаковым названием в разных проектах; сохранить отдельные название и многострочный текст с пробелами. «Скопировать промпт» должен дать ровно текст, без названия и дополнительных строк. Проверить поиск, избранное, перенос между проектами, удаление категории с сохранением записей и удаление непустого проекта с переносом в общий раздел либо удалением всех его промптов. Проверить добавление без проектов, скрытый блок категорий, окно создания/переименования в стиле ZeTer OS, полную focus-обводку выбора проекта, эксклюзивные галочки, отмену/Escape/Tab/Enter, отказ записи с повтором и параллельным сохранением. Открыть второе окно, сохранить черновик при обновлении библиотеки, перезапустить и сверить данные. На другом рабочем столе библиотека пустая; удаление стола без выбранных групп сохраняет промпты в архиве, выбор prompts удаляет только эту группу. Проверить ширины 980px и 460px, штатную тёмную тему, клавиатуру, ошибку записи и копирования. При FAIL нужны точные шаги, видимая ошибка и console без личных текстов.

## Ссылки

`smoke_link_library.js` проверяет CRUD, порядок/удаление категорий с сохранением записей, избранное/поиск, Windows-дубли, unsafe targets/IDs, escaping, production import validator, настоящий ZIP/manifest round-trip всех библиотек и отказ сохранения → повтор без потери независимого state. Два synthetic workspace подтверждают изоляцию CRUD/favorite/category и switch перед очередью/во время сохранения. Migration-smoke проверяет старое состояние, однократный перенос legacy root в исходный стол и recovery при конфликте.

Ручная проверка: открыть Ссылки из Пуска/Приложений, добавить сайт, Windows-путь и внутренний объект; создать категорию из формы, переименовать/переставить/удалить, проверить избранное и поиск. В двух окнах проверить сохранение черновика и обновление списка одного стола, затем создать другой рабочий стол и подтвердить пустую отдельную библиотеку; добавить свою запись/категорию/избранное, перезапустить и проверить оба стола. Проверить 980px и 460px ширины, длинный адрес, клавиатурный focus, штатную тёмную тему. Проверить native открытие и executable confirmation отдельно; в браузере Windows-путь должен оставаться доступным для копирования. При FAIL приложить точные шаги, скриншот, текст видимой ошибки и browser console без личных адресов.

Адрес в карточке открывает ту же цель, что и «Открыть» (мышь/Enter/Space). Шестерёнка каждой категории показывает переименование, закрепление/открепление, порядок внутри своей группы и удаление; настройки не переключают выбранный фильтр. Проверить Escape с возвратом фокуса и щелчок снаружи; закрепление сверху → reload → открепление, сохранность черновика при действиях с другой категорией и возврат ссылок в «Без категории» при удалении. `smoke_link_library.js` проверяет pinned JSON/ZIP round-trip, invalid flag, отказ сохранения с откатом, разделение порядка и независимость рабочих столов. В узком окне форма и список прокручиваются целиком.

Булавка карточки закрепляет ссылку только в текущем разделе. Для каждой из четырёх групп (all/favorites/uncategorized/category) проверить подъём последней карточки, отсутствие pin в других разделах, query и reload; Space сохраняет фокус кнопки. Перенести запись, удалить категорию и снять избранное: pin исчезает только из раздела, в который запись больше не входит. JSON/ZIP/import, legacy-флаг и отказ сохранения проверяются отдельно.

Удаление рабочего стола: `smoke_state_migration.js` проверяет отмену, staged отказ→повтор, архивирование без переноса на основной стол, сохранность исходных ID/категорий/проектов/избранного и скрытого дерева, выборочное удаление, независимые изменения, compensation success/failure, active runtime до release barrier. Import-smoke проверяет глубину архивов и unsafe payload paths. `smoke_desktop_backup_native.py` проверяет desktop ZIP с byte-identical payload, отмену, traversal/missing, atomic failure, читаемую архивную копию и retention после замены активного состояния; strict-check запускает этот тест автоматически.

Ручная/isolated browser проверка: дополнительный стол с документом, событием и ссылкой → × → все флажки выключены → cancel/Escape/Delete/Ctrl+Z без изменений. Выбрать календарь, скачать ZIP: проверить desktop.json со всеми группами (включая календарь), документом и без чужих столов; скачивание не закрывает диалог. Удалить: календаря в retained архиве нет, ссылка и документ остались в archivedDesktops, основной стол их не получил. Reload сохраняет архив. В Windows проверить выбранный путь ZIP, реальное вложение и data/Архив рабочих столов/<id>/desktop.json. Отдельно выбрать links на другом столе: выбранные ссылки исчезают, основной стол остаётся прежним. Проверить маленькое окно, focus/Space/Enter, ошибку и отмену экспорта. При FAIL нужны шаги, выбранные группы, видимая ошибка и console без личных данных.

Подсчёты: добавить РКО → изменить поля → перетащить за ручку на выбранную карточку внутри окна → «Выше»/«Ниже» и границы списка → убрать и вернуть с прежним вводом → перезапустить и проверить порядок. Pointer drop вне окна не меняет данные рабочего стола. Также: пустой список, поиск без результатов, нули/неверный ввод, два окна и другой стол, узкая ширина, отказ сохранения и повтор, JSON/ZIP round-trip.

Подсчёты, размеры и перетаскивание: 1320×840 и широкое окно — две карточки в ряд, 460px — одна; захват за ⠿ показывает целую движущуюся карточку и место вставки. Проверить порядок в сетке, выход за окно, Escape/pointercancel, удержание у края списка для прокрутки и закрытие окна во время жеста. Потянуть ↘ по ширине/высоте, расширить на обе колонки, убрать/вернуть, reload, узкое окно и сброс. Проверить стрелки на ручке размера и доступность прокручиваемого содержимого. Неподтверждённая запись размера (в том числе отказ предварительного сохранения dirty-ввода) возвращает прежний размер и сохраняет текст в окне; затем повтор должен сохранить.

Перенос на позицию карточки: A→B и B→A среди соседних, перенос между рядами в обе стороны; левую/правую половины в двух колонках и верх/низ в одной колонке трактовать одинаково. Источник занимает прежний индекс цели, остальные сохраняют взаимный порядок. Проверить широкую растянутую карточку, reload ввода/размера/порядка, отмену/выход за окно и отказ сохранения → повтор без потери данных.

### Создание и быстрая смена проекта

Категории задач: `node tools/smoke_task_categories.js` использует искусственное VM-состояние и проверяет legacy/межпроектную нормализацию, фильтры, Обзор, сохранение после подтверждения, отказ → повтор, дубликаты и JSON round-trip. `tools/smoke_task_categories_ui.js` экспортирует `runTaskCategoriesSmoke({chromium,startPreview,outputDir})` для установленного Playwright runner, аналогично `runTasksLayoutSmoke`. Он открывает отдельный browser context, искусственный state и allowlisted preview только `app/`, блокирует service worker и внешние запросы. Проверяет создание/отказ/pending/повтор/дубликат, назначение и снятие категории в create/edit, смену проекта без потери текста, три представления, reload, фокус/Escape и отсутствие наложений при 1440/390 px; снимки — `work/task-categories-qa/`. Дополнительно вручную: выбрать категорию в одном окне, открыть другой файловый tasklist, изменить там задачу и вернуться — выбор первого окна сохраняется. Настоящий Windows EXE и установленная PWA проверяются отдельно.

`node tools/smoke_project_overview.js` проверяет синхронный выбор при отложенной записи, объединение ожидающих ID между двумя контроллерами одного store, отказ → явный повтор, защиту нового выбора от старого rollback, ожидание staged создания вне барьера и отклонение сменившегося владельца. Только искусственное VM-состояние.

Browser `runTasksLayoutSmoke` дополнительно проверяет точную надпись «Создать проект», отсутствие browser prompt, Enter/Escape/возврат фокуса, отказ создания без добавления проекта и сохранность названия, повторное сохранение, переключения при удержанном write в настоящей primary queue. Изолированные context/HTTP-preview и синтетические записи обязательны. Вручную в Windows: открыть Задачи, создать проект, быстро переключить несколько проектов и повторить после перезапуска; реальная скорость native-диска и GUI установленной сборки требуют отдельной проверки.

### Постоянные действия карточки задачи

В `runTasksLayoutSmoke` проверяются отсутствие «Ещё», видимость всех пяти кнопок без раскрытия, заполнение ширины панели и отсутствие пересечений между кнопками в списке и на доске при ширинах окна 1870/900/560 px и viewport 390 px. Закрепление сохраняет фокус на кнопке после перерисовки. Проверка проходит на искусственных задачах в отдельном context; снимки `actions-list-*.png` и `actions-board-*.png` показывают панель в обоих представлениях. Вручную проверить редактирование, закрепление, смену срока, уведомление и отмену удаления.

### Форма создания задачи

`runTasksLayoutSmoke` открывает настоящий taskedit/create на искусственных данных и измеряет text range подписи и rect поля: отступ до поля ограничен, однострочные поля имеют компактную одинаковую высоту, ширина формы не растягивается на весь экран. Размеры: 1870×850, 680×520, 560×650 и viewport 390×844 с окном 390×680; узкое внутреннее окно использует одну колонку даже при широком viewport. Нижние кнопки остаются в видимой области. Проверяются сохранность названия/описания при resize, бессрочность, Ctrl+Enter и сохранённая задача после reload. Снимки `task-editor-wide.png`, `task-editor-680.png`, `task-editor-560.png`, `task-editor-390.png` принадлежат тому же изолированному browser run. Редактирование существующей задачи использует прежнюю отдельную вёрстку.

### Дата после бессрочного режима

`runTasksLayoutSmoke` проверяет доступность поля даты после «Бессрочная», снятие режима мышью/Shift+Tab/вводом даты, восстановление последней даты, повторное включение бессрочности и `aria-pressed`. Обе конечные формы проходят создание и reload: выбранная дата остаётся датой в карточке, повторно включённая бессрочность остаётся меткой в метаданных. `task-ui-utils.js#toggleTaskCreateIndefinite` хранит последнюю дату только в dataset поля редактора, без изменения state/schema. Первый regression о недоступном поле сохранён отдельно; тесты используют искусственное browser state.
