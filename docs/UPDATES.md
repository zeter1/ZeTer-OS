# Обновление Windows-сборки ZeTer OS

Автоустановка работает только в готовой 64-битной Windows EXE-сборке с `zeter-update.json` и отдельным `ZeTer-OS-Updater.exe`. Исходный Python-проект и браузер/PWA не заменяются бинарниками. Уже выпущенным версиям без механизма обновления сначала потребуется обычная установка новой сборки.

## Как подготовить и опубликовать обновление

1. Повысить числовую версию MAJOR.MINOR.PATCH в `app/js/core/version.js`, синхронизировать README, CHANGELOG и PWA-кэш по правилам проекта.  
2. Выполнить существующий `build_exe.bat` (`--ci` для проверки без установки WebView2). Сборщик создаёт основную flat-onedir поставку и отдельный onefile-установщик, затем manifest с hashes/размерами и versioned ZIP.  
3. В [GitHub Releases](https://github.com/zeter1/ZeTer-OS/releases) опубликовать новую версию с файлами `dist/ZeTer-OS-<версия>-Windows-x64.zip` и `dist/ZeTer-OS-<версия>-Windows-x64.sha256.txt`. Нельзя переименовывать ZIP в произвольное имя или загружать только главный EXE: нужны все DLL и ресурсы поставки.  
4. В CI существующий `[package]`\-коммит или `workflow_dispatch` собирает и публикует эти файлы. Для `[package]` требуется свежий `RELEASE_NOTES_RU.md` в том же коммите; обычные docs-правки не запускают packaging. Публикация разрешена только из `main` репозитория `zeter1/ZeTer-OS`.

Номер обновления берётся из канала на GitHub Pages, сверяется со строгим именем ZIP и после скачивания — с вложенным manifest. Предлагается только числовая версия строго выше установленной; одинаковая и более старая версия не переустанавливаются. Prerelease поддерживается: канал указывает на конкретный опубликованный пакет. Legacy-архивы без нового контракта не устанавливаются.

## GitHub Pages: включить один раз

В репозитории открой **Settings → Pages → Build and deployment → Source → GitHub Actions**. Платный сервер, личный API-токен в приложении и отдельный сайт не нужны. У репозитория должны быть разрешены Actions и развёртывание environment `github-pages` из `main`. Не включай custom domain для этого канала: клиент принимает только фиксированный адрес `https://zeter1.github.io/ZeTer-OS/updates.json` без перенаправлений.

После загрузки исходников запусти **Actions → CI → Run workflow → main**. CI проверит проект, соберёт EXE/ZIP, создаст Release, скачает опубликованный ZIP по обычной публичной HTTPS-ссылке и сравнит его размер/SHA-256 с проверенной сборкой. Только после успеха создаётся Pages artifact и выполняется `publish-pages`. В Pages вместе с файлом версии публикуется содержимое `app/`, чтобы сохранить браузерную версию приложения. Развёртывание заменяет весь сайт этого репозитория; внешний сайт или дополнительные файлы Pages этим workflow не поддерживаются.

Открой адрес `updates.json` и проверь номер версии и прямую ссылку на ZIP. Если Pages ещё не включён или deploy завершился ошибкой, опубликованный Release остаётся доступным для ручной загрузки, но новый канал не считается готовым. Публикацию Pages после исправления настроек можно повторить через **Re-run failed jobs**. Полный повтор сборки получает новый тег `build-<полный SHA>-<run id>-<attempt>`: ZIP старого релиза не перезаписывается, ссылки прежних клиентов остаются действующими.

Непосредственно перед Pages deployment проверяются текущий SHA `main` и уже опубликованная версия. Повтор старого запуска после нового коммита или попытка понизить номер останавливаются; старый run не возвращает прежний feed/веб-приложение. Если `main` успел измениться, запусти CI для актуального `main`. При неизвестном состоянии канала (offline/повреждённый JSON/отказ сервера) deployment останавливается; только HTTP 404 допускается как первая публикация.

### Формат файла версии

`updates.json` — отдельный файл, не путать с вложенным в ZIP `zeter-update.json`:

{

  "schema": 1,

  "repository": "zeter1/ZeTer-OS",

  "platform": "windows-x64",

  "version": "4.0.16",

  "tag": "build-\<SHA\>-\<run-id\>-\<attempt\>",

  "name": "ZeTer-OS-4.0.16-Windows-x64.zip",

  "url": "https\://github.com/zeter1/ZeTer-OS/releases/download/\<tag\>/ZeTer-OS-4.0.16-Windows-x64.zip",

  "size": 12345678,

  "sha256": "\<64 строчных шестнадцатеричных символа\>",

  "notes": "Краткое описание; подробности — в CHANGELOG."

}

Это пример структуры с заполнителями, а не готовый файл для публикации. Размер/hash нельзя вводить наугад. Источник — окончательный ZIP; генератор сверяет checksum и вложенный manifest. Все поля обязательны, лишние/дублирующиеся поля отклоняются; лимит ответа 64 КиБ, описания — 4000 символов. Вручную подготовленный Release требует отдельного Pages deployment с файлом, созданным из того же ZIP:

python tools/build\_update\_feed.py \--package dist/ZeTer-OS-\<версия\>-Windows-x64.zip \--tag \<точный-тег-релиза\> \--output work/pages/updates.json \--verify-download

Эта команда проверяет публичное скачивание и создаёт локальный feed; сама на Pages ничего не загружает. Штатный путь публикации — CI. Файл версии публикуется последним; при отказе скачивания/проверки предыдущий файл не заменяется. Не понижай опубликованную версию и не меняй содержимое ZIP под уже опубликованной ссылкой.

Установленные версии до этой правки продолжают обращаться к REST API. Для перехода нужно один раз установить новую полную сборку вручную либо получить её старым механизмом, когда API доступен. Автоустановка/rollback сохраняют прежний контракт.

## Сценарий пользователя

При запуске и каждые шесть часов native bridge читает фиксированный `updates.json` на GitHub Pages. Кнопка «Проверить обновления» выполняет ручную проверку. Это обычный HTTPS-запрос, не GitHub REST API: клиент не перечисляет релизы и не расходует API-лимит. После нажатия «Обновить» ZIP скачивается напрямую из Releases, также без REST API. Обычные ограничения/отказы Pages и CDN сохраняются; бессрочная доступность не гарантируется.

Новая версия появляется в центре уведомлений как системное сообщение и в предложении рядом с верхней кнопкой «О ZeTer OS». «Позже» скрывает предложение; обновление остаётся в центре и в разделе «Версия и обновления». Дедупликация использует `source=update:<версия>`; запись сохраняется в уведомлениях рабочих столов. При отключённом интернете действующая версия продолжает работать. Серверный Retry-After/лимит запросов учитывается; повторная ручная проверка во время cooldown не обращается к сети.

Равная/старая версия в корректном feed даёт «Установлена актуальная версия». Непубликованный feed (HTTP 404), отказ доступа (403), ограничение запросов (429), отсутствие соединения и повреждённый feed — разные ошибки проверки; ни одна не означает отсутствия обновлений. Автоматического fallback к API нет. Скачивание и установка не начинаются при одной лишь проверке версии.

Нажатие «Обновить» скачивает и проверяет пакет в фоне. Загрузка отменяется кнопкой «Отмена». После проверки пользовательские действия и новые автоматизации приостанавливаются; завершаются уже поставленные операции, синхронизируются редакторы и ожидается подтверждённая запись состояния. Ошибка сохранения не закрывает программу. Helper подтверждает готовность и точную identity процесса; только затем frontend вызывает обычный `close_app`.

«Что нового» в обоих уведомлениях открывает [CHANGELOG](https://github.com/zeter1/ZeTer-OS/blob/main/CHANGELOG.md). «Обновить вручную» открывает отдельное обычное окно ZeTer OS с инструкцией: экспорт ZIP-бэкапа → скачивание полной сборки из Releases → закрытие → новая пустая папка → копирование всей data → проверка новой версии и обновление ярлыка/автозапуска. Старую папку и бэкап сохраняют; данные нового формата не копируют назад в старую версию. Для браузера предлагается экспорт/импорт ZIP через Центр безопасности данных.

Ссылки на репозиторий и Releases внутри инструкции открываются через штатный обработчик внешних ссылок. Текст можно выделить и скопировать: щёлкнуть по выделенному левой или правой кнопкой мыши → «Копировать», либо нажать Ctrl+C. Левый щелчок вне выделения позволяет выделить другой фрагмент; кнопки и ссылки без выделения сохраняют своё обычное действие.

До нажатия «Обновить» в центре уведомлений, предложении обновления и «О ZeTer OS» показывается отдельное пояснение об автоматическом перезапуске. Оно остаётся видимым при загрузке и установке, в том числе у восстановленного из данных уведомления. Окно закрывается для установки, затем программа запускается сама; нужно дождаться открытия и не запускать её вручную. Сообщения готовности и ожидания закрытия также явно описывают этот порядок. При ручном обновлении запуск новой сборки остаётся ручным.

## Владельцы и границы

После запуска установленной версии сохранённое предложение этой или более старой версии удаляется нормализатором уведомлений на всех рабочих столах. Проверка опирается на текущую `OS_VERSION`, работает без интернета и после импорта старого бэкапа. Предложения более новых версий и остальные уведомления сохраняются. Контракт — [DATA\_MODEL.md](http://DATA_MODEL.md#уведомления-об-обновлениях).

- `app_updater.py` — фиксированные feed/repository, строгий schema/HTTPS/redirect contract, версия, размер/SHA256, ZIP/manifest, preflight и lifecycle подготовки.  
- `update_runner.py` — отдельный процесс, HANDLE родителя, nonce handshake, mutex, durable journal, backup/swap/rollback, read-only probe и перезапуск.  
- `run_zeter_os.py` — пять bridge-действий и gate активных native операций. `ProbeApi` служит отдельной странице без NativeStorageApi/startup normalization/GC.  
- `app/js/core/update-ui-utils.js` — проверки, предложение, прогресс/отмена и порядок save → install → close. `app.js` связывает это с уведомлениями, редакторами и persistence queue.  
- `tools/build_update_package.py`, `build_exe.bat` и `.github/workflows/ci.yml` — единственный binary package workflow. Исходный portable ZIP остаётся отдельным сценарием `build_release.cmd`.  
- `tools/build_update_feed.py` — feed из окончательного ZIP/checksum; optional public-download gate, затем атомарная публикация локального файла. CI публикует Pages только после этого gate.

JavaScript не передаёт URL, каталог установки или команду. Источник — только `zeter1/ZeTer-OS`; TLS не отключается. SHA256 из feed обязателен; имя/версия/tag/точный URL связаны, перенаправления feed запрещены, ZIP допускает только проверенные GitHub CDN redirects. SHA256 выявляет повреждение/перепутанный пакет, но доверие к издателю остаётся доверием к GitHub-репозиторию и его сборке. Секреты доступны только CI, в EXE токена нет.

До распаковки проверяется полный список членов ZIP: traversal, drive/UNC, ADS, device names, короткие 8.3 aliases, trailing dot/space, case/file-directory collisions, special/symlink/encrypted entries и лимиты. Затем сверяются состав, размеры и hashes manifest. Reparse/junction отклоняются на путях staging/target/backup. Локально изменённый owned-файл и неизвестный collision блокируют установку; скрытого повышения прав нет.

Установка меняет только manifest-owned файлы программы. `data`, «Логи проблем» и чужие файлы не входят в замену. Старые program bytes и exact map сохраняются в `data/updates/<уникальная-транзакция>`; при отказе восстанавливаются из journal. Recovery не зависит от сохранности скачанного staging. Rollback автоматически не удаляется.

До обычного запуска новая установленная сборка проходит `--self-test` и отдельный `--update-probe <nonce> <version> <session>`: WebView2/private cache/bridge/version проверяются без пользовательского state. Probe должен подтвердить nonce/version и завершиться; лишь затем происходит commit и normal launch. Этот gate проверяет среду запуска, ресурсы и bridge, но не весь пользовательский сценарий и будущие миграции данных. После обычного запуска нельзя автоматически откатывать бинарники по старому readiness-маркеру.

## Восстановление и evidence

Незавершённый journal блокирует обычный запуск до восстановления. Для сохранённой транзакции доступна команда:

"\<папка ZeTer OS\>\\data\\updates\\\<транзакция\>\\ZeTer-OS-Updater.exe" \--recover "\<папка ZeTer OS\>\\data\\updates\\\<транзакция\>\\journal.json"

Не удаляйте эту папку при ошибке. При отказе полезны версия, точный этап, `journal.json` и `result.json` с удалёнными личными абсолютными путями. Команды и матрица — [TESTING.md](http://TESTING.md); источник публичного API — [NATIVE\_BRIDGE.md](http://NATIVE_BRIDGE.md). Source/синтетические проверки не доказывают реальное обновление установленного EXE, CDN, отключение питания или поведение антивируса.
