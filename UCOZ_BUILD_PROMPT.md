# ЗАДАЧА: собрать ZeTer OS для ручной публикации на uCoz без очистки кэша

Перед выбором сборки прочитай `docs/UCOZ.md`: если меняется только обработчик кэша уже опубликованной версии, используй штатный `--runtime-only-from <её полный ZIP>`, а не новую release-папку. Загружается только worker из `upload-plan.json`; сам план остаётся локально. Сверь активный серверный указатель с архивом до передачи. Не затрагивай Python/EXE ради веб-патча. После передачи проверь точные байты и настоящий runtime/complete через `ZETER_UCOZ_RUNTIME_STATUS`; одинаковый scriptURL не является проверкой версии обработчика.

Я прикрепил ZIP с актуальными исходниками ZeTer OS. Самостоятельно изучи архив и подготовь проверенный веб-пакет для загрузки через файловый менеджер uCoz или FTP в `/portfolio/ZeTerOS/`.

Постоянный адрес запуска: `https://dkl.do.am/portfolio/ZeTerOS/index.html`.

**Итоговый адрес браузера:** после загрузки и обычного reload в строке должен оставаться именно этот `index.html`. Итоговый `/releases/<build ID>/index.html` означает FAIL, даже если версия актуальна. Автоматические переходы допустимы внутри загрузки, но entry должен вернуть постоянный адрес до запуска приложения. У штатного сборщика это `ucoz-entry.js`: закреплённый абсолютный base сохраняет пути неизменяемых ресурсов, затем `history.replaceState` возвращает адрес с query/hash и прежним history.state. Bootstrap входит в precache. Только generated HTML разрешает `base-uri 'self'`, исходный HTML сохраняет `base-uri 'none'`; inline/eval-скрипты запрещены. Проверяй `location.href`, `document.baseURI`, root worker URL/scope, reload и offline отдельно.

**Обязательный результат:** посетитель открывает именно этот прежний адрес из своей старой закладки и получает актуальную сборку после завершённой публикации. Он не знает номер версии, имя папки сборки и никакую новую ссылку. Проверяются и новый посетитель, и человек, у которого уже сохранены старые HTML, загрузчик и Service Worker.

Не предлагай посетителю `?ucoz=...`, `?v=...`, другую страницу, Ctrl+F5, очистку кэша/данных сайта, удаление PWA, отключение кэширования, закрытие всех вкладок или повторное открытие «ещё раз». Не меняй публичную ссылку ради обхода проблемы. Внутренние запросы к metadata/ресурсам могут иметь content hash или технический query; посетитель не должен их вводить или искать. Автоматический переход после проверки версии допустим, публичный вход всегда остаётся прежним.

Нужны готовый ZIP и ссылка на его скачивание. Ничего не публикуй на GitHub/uCoz, не подключайся к FTP и не запрашивай пароли. Не заменяй результат общими рекомендациями или кодом, который мне нужно самостоятельно дописать.

## 1. Сначала установи факты

Распакуй архив в отдельный рабочий каталог. Найди реальный корень проекта, AGENTS.md, README, `app/index.html`, `app/js/core/version.js`, manifest, Service Worker, владельца регистрации PWA и доступные тесты. Версию возьми из исходников, не из имени архива. Не копируй номер версии из примеров этой инструкции.

Если есть `tools/build_ucoz.py`, начни со штатного сборщика, затем проверь его по всем критериям этого промпта:

```text
python -B tools/build_ucoz.py
```

Перед запуском прочитай его и `docs/UCOZ.md`, проверь границы записи. Сборщик использует стандартную библиотеку Python, не требует Windows и не должен запускать native-приложение или читать пользовательскую `data`. Используй вывод команды для поиска результата. Не запускай `.cmd` в Linux. При конфликте уже существующего ZIP используй новый `--output-dir`, не удаляй чужой результат.

Наличие штатного сборщика, успешное выполнение команды и номер версии не доказывают правильность обновления. В прежнем варианте переход со старой плоской публикации требовал специальной ссылки либо следующего повторного reload; по текущим требованиям это FAIL. Не объявляй такой ZIP полностью готовым без исправления и повторной проверки именно первой навигации по старому адресу.

Конкретная прежняя локальная проверка со старой плоской 4.0.19 и её worker при HTTP `max-age=1728000` показала 4.0.19 при первом открытии и 4.0.20 только после следующего обычного reload; маркер данных сохранился. Если её артефакты есть, изучи `work/ucoz-browser/legacy-test.cjs` и `legacy-result.json`. Историческая метка `PASS_WITH_INITIAL_MIGRATION_LIMIT` не является PASS новых требований. Эта fixture задаёт регрессию; актуальную сборку проверяй заново, не копируя старый результат.

Если сборщик отсутствует, реализуй ту же схему только в отдельной подготовленной веб-копии по разделам ниже. Если существующий сборщик не удовлетворяет требованиям, установи конкретную причину и исправь минимальный доказанный дефект; не заменяй его произвольным bundler. Разрешены необходимые изменения загрузки/обновления подготовленного веб-пакета. Сохрани их в воспроизводимом сборщике/шаблонах и отдай отдельно от веб-пакета, чтобы следующая сборка не потеряла исправление. Не прячь ручные post-build изменения только в ZIP.

## 2. Сохранение функциональности

До упаковки проверь ограничения файлового менеджера uCoz: до 30 файлов за один выбор, общий размер выбранных файлов до 200 МБ, до 1000 элементов в каталоге, глубина до 10 папок вместе с `portfolio/ZeTerOS`, имя файла до 45 символов, папки — до 15. Папки — только латинские буквы, цифры, `_`, `-`; файлы могут содержать точки расширения. Реальная попытка создать папку версии с точками ранее дала `553 Prohibited file name`. Используй build ID `vCONTENT_HASH`: буква v и 14 hex-символов SHA-256, всего 15 символов; версия приложения и metadata остаются фактической semver с точками. Проверь каждый путь ZIP, а не только имя сборки. В файловом менеджере файлы с одинаковыми именами перезаписываются.

Лимит 30 относится к выбору файлов в этом интерфейсе. Инструкция должна разбивать передачу по каталогам назначения и партиям до 30, с проверкой общего размера. Не переносить это число на FTP/API без проверки и не выдавать поддержку FTP за проверку файлового менеджера. Не предлагай загрузить один ZIP и распаковать его на сервере без доказанной функции uCoz. Не сокращай имена только в готовом ZIP/на сервере без исправления и проверки всех ссылок в воспроизводимом источнике.

- Не объединяй, не минифицируй и не переставляй JavaScript/CSS.
- Не меняй области видимости, порядок исходных `<script>`, обработчики инициализации и событий.
- `app.js` должен загружаться ровно один раз. Ранее его двойное подключение после объединения JS ломало меню «Пуск» и уведомления — не повторяй это.
- Не сокращай количество файлов. Сохрани необходимые изображения, значки, модули, шрифты и другие ресурсы, включая неизвестные, пока их назначение не установлено.
- Не меняй возможности ZeTer OS, DOM, темы, окна, приложения, сохранение или формат данных ради упаковки.
- Не включай Python, EXE, зависимости разработки, Git, секреты, реальные пользовательские данные, резервные копии и журналы в веб-пакет.
- Исходное Windows-приложение не переделывай. Изменения интеграции PWA допускаются в подготовленном веб-пакете и должны быть перечислены в отчёте.

## 3. Схема публикации и кэша

Цель: после полностью завершённой загрузки новой сборки её можно открыть обычным переходом/обновлением страницы без Ctrl+F5, ручной очистки кэша и удаления данных сайта. Открытую рабочую вкладку нельзя принудительно перезагружать: это может потерять несохранённые изменения.

Используй неизменяемые папки сборок, общий вход и переключатель:

```text
index.html
ucoz-loader.js
release.json
manifest.json
service-worker.js
releases/
  vCONTENT_HASH/
    index.html
    js/...
    css/...
    assets/...
    прочие необходимые файлы веб-приложения
```

Это содержимое корня ZIP; не добавляй внешнюю папку `app`, `ZeTer OS` или имя архива. Внутри папки сборки сохрани оригинальную веб-структуру. В дальнейших шагах `<build ID>` означает фактическое `vCONTENT_HASH`, без точек и в пределах 15 символов. `CONTENT_HASH` вычисляй по точным байтам подготовленного immutable-payload и entry-bootstrap, отдельно от корневого worker/загрузчика; он должен меняться при изменении ресурсов даже с прежним номером версии. Не записывай новые байты под старые адреса сборки.

Общий `index.html` — постоянный загрузчик: получает `release.json` с `cache: "no-store"` и уникальным параметром запроса, проверяет HTTP-статус и структуру JSON, затем открывает соответствующий `releases/<build ID>/index.html`. Путь допускается только внутри этой публикации, без стороннего origin, `..` и произвольных redirect. При ошибке покажи понятное сообщение и повтор по действию пользователя, без бесконечного redirect/reload. Не вставляй HTML из JSON через innerHTML.

**Проверь всю цепочку загрузки:** старый URL → HTML → загрузчик → release.json → Service Worker → index сборки → JS/CSS/остальные ресурсы. Обновление только последнего `app.js` или release.json не исправляет устаревший код раньше в цепочке. Постоянный `ucoz-loader.js` безопасен лишь при доказанно совместимом протоколе и корректной проверке актуальности; неизменность имени сама по себе не доказывает баг. Если меняется его логика, обеспечь получение нужного кода и проверь это при прогретом кэше загрузчика. Версионирование `src` загрузчика в новом HTML само по себе тоже недостаточно: закэшированный старый HTML продолжит ссылаться на старый `src`.

Изучи фактические HTTP Cache-Control/ETag/Last-Modified/Age, если сайт доступен для публичного чтения. `max-age=1728000` (20 дней) — обязательная локальная стресс-fixture по ранее обнаруженным условиям, а не доказательство сегодняшней конфигурации сервера. Различай HTTP-кэш браузера, Service Worker CacheStorage, серверный/CDN-кэш и уже работающую страницу. `fetch(..., {cache: "no-store"})` не заставляет загрузиться код, который ещё не выполняется; `updateViaCache: "none"` относится к worker-скриптам и не обновляет автоматически HTML/загрузчик. Не ослабляй CSP до unsafe-inline/eval ради вставки bootstrap.

Полный URL в новой папке меняется для всего дерева ресурсов: обычных скриптов, CSS, вложенных `@import`, `url(...)`, изображений и динамических относительных путей. Не считай `?v=VERSION` на одном `app.js` решением: текущий исходный Service Worker может удалять search-параметры перед поиском в кэше и возвращать старые файлы.

Оставь одну регистрацию общего Service Worker в корне публикации с ограниченным scope `/portfolio/ZeTerOS/` и `updateViaCache: "none"`; его путь из папки сборки должен разрешаться в корневой worker. Сохрани защиту native-режима. Общий manifest должен иметь постоянные start_url/scope/id и правильные пути значков. У исходного приложения порядок JS не меняется; минимальные необходимые изменения — ссылка manifest и путь/опции регистрации PWA.

Service Worker должен:

1. Заново получать указатель версии при навигации на постоянный адрес и обычном reload страницы сборки. При отличии пути переходить на новую сборку. Metadata не выдавать cache-first.
2. Кэшировать неизменяемые ресурсы отдельным именем с путём scope и build ID; считать offline-сборку доступной только после завершения precache. Неполная установка не должна заменять рабочую offline-копию.
3. Сравнивать полный URL ресурсов. Не подставлять HTML fallback вместо недостающего JS/CSS.
4. При отсутствии сети использовать ранее полностью закэшированную сборку, не выдавая её за новую. Не зависать в цикле перенаправлений.
5. Сохранять старые версии ресурсов для открытых вкладок; не удалять все CacheStorage на origin, чужие Service Worker и чужие кэши.
6. Никогда не очищать localStorage, IndexedDB, файлы виртуальной системы, настройки, ключи шифрования или пользовательские документы.

Активация нового worker и отображение новой версии — разные события. `skipWaiting()`/`clients.claim()` сами по себе не заменяют уже исполняемый старый JavaScript. Проверь миграцию со старым worker на прежнем script URL и scope. Во время нового открытия разрешён ограниченный автоматический переход до готовности рабочего интерфейса; он должен приводить к актуальной полной сборке без циклов. Не делай безусловные `location.reload()` на каждом `controllerchange`, массовые `client.navigate()` или таймеры принудительного обновления уже работающих вкладок. Если для безопасного перехода нужен сигнал готовности/сохранения, докажи его наличие у старой страницы; не предполагай, что ранее опубликованный код уже умеет отвечать новому протоколу.

Сохрани origin и имена хранилищ. Перенос URL внутри того же origin не является основанием для сброса данных. Проверь реальные ключи/имена баз текущего проекта.

Не обещай, что ZIP способен мгновенно заменить код, который браузер ещё ни разу не получил. Если для конкретной старой публикации безопасный первый переход при неизменном URL нельзя обеспечить только файлами, установи и покажи причинную цепочку и минимальную необходимую настройку хостинга. Это конкретный блокер цели, а не разрешение выдать специальную ссылку или требование ручной очистки. Meta `Cache-Control` не заменяет HTTP-заголовки. Не рассчитывай на `.htaccess`, PHP, серверные redirects или настройку заголовков без подтверждения поддержки uCoz. Даже новые заголовки не отменяют мгновенно прежний свежий HTTP-кэш у посетителя. При недоступном live uCoz укажи NOT_VERIFIED; при воспроизведённом нарушении старого URL — FAIL. Не называй такой результат полностью соответствующим требованиям и не стирай первый неуспешный результат последующим успешным reload.

## 4. Проверки перед выдачей ZIP

- Проверь состав ZIP, CRC, отсутствие дубликатов, traversal и лишней внешней папки; распакуй его в чистый каталог и сравни байты с подготовленной копией.
- Проверь все статические локальные ссылки HTML/CSS, вложенные импорты, manifest и значки. Отдельно изучи динамические пути JS; статическая проверка не доказывает их все.
- Выполни доступный `node --check` для JS, профильные тесты упаковки и существующие безопасные проверки проекта после изучения их side effects и изоляции.
- Сравни списки скриптов до/после: порядок одинаковый, повторных подключений нет. Перечисли каждое отличие байтов JS/CSS от исходника и его необходимость; CSS/JS не объединять.
- Запусти распакованную сборку через локальный HTTP, в подпапке `/portfolio/ZeTerOS/`, в отдельном browser context с искусственными данными. Не используй реальные browser profile или `data` пользователя.
- Проверь «Пуск», запуск приложения, панель задач/окна, уведомления, настройки, файл/заметку и сохранение после reload; консоль и Network не должны содержать необъяснённых ошибок.
- Главная проверка обновления: открыть A и прогреть HTTP/SW-кэши с обычными настройками браузера; сохранить тестовые задачу/заметку и настройки; подготовить B с другим build ID; загрузить новые файлы, затем заменить `release.json`. В том же browser context выполнить ПЕРВОЕ обычное открытие ТОЧНО `https://dkl.do.am/portfolio/ZeTerOS/index.html` (локально — тот же origin/path без query). До начала редактирования должна открыться B. Отдельно проверить обычный reload старой вкладки. Подтвердить build ID B, новые URL всех загруженных JS/CSS, отсутствие двойной инициализации и сохранность ID/содержимого тестовых данных. Не применять hard reload, DevTools Disable cache, unregister/clear storage или новый профиль между A и B.
- Обязательная матрица: (а) чистый посетитель открывает прежний URL; (б) посетитель со старой плоской версией и исходным worker; (в) посетитель со старой сборкой нового формата; (г) старые HTML и загрузчик в HTTP-кэше с max-age=1728000; (д) изменённая логика загрузчика между A/B; (е) две вкладки: работающая A с черновиком остаётся нетронутой, новое открытие прежнего URL получает B. Каждый сценарий использует собственную изолированную fixture, но профиль внутри его перехода A→B сохраняется. Не подменяй проверку наследованного worker только двумя сборками нового формата.
- Запиши доказательства первой навигации: исходный URL, HTTP-заголовки fixture, последовательность document/loader/metadata/worker-запросов, controller/update-события, активный build ID и проверку данных. Если первая навигация осталась A, а вторая показала B, первая проверка — FAIL. Одного нового номера кеша, успешной регистрации worker или номера версии в заголовке окна недостаточно.
- Пока B ещё передаётся и release.json не переключён, A должна продолжать открываться. Уже открытая вкладка A не должна сама перезагрузиться после переключения.
- После успешного precache проверь offline-запуск и отсутствие redirect-loop. Установленную PWA и реальный HTTPS uCoz проверяй только при фактической доступности.

Для каждой невыполненной проверки укажи NOT_VERIFIED и конкретный следующий шаг. Не называй полный интерфейс проверенным только потому, что открылся HTML. Не выдавай локальный тест за тест хостинга.

**Запрет ложной приёмки:** сборка не считается готовой по этой задаче, если для получения B понадобилась новая публичная ссылка, ручная очистка, дополнительный пользовательский reload после первого открытия, сброс данных или принудительное прерывание другой рабочей вкладки. При блокере можно приложить кандидат и диагностику, явно указав не выполненный критерий; это не готовая рабочая публикация.

## 5. Выдача и инструкция загрузки

Назови ZIP `ZeTer-OS-uCoz-FTP-VERSION.zip`, где VERSION — фактическая версия исходников. Дай прямую ссылку на скачивание готового файла в среде чата.

Кратко сообщи версию, build ID, состав, число файлов, SHA-256, необходимые изменения и способ воспроизвести ZIP из исправленного сборщика/шаблонов. Для каждого критерия из раздела 4 дай компактную таблицу: сценарий → `PASS`/`FAIL`/`NOT_VERIFIED` → конкретное доказательство → следующий шаг. Отдельно обозначь локальный HTTP, публичный HTTPS uCoz, файловый менеджер и установленную PWA. Публичное чтение сайта не равно праву публикации. Если доказанный дефект исправить в доступной среде нельзя, приложи кандидат и диагностику с точным блокером; статус «готово» недопустим.

Инструкция пользователю:

1. Сохранить резервную копию заменяемых корневых веб-файлов и `release.json`; перед первой миграцией экспортировать данные штатным способом.
2. Распаковать ZIP. Загрузить распакованное содержимое в `/portfolio/ZeTerOS/`.
3. Сначала полностью передать новую `releases/<build ID>/`: в файловом менеджере создать каталоги и передавать файлы каждого каталога партиями до 30 и суммарно до 200 МБ за выбор. Затем передать общие loader/index/manifest и Service Worker. Проверить завершение всех передач и точный каталог назначения.
4. `release.json` заменить ПОСЛЕДНИМ; если возможно — загрузкой временного имени и переименованием. Не переключать указатель на неполную папку.
5. Не удалять прежние папки releases и файлы старой плоской публикации: они могут требоваться открытым вкладкам и для отката.
6. Открыть постоянный URL обычным способом. Уже первое открытие после завершённой публикации должно показывать актуальную сборку; текущая работа в другой вкладке продолжается без принудительной перезагрузки. Дополнительный пользовательский reload для исправления первого не считается успехом.

В итоговой инструкции посетителю указывай только исходный адрес без query и без требования знать о выпуске. Никакой отдельной «ссылки первого запуска». Если приёмка старой закладки не пройдена, сообщи владельцу сайта точный FAIL/NOT_VERIFIED и минимальный следующий шаг; не перекладывай обновление на посетителя и не представляй обходной URL выполнением задачи.

Технический откат указателя не гарантирует совместимость уже изменённых пользовательских данных со старым кодом. Не обещай автоматического отката формата данных.

Приоритет: рабочие функции и сохранность данных, затем доказанное обновление без очистки кэша. INSPECT → PLAN → BUILD → VERIFY → REVIEW → DELIVER. Если выполнить действие в среде нельзя, сообщи конкретный блокер и выдай доступные артефакты с честными границами проверки.
